## 新增卡片：协议支付的上划下拨（E4-02）

- 用户问题：协议支付的上划下拨，为什么只有下拨要对内部户冻结；要求从负债/权益切入，产品层面设计完整资金流与交易流。
- 归类：挂「账务与账户」（E4），关联「资金安全」（E5）与「清算与结算」（E2）；`direction: 支付清算`，`event: 项目实践`。
- 核心论点（这是这张卡的骨架，别改散）：
  1. 内部户余额在会计上是**负债**（应付账款），不是平台资产；平台只是代持。
  2. 上划平台是收款方，钱到了才确认负债，晚确认没有风险；下拨平台是付款方，钱一出账资产就减，负债要等回执才能减，中间必须锁住。
  3. 冻结不是扣钱，是**负债的内部结构调整**（可用→冻结，总额不变）；真正的负债减少在到账确认时与资产减少同时发生。
  4. 全程 `资产 = 负债 + 权益` 成立；不冻结的三种击穿路径：重复下拨、下拨在途又提现、退票未冲回。
  5. 判据是资金流向不是业务名称：凡平台往外付钱（下拨/提现/退款/代付）都要冻结。

## 重写卡片：热点账户分档解法（B6-01）

- 用户问题：什么是热点账户、怎么解频繁读写、怎么保证资金不出错；要求**按交易量从低到高**讲方案，考虑落地成本与收益，不要一味「百亿流量」。

- 骨架（别改散）：
  1. **先分三类**：入账型 / 扣款型 / 读热点。**缓冲合并只对纯入账安全**，扣款型合并成净额会掩盖单笔余额不足。
  2. 单账户 TPS ≈ 1000 ÷ 持锁毫秒；**加机器无效**（写只走主库、同账户同一分片）。
  3. **账户性质定上限**：用户资金户（备付金）账必须落库 → 第 2 档封顶；平台自有资金可透支 → 才敢上第 4 档内存账本。
  4. 五档：<200 只保正确性 / 200~1000 事务瘦身+按账户串行 / 1000~1 万 缓冲合并 / 1 万~10 万 拆子账户 / >10 万 换账本。每档带成本（人周/月/季/半年）与风险。
  5. **扛量与不出错是两条线**：性能方案换并发度，四条不变量不换（唯一键幂等、余额与流水同事务、每批守恒、日终对账）。
  6. 真实量级：热点大多 200~800 TPS，第 1 档就够；跳到第 3 档换来的是更复杂的对账。
- 项目细节（可复用素材）：某支付公司结算户 800 TPS → 事务瘦身 + 分桶串行 + 100ms 批量，update 800→10 次/秒，P99 2s→80ms；某分润平台手续费户是**扣款型**，用额度预分配（号段式）而非缓冲；某银行代发**分片键一开始选付款账户导致等于没分**，改收款账户才对。

## 侧栏跟随当前文章（交互）

- 用户问题：打开某篇文章后，左侧目录不定位，还得自己找在哪个分类下。
- 原因：`markSide()` 原来只给 `.slink` 加 `.on` 高亮。折叠组里 `.slink` 是 `display:none`，高亮了也看不见；展开时长列表里条目也可能在视口外。
- 改法（`theme/app.js` 的 `markSide` + 新增 `revealCurrent`）：
  1. 当前项在折叠组里 → 自动展开该组，`folds[dir]=false` **只改内存不改存档**，并 `syncFoldBtn()` 同步按钮文案。
  2. 不在可视区 → 滚到可视区中间偏上（40% 处）；已可见则不动，避免切页抖动。
  3. 顺带把分组标题带进视野（`.sgroup` 上内边距 16px，判断文字顶而不是元素顶），并给组标题加 `.cur`（蓝字 + 左侧 2px 竖条）。
  4. `markSide({scroll:false})` 用于进度按钮刷新：不滚动、不强行展开，否则用户刚点的「全部折叠」会被「能讲」破功。
- 可视区顶部要按 sticky 工具条 `.side-tools` 的 `getBoundingClientRect().bottom` 算，不能用 `offsetHeight + 12`（实测 barH 45，组标题 top 47，用 offsetHeight+12=57 会误判为不可见）。
- 验证脚本 `/tmp/side_test.py`、`/tmp/side_test2.py`、`/tmp/smoke.py`（CDP）：定位、折叠后重进、全部折叠、相邻不跳、进度不展开、场景题、刷新冷启动、九路由无报错。
