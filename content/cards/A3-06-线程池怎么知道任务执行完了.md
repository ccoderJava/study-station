## 30 秒简述

**线程池本身不提供「一批任务跑完了」这个事件。** 它只有「提交」和「线程空闲」两个动作，没有批次边界的概念——因为它根本不知道你提交的哪些任务属于同一批。

要知道完成，只能靠**外部引入一个「计数或信号」**。三种思路：

1. **拿凭证逐个问**：`submit()` 返回 `Future`，`get()` 阻塞等结果。
2. **放个计数器**：`CountDownLatch`，每个任务结束时减一。
3. **等整个池子关门**：`shutdown()` + `awaitTermination()`——粒度最粗，且池不可复用。

还有两个更工程化的：**`CompletionService`**（谁先完成先拿谁，边跑边处理）、**`CompletableFuture.allOf()`**（异步编排，不阻塞提交线程）。

**面试的关键分水岭**：能说出 `execute` 与 `submit` 的差别（前者无返回、异常走 handler，后者吞进 Future）、能说清 `Future.get()` 在同一个池里嵌套调用会死锁、能说出 `shutdown` 之后 `isTerminated` 为什么可能永远是 false。

## 是什么

### 一、为什么这是个真问题

```java
ExecutorService pool = Executors.newFixedThreadPool(8);
for (Task t : tasks) {
    pool.execute(t);        // 返回 void，什么都没给
}
// 此刻 8 个线程在跑，队列里还排着一堆，但主线程完全不知道进度
```

三个结构性原因：

1. **`execute()` 返回 `void`**——没有句柄，问都不知道问谁。
2. **线程是复用的**——不能用 `Thread.join()`，那个线程跑完你这个任务还会去跑下一个。
3. **线程池不记录「批」的概念**——它眼里只有「一个接一个的任务」，你的业务批次它不知道。

所以「等一批任务跑完」这件事，**必须由调用方自己构造**。这就是所有方案的共同点。

### 二、先分清 `execute` 和 `submit`

这是所有方案的起点，也是最容易答错的地方：

| | `execute(Runnable)` | `submit(...)` |
|---|---|---|
| 返回 | `void` | `Future<T>` |
| 任务异常 | **抛给线程的 `UncaughtExceptionHandler`**，可通过 `ThreadFactory` 捕获 | **吞进 `Future`**，不调用 `get()` 永远不知道 |
| 用途 | 只管跑，不关心结果 | 需要结果、需要知道成败 |

**最阴的坑**：`submit()` 提交的任务抛异常，如果没人调 `get()`，**异常就静默消失了**——日志没有、告警没有，任务像是没执行过。批量任务里这会导致「少跑了 100 个分片，但没人知道」。

### 三、六种方案

#### 方案 1：`Future.get()` —— 逐个等

```java
List<Future<Result>> futures = new ArrayList<>();
for (Task t : tasks) {
    futures.add(pool.submit(() -> handle(t)));   // submit 才有 Future
}
for (Future<Result> f : futures) {
    Result r = f.get();        // 阻塞直到这个任务完成
}
```

**特点**：简单直接，能拿到每个任务的结果和异常。

**两个坑**：

- **顺序等待会拖长总耗时**：`f.get()` 按提交顺序等，如果第 1 个任务特别慢，后面 999 个早就完成了也得等它。总耗时 = 最慢的那条链，而不是平均。
- **`get()` 不带超时会永久阻塞**：任务死循环、或者内部又等锁，主线程就卡死了。**生产代码必须带超时**。

```java
f.get(30, TimeUnit.SECONDS);   // 必须带超时
```

#### 方案 2：`invokeAll()` —— 批量等

```java
List<Callable<Result>> callables = ...;
List<Future<Result>> futures = pool.invokeAll(callables);   // 全部完成才返回
```

**特点**：一行搞定，内部就是「提交全部 + 逐个 get」。**阻塞直到全部完成**。

**坑**：`invokeAll` 有超时版本 `invokeAll(tasks, timeout, unit)`，但它的语义是「超时后**取消所有未完成的任务**」并抛 `CancellationException`，**不是「返回已完成的部分」**。想要「尽力而为」不能直接用它。

#### 方案 3：`CountDownLatch` —— 自己数

```java
CountDownLatch latch = new CountDownLatch(tasks.size());
for (Task t : tasks) {
    pool.execute(() -> {
        try { handle(t); }
        finally { latch.countDown(); }   // ← 必须 finally，异常也要减
    });
}
latch.await();                    // 或者 latch.await(5, MINUTES)
```

**特点**：最灵活。不关心返回值时最轻量，也不用给每个任务分配 `Future` 对象。

**三个必须注意的点**：

1. **`countDown()` 必须在 `finally`**——否则任务抛异常，计数永远不减，`await()` 卡死。
2. **`count` 必须和实际提交的任务数完全一致**——循环里如果因为拒绝策略丢了任务，`count` 就永远到不了 0。这也是「用 `CallerRunsPolicy` 时安全、用 `DiscardPolicy` 时危险」的原因。
3. **`await()` 必须带超时**，否则上游一旦卡住就是永久阻塞。

**`CountDownLatch` 是一次性的**——计数到 0 就不能重置，想复用要 `CyclicBarrier` 或新建。

#### 方案 4：`CompletionService` —— 谁先完成先拿谁

```java
CompletionService<Result> cs = new ExecutorCompletionService<>(pool);
for (Task t : tasks) cs.submit(() -> handle(t));

for (int i = 0; i < tasks.size(); i++) {
    Future<Result> f = cs.take();       // 阻塞，返回"已完成"的下一个
    save(f.get());                       // 立刻处理，不用等最慢的那个
}
```

**它解决了方案 1 的核心痛点**：不用按提交顺序等，**完成一个处理一个**。

内部实现很简单：`ExecutorCompletionService` 持有一个 `BlockingQueue<Future>`，把任务包一层——跑完先 `queue.put(future)` 再返回。所以 `take()` 拿到的必然是已完成的。

**适用**：处理结果可以流式消费的场景（边跑边落库、边跑边汇总）。**不适用**：必须等全部结果才能决策的场景（比如「全部分片成功才算对账通过」）。

#### 方案 5：`CompletableFuture.allOf()` —— 异步编排

```java
CompletableFuture<?>[] all = tasks.stream()
    .map(t -> CompletableFuture.supplyAsync(() -> handle(t), pool))
    .toArray(CompletableFuture[]::new);

CompletableFuture.allOf(all).join();      // 等全部完成
// 此时每个 future 的 get() 不会阻塞
List<Result> results = Arrays.stream(all).map(CompletableFuture::join).toList();
```

**特点**：可以**串联、组合、异常处理**，是 JDK 8 之后异步编排的标准做法。

**三个坑**：

1. **`allOf` 只在全部完成时完成，不传播异常**——某个任务挂了，`allOf` 照样「正常完成」，必须逐个 `join()` 或 `get()` 才能看到异常。
2. **默认用 `ForkJoinPool.commonPool()`**——不传 `pool` 的话，IO 密集任务会把公共池打满，影响整个 JVM 里所有用默认池的代码。**必须显式传自己的线程池**。
3. **`join()` 抛 `CompletionException`**（unchecked），`get()` 抛 `ExecutionException`（checked），异常类型不同，捕获写法不一样。

#### 方案 6：`shutdown()` + `awaitTermination()` —— 等整个池关门

```java
pool.shutdown();                                        // 不再接受新任务
boolean done = pool.awaitTermination(5, TimeUnit.MINUTES);  // 等所有任务结束
if (!done) pool.shutdownNow();                          // 超时强制中断
```

**这是最粗的粒度**，且有两个硬伤：

1. **池被关掉了**，不能再用。如果这是个共享的 Spring Bean 线程池，等于把整个应用的这个能力废了。
2. **没有「批次」概念**——池里如果有别的任务，你会连它们一起等。

**正确用途**：**服务关闭时的优雅停机**（`@PreDestroy` 里调用），不是「等一批任务」。

### 四、`shutdown` 之后 `isTerminated` 为什么可能是 false

这是面试高频追问，需要理解线程池的状态机。

线程池把**运行状态和线程数打包在一个 `AtomicInteger ctl`** 里：

```
ctl = (runState << 29) | workerCount
      高 3 位 → 状态          低 29 位 → 线程数（上限约 5 亿）
```

一个 int 同时管两件事，好处是状态和线程数**永远一致**（一次 CAS 同时改），代价是要位运算。

五种状态：

| 状态 | 值 | 含义 | 还会执行队列任务吗 |
|---|---|---|---|
| `RUNNING` | 高 3 位 `111` | 正常，接受新任务并处理队列 | 是 |
| `SHUTDOWN` | `000` | 不接受新任务，**继续处理队列** | **是** |
| `STOP` | `001` | 不接受新任务，不处理队列，**中断进行中的任务** | 否 |
| `TIDYING` | `010` | 所有任务已终止，`terminated()` 钩子即将执行 | 否 |
| `TERMINATED` | `011` | `terminated()` 已执行完毕 | 否 |

**`isTerminated()` 只有在 `TERMINATED` 时才返回 true**，而进入 `TERMINATED` 的条件是「队列为空 **且** 工作线程数为 0」。

所以 `shutdown()` 之后 `isTerminated()` 还是 false，是**正常的**：`SHUTDOWN` 状态下线程池**还在把队列里剩下的任务跑完**，只有全部跑完、线程全部回收，才会进 `TIDYING` → `TERMINATED`。

**两个常见误解**：

- 以为 `shutdown()` 会立刻停止一切——它只是「关门，里面的人把手上的活干完」。
- 想立刻停就 `shutdownNow()`——它返回**还没开始执行的任务列表**（这个返回值一定要处理，否则任务静默丢失），并中断正在跑的线程。

### 五、`FutureTask` 内部是怎么「等」的

`FutureTask` 是 `Future` 的默认实现，`submit` 提交的 `Runnable` 会被包成它。内部结构：

```java
private volatile int state;        // 状态机
private Object outcome;            // 结果 或 异常
private volatile Thread runner;    // 正在执行它的线程
private volatile WaitNode waiters; // 等待者栈（Treiber stack，无锁）
```

**状态流转**（只能单向）：

```
NEW ──► COMPLETING ──► NORMAL       （正常完成）
 │           └──────► EXCEPTIONAL  （抛异常，异常存在 outcome）
 ├────► CANCELLED                    （取消，未开始执行）
 └────► INTERRUPTING ──► INTERRUPTED （取消，正在执行 → 中断）
```

`get()` 的逻辑：

1. 状态 `<= COMPLETING` 说明还没跑完 → 把自己压进 `waiters` 栈 → `park()` 挂起。
2. 完成时 `finishCompletion()` 遍历 `waiters` 栈，逐个 `unpark()`。
3. 醒来后按状态返回 `outcome` 或抛异常包装。

**这就是「`get()` 会阻塞」的实现**——不是轮询，是 park/unpark（和 AQS 同一套底层机制）。

## 为什么这么设计

**为什么线程池不内建「批次完成」回调**：线程池的抽象层级是「任务」，不是「批」。如果内建批次，就得引入「批 ID」「批状态」「批回调」，复杂度爆炸，而且绝大多数提交方根本不关心批次。**JDK 选择把这件事交给调用方组合**——`Future`、`CountDownLatch`、`CompletionService` 都是可组合的小积木。

**为什么 `execute` 不返回 `Future`**：为了省开销。`Future` 需要分配对象、维护 waiters 栈，一个纯执行的任务不需要这些。**这是「显式选择成本」的设计**——你要结果就 `submit`，不要就 `execute`。

**为什么 `CompletionService` 要包一层队列**：因为 `Future` 本身没有「完成通知」机制，`get()` 只能阻塞。要「谁先完成先拿谁」，只能让任务完成时主动往一个队列里扔信号——**队列就是这个信号的中转站**。

**为什么 `ctl` 要压进一个 int**：如果状态和线程数分开存，就可能出现「状态已变 SHUTDOWN，但线程数还没更新」的中间态，导致判断出错（比如判断「能不能关」时看到脏数据）。压进一个 int 后，一次 CAS 同时改两者，**天然一致**。

## 不用会怎么样

- **只 `execute` 不等待**：主线程以为提交完就结束了，实际任务还在跑；进程退出、容器重启，任务全部丢失。
- **`submit` 后不看 `Future`**：异常被静默吞掉。批量对账里表现为「结果少了，但日志干净得像没出错」。
- **`Future.get()` 不带超时**：某个任务死锁，主线程永久挂起，整个批次卡住。
- **`CountDownLatch` 的 `countDown()` 不在 `finally`**：一个任务抛异常，`await()` 永远等下去。
- **在同一个线程池里嵌套 `get()`**：任务 A 提交任务 B 到同一个池，然后 `get()` 等 B。池满时 B 排不上队、A 占着线程不放手 → **线程池死锁**。这是最隐蔽的一类死锁。
- **用 `shutdown()` 等批次**：共享池被关掉，后续所有提交抛 `RejectedExecutionException`。

## 替代方案

| 方案 | 粒度 | 是否阻塞调用方 | 适用 |
|---|---|---|---|
| `Future.get()` | 单个任务 | 是 | 需要每个任务的结果 |
| `invokeAll()` | 一批（全完成） | 是 | 批处理，且必须全成功 |
| `CountDownLatch` | 一批（计数） | 是（可超时） | 不需要返回值，只要「都跑完」 |
| `CompletionService` | 流式（先完成先拿） | 是（`take()`） | 边跑边处理，不让慢任务拖后腿 |
| `CompletableFuture.allOf` | 一批 + 可编排 | 否（`join` 才等） | 异步链路编排、需要组合依赖 |
| `shutdown + awaitTermination` | 整个池 | 是 | **优雅停机**，不是等批次 |
| `Phaser` | 多阶段、可复用 | 是 | 分批同步、动态增减参与者 |

## 项目中如何使用

- **某银行对账千分片汇总**：1000 个分片（按银行 + 业务类型切分）提交到固定线程池，用 `CountDownLatch` 等全部结束，再统一汇总。为什么不用 `invokeAll`——因为分片之间互不依赖，任何一个分片失败不应该影响其他分片跑完，用 `latch` 能收集「哪些成功、哪些失败」，而 `invokeAll` 是「一个失败整批异常」的语义。`countDown()` 放在了 `finally` 里，这是上线前 code review 卡住的一条。
- **代发批量结果统计**：用 `CompletionService`，每完成一个分片就把结果落库并累加成功/失败笔数。好处是**进度可观测**——运营能实时看到「已处理 600/1000」，而不是盯着一个转圈等 20 分钟。慢分片（某家银行接口特别慢）也不会拖住其他分片的结果写入。
- **某支付公司流量回放**：回放任务量大（百万级请求），用 `CompletableFuture` 分批编排，每 1000 个请求一个批次，批内 `allOf().join()`，批间串行推进。这样内存可控，且任意一批失败可以单独重跑。**显式传了自定义线程池**——默认的 `commonPool` 只有 CPU 核数 - 1 个线程，IO 密集的回放会立刻打满。
- **一次真实事故**：`CountDownLatch` 的 `count` 用了 `tasks.size()`，但线程池配了 `DiscardPolicy`，队列满时任务被静默丢弃，`countDown` 次数不足，主线程 `await()` 卡了 30 分钟直到超时。之后规约：**用 `latch` 就必须保证任务不被丢弃**（`CallerRunsPolicy` 或 `AbortPolicy` + 显式处理拒绝）。

## 常见陷阱

- **`submit` 之后不 `get`，异常静默丢失**——`submit` 的异常存在 `Future` 里，不取就永远看不到。批量任务要么 `get`，要么在任务内部自己 try-catch 打日志。
- **在池内嵌套等待同一个池**：死锁。要么用不同的池（一个给「等待方」一个给「执行方」），要么改成异步回调。
- **`invokeAll` 超时的语义搞错**：它超时会**取消未完成的任务**，不是返回部分结果。
- **`CountDownLatch` 用完想重置**：做不到，它是单向的。要复用选 `CyclicBarrier` 或 `Phaser`。
- **`CompletableFuture` 不传线程池**：默认用 `ForkJoinPool.commonPool()`，IO 任务会污染公共池。
- **`allOf` 之后不检查各 future 的异常**：`allOf` 只保证「都结束了」，不保证「都成功了」。
- **`awaitTermination` 的返回值不检查**：返回 `false` 表示超时，此时应该 `shutdownNow()` 并记录剩余任务，而不是直接往下走。
- **`shutdownNow()` 的返回值丢弃**：它返回未执行的任务列表，丢掉就是「以为取消了，实际任务没了也不知道」。

## 三层追问

1. **`Future.get()` 和 `CountDownLatch.await()` 到底差在哪？**——`Future` 是**每个任务一个**的句柄，能拿到返回值、能拿到异常、能取消单个任务；`latch` 是**一个整体计数**，只知道「都到齐了」，不知道谁成谁败。所以**要结果用 `Future`，只要「都跑完」用 `latch`**（后者更轻，不用为每个任务分配对象）。
2. **为什么说 `shutdown` 不能用来等一批任务？**——三个原因：它会让池拒绝后续所有提交（共享池等于报废）；它没有批次概念，会把池里无关任务一起等；进入 `TERMINATED` 需要「队列空 + 线程数 0」，如果任务里又在往同一个池提交任务，可能永远等不到终止。
3. **`CompletionService` 和 `CompletableFuture` 都支持「先完成先处理」，怎么选？**——`CompletionService` 是**拉模式**：调用方主动 `take()`，天然适合「有界队列 + 边跑边消费」，背压清晰；`CompletableFuture` 是**推模式**：完成时触发回调，适合编排（A 完成后触发 B），但回调执行在哪个线程、异常怎么传播都要想清楚。**流式消费选前者，链路编排选后者**。
