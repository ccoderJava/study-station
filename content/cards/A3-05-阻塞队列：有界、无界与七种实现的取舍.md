## 30 秒简述

「有界」和「无界」的差别不是「有没有上限」，而是**上限会不会被撞到**。

严格说 Java 里**没有真正的无界队列**——所有"无界"实现内部都有一个 `Integer.MAX_VALUE` 的容量字段。它叫无界，是因为**实践中永远撞不到这个上限**，于是 `put()` 永不阻塞。

由此推出两个致命推论：

1. **`put()` 永不阻塞 = 生产者永远不会被反压** → 消费不过来时，队列无限膨胀 → **OOM**。
2. **队列永不满 = 线程池永远不会创建超过核心线程数的线程** → `maximumPoolSize` 形同虚设。

所以工程上唯一的正确姿势是：**有界队列 + 明确的拒绝策略 + 队列积压监控**。`Executors` 工厂方法给的无界队列，就是给别人踩的坑。

## 是什么

### 一、`BlockingQueue` 的四组方法

这是理解阻塞队列的起点。同一件事有四种语义，**区别在「队列满/空时怎么办」**：

| 操作 | 抛异常 | 返回特殊值 | **阻塞** | 超时 |
|---|---|---|---|---|
| 插入 | `add(e)` | `offer(e)` → false | **`put(e)`** | `offer(e, t, u)` |
| 移除 | `remove()` | `poll()` → null | **`take()`** | `poll(t, u)` |
| 检查 | `element()` | `peek()` → null | — | — |

- `add` 满了抛 `IllegalStateException`，`remove` 空了抛 `NoSuchElementException`。
- `offer/poll` 不阻塞，用返回值告诉你成功与否。
- **`put/take` 才是「阻塞队列」这个名字的由来**：满了就等，空了就等。
- 超时版本是两者的折中：等一会儿，等不到就返回 false/null。

**面试考点**：`put` 和 `offer` 的区别不只是"阻塞与否"，还有**异常语义**——`add` 用异常表达失败，`offer` 用返回值，`put` 用阻塞。

### 二、七种实现

| 实现 | 底层 | 有界？ | 锁 | 特点 |
|---|---|---|---|---|
| `ArrayBlockingQueue` | 数组 + 环形索引 | **必须指定** | 1 把锁 + 2 个 Condition | 内存连续、无节点开销；**必须给容量** |
| `LinkedBlockingQueue` | 单向链表 | **默认 `Integer.MAX_VALUE`** | **2 把锁**（putLock/takeLock） | 吞吐比 Array 高；默认等于无界，**必须显式给容量** |
| `SynchronousQueue` | 无存储 | **容量 0** | CAS / 队列 | 不存元素，直接移交；`CachedThreadPool` 用它 |
| `PriorityBlockingQueue` | 二叉堆 | 无界（`Integer.MAX_VALUE`） | 1 把锁 | 按优先级出队，**不保证 FIFO** |
| `DelayQueue` | 优先队列 + 延迟 | 无界 | 1 把锁 | 到时间才能取；元素须实现 `Delayed` |
| `LinkedTransferQueue` | 链表 | 无界 | CAS | 多了 `transfer()`：**必须被消费才返回** |
| `LinkedBlockingDeque` | 双向链表 | 可选 | 1 把锁 + 2 个 Condition | 两端都可进出，适合工作窃取 |

### 三、有界 vs 无界：把概念说透

#### 什么叫「有界」

```java
// 有界：容量 1000，满了 put 会阻塞
BlockingQueue<Task> q = new ArrayBlockingQueue<>(1000);

// 有界：显式给容量
BlockingQueue<Task> q2 = new LinkedBlockingQueue<>(1000);
```

**有界队列的价值不是「限制数量」，而是「提供反压」**：队列满了，生产者就被阻塞（或收到拒绝），生产速度被迫降到消费速度——**压力沿着调用链往上游传，最终传到用户端或上游系统**。这是分布式系统里最朴素也最有效的保护机制。

#### 什么叫「无界」

```java
BlockingQueue<Task> q = new LinkedBlockingQueue();   // 默认容量 = Integer.MAX_VALUE
```

源码里就是：

```java
public LinkedBlockingQueue() { this(Integer.MAX_VALUE); }
```

**所以「无界」是个善意的谎言**：它有上限，只是这个上限是 21 亿，你撞不到。

由此产生的第一个后果：**`put()` 实际上永不阻塞**。生产者以为自己在做流控，其实什么都没控住。

第二个后果更隐蔽：**内存以「每个节点约 24~40 字节」的速度无上限增长**。按 100 字节/条算，1000 万条积压就是 1GB——直接吃掉整个堆。

#### 为什么无界队列在工程上是危险的

```
消费变慢（下游抖动 / DB 慢 / 线程池被占满）
   ↓
队列积压，put 不阻塞，生产者继续灌
   ↓
堆内存上涨 → 老年代占用高 → Full GC 频繁
   ↓
STW 变长 → 接口 RT 上升 / 健康检查超时 → Pod 被重启
   ↓
重启后积压任务全丢（内存队列不持久化）
```

注意最后一环：**内存队列里的任务在重启后全部丢失，且不会有人知道丢了什么**。这是比 OOM 更严重的问题——OOM 至少会告警。

### 四、两个关键实现细节（面试深水区）

#### 为什么 `ArrayBlockingQueue` 一把锁，`LinkedBlockingQueue` 两把锁？

**`ArrayBlockingQueue`**：数组的头尾索引（`takeIndex` / `putIndex`）和 `count` 是**强耦合**的——`count` 变了两个索引的语义都变，必须一起维护。所以只能一把锁：

```java
final ReentrantLock lock;
private final Condition notEmpty;
private final Condition notFull;
```

一把锁 + **两个 Condition**：生产者等 `notFull`，消费者等 `notEmpty`，靠条件队列区分等待原因，避免误唤醒。

**`LinkedBlockingQueue`**：链表天然两端分离——**头节点只有 take 会改，尾节点只有 put 会改**。所以拆成两把锁：

```java
private final ReentrantLock takeLock = new ReentrantLock();
private final Condition notEmpty = takeLock.newCondition();
private final ReentrantLock putLock = new ReentrantLock();
private final Condition notFull = putLock.newCondition();
private final AtomicInteger count = new AtomicInteger();   // 计数必须原子
```

**这就是它吞吐更高的原因**：生产和消费可以**真正并行**，不再互相阻塞。代价是引入 `AtomicInteger count` 做跨锁计数，以及在 `remove(Object)` 这类需要同时看两端的操作里要**同时拿两把锁**。

面试如果问「为什么 LinkedBlockingQueue 比 ArrayBlockingQueue 快」，答「两把锁 + 原子计数」就对了；再追问「那为什么还要用 ArrayBlockingQueue」，答「数组内存连续、无 Node 对象开销、GC 压力小，且必须给容量反而更安全」。

#### `SynchronousQueue` 为什么容量是 0

它**不存储元素**。`put` 会一直阻塞，直到有另一个线程 `take`——**直接把手上的元素交给对方**，中间不落地。

```java
SynchronousQueue<String> q = new SynchronousQueue<>();
new Thread(() -> q.put("x")).start();      // 阻塞，直到有人 take
new Thread(() -> System.out.println(q.take())).start();  // 拿到 "x"，put 立刻返回
```

**它的意义**：`newCachedThreadPool` 用它当队列——因为没有存储，`offer` 必然失败，于是线程池**立刻创建新线程**去处理。这就是「来一个任务开一个线程（复用空闲的）」的实现方式。同时它也解释了为什么 `CachedThreadPool` 的 `maxPoolSize` 是 `Integer.MAX_VALUE`——**队列不缓冲，只能靠加线程**。

公平模式用 `TransferQueue`（FIFO），非公平用 `TransferStack`（LIFO）。非公平吞吐更高。

#### 其余几个的要点

- **`PriorityBlockingQueue`**：`put` **永不阻塞**（无界），只可能抛 `OutOfMemoryError`。元素要么实现 `Comparable`，要么传 `Comparator`。**它不保证同优先级元素的顺序**。
- **`DelayQueue`**：元素必须实现 `Delayed`（`getDelay()` + `compareTo()`）。`take()` 会等到最早的元素到期才返回。**`put` 不阻塞**（无界）。典型用途：订单超时关闭、延迟重试。
- **`LinkedTransferQueue`**：`transfer()` 比 `put()` 更强——**必须被消费者取走才返回**，没被取走就一直阻塞。适合「一定要送达」的场景。
- **`LinkedBlockingDeque`**：两端都能进出，`ForkJoinPool` 的工作窃取用它（自己从头部拿、别人从尾部偷）。

## 为什么这么设计

**为什么 JDK 给 `Executors` 配的是无界队列**：为了让新手**不会遇到拒绝异常**。`newFixedThreadPool(10)` 如果能拒绝任务，大量示例代码会直接崩，JDK 的设计者选择了"先跑起来"。代价是把问题从「立刻报错」推迟成「运行几小时后 OOM」——**而后者更难排查**。

**为什么有界队列必须配拒绝策略**：有界意味着「一定会满」，满了必须有个说法。默认的 `AbortPolicy` 抛异常最直接，但批量任务更常用 `CallerRunsPolicy`——让**提交任务的线程自己去跑**，形成天然反压：提交线程被占住，自然就提交得慢了。

**为什么 `ArrayBlockingQueue` 强制指定容量**：这是设计者的态度表达——**数组必须预先分配，你要么现在想清楚容量，要么就别用它**。相比之下 `LinkedBlockingQueue` 的无参构造是个历史包袱。

**为什么条件队列要两个**：一个等待集时，`notifyAll` 会把「等不满的生产者」和「等不空的消费者」一起叫醒，被错误唤醒的线程重新检查条件、发现不满足、再睡回去——**每次唤醒都是白白的一次上下文切换**。

## 不用会怎么样

- **`newFixedThreadPool` 直接用于批量任务**：等于 `LinkedBlockingQueue` 无界 + `maximumPoolSize` 无效。对账任务白天堆积，晚上全量涌入，堆内存持续上涨，Full GC 后 Pod 被探活杀掉，**积压的任务全部丢失**。
- **用 `SynchronousQueue` 当普通队列**：`put` 直接阻塞到有人消费，如果消费侧是同一个线程串行执行，**立刻死锁**。
- **`PriorityBlockingQueue` 期望 FIFO**：同优先级的元素顺序不确定，依赖顺序的业务会错乱。
- **`DelayQueue` 里放不可变对象**：`getDelay()` 依赖的过期时间没法更新，只能重新入队。
- **无界队列 + 无监控**：队列长度是**最灵敏的故障前兆指标**，不采集就等于放弃了预警窗口。

## 替代方案

| 场景 | 选择 | 理由 |
|---|---|---|
| 通用任务队列 | `LinkedBlockingQueue(容量)` | 吞吐好，显式容量即有界 |
| 内存敏感、容量固定 | `ArrayBlockingQueue(容量)` | 无节点开销，GC 友好 |
| 任务必须立刻被处理 | `SynchronousQueue` | 不缓冲，直接移交 |
| 有优先级 | `PriorityBlockingQueue` | 堆排序 |
| 延迟/超时任务 | `DelayQueue` | 到期才能取 |
| 工作窃取 | `LinkedBlockingDeque` | 双端操作 |
| 跨进程、需持久化 | Kafka / RocketMQ | 内存队列重启即丢，跨进程必须走 MQ |

## 项目中如何使用

- **某银行对账批量**：最早用 `Executors.newFixedThreadPool(8)`，无界队列。白天零星对账、夜间全量任务叠加，队列积压到几十万条，堆内存直线上涨，触发 Full GC 后健康检查超时，Pod 被反复重启。**改成 `new ThreadPoolExecutor(8, 16, 60s, new LinkedBlockingQueue<>(2000), new CallerRunsPolicy())` 后问题消失**——队列满时调度线程自己跑，反压直接传导到上游的定时调度器，它自然会延迟下一批。同时加了 `getQueue().size()` 的监控打点。
- **某支付公司渠道通知重试**：用 `DelayQueue` 实现分级重试（1min / 5min / 30min / 2h），元素是「通知任务 + 下次执行时间」。为什么不用 MQ 的延迟消息：渠道通知量级不大（日均几万），延迟精度要求到秒级，本地 `DelayQueue` 足够，且省了一次网络往返。**但它无界**，所以另加了一个 `AtomicInteger` 计数器，超过阈值就拒绝入队并落库，靠定时任务兜底扫描。
- **某跨境电商回调削峰**：第三方回调的瞬时并发很高，但处理逻辑要调内部接口。用 `ArrayBlockingQueue(5000)` + `CallerRunsPolicy`——**满的时候让 Tomcat 的工作线程自己去处理**，直接降低回调接收速率，第三方平台看到 RT 上升会自动退避。这比返回 500 让第三方重试更平滑。
- **一次教训**：曾以为 `LinkedBlockingQueue(1000)` 就安全了，但忘了**同一个队列被两个业务共用**——回放任务把队列占满，正常的对账任务全被拒绝。之后规约：**不同业务必须用独立线程池 + 独立队列**，队列名要有业务前缀，方便监控区分。

## 常见陷阱

- **说「LinkedBlockingQueue 是无界队列」就完了**——它有 `Integer.MAX_VALUE` 的容量，准确说法是「默认容量接近无界，实践中不会满」。
- **认为无界队列 `put` 不会阻塞**——这个结论对，但要知道**前提是内存够**。内存不足时不会阻塞，而是抛 `OutOfMemoryError`。
- **`newFixedThreadPool` / `newSingleThreadExecutor` 直接用**——两者都是无界队列，`maximumPoolSize` 无效。这是 `Executors` 最常被诟病的点。
- **以为 `ArrayBlockingQueue` 也是一把锁睡着生产和消费**——它确实是**一把锁**，但配了**两个 Condition**，所以不会误唤醒。
- **`take()` 没处理 `InterruptedException`**——中断后直接 `catch` 吞掉，线程池关闭时任务静默丢失。
- **用 `size()` 做精确判断**——并发下 `size()` 是瞬时值，判断完就变了。要「队列是否为空」用 `isEmpty()` 也不能保证后续 `poll` 拿到东西。
- **把阻塞队列当消息队列用**——进程重启数据全丢、无法多实例消费、无重试与死信。**内存队列只适合单进程内解耦**。

## 三层追问

1. **为什么 `LinkedBlockingQueue` 能用两把锁而 `ArrayBlockingQueue` 不行？**——因为数组的 `takeIndex` 和 `putIndex` 共享同一个 `count`：生产者加元素要 `count++`，消费者减元素要 `count--`，两者必须和索引一起原子更新，拆不开。链表的两端在物理上就是分离的（头节点 vs 尾节点），可以用 `AtomicInteger` 单独维护计数。
2. **无界队列一定不能用吗？**——不是。如果**生产者速率天然受控**（比如由外部限流器保证 QPS，或者生产者本身就是单线程定时任务），无界队列不会积压到危险程度。但即便如此也要**加长度监控**——「理论上不会满」和「实际不会满」是两回事。
3. **`CallerRunsPolicy` 有什么副作用？**——它让**提交任务的线程**执行任务。如果提交方是 Tomcat 工作线程，意味着这个 HTTP 请求的 RT 会包含任务执行时间，可能拖长响应甚至超时；如果提交方是定时调度线程，整个调度会被阻塞。所以它适合「宁可慢也不要丢」的场景，不适合「请求必须快速返回」的在线接口——后者更适合 `AbortPolicy` + 上层快速失败。
