## 30 秒简述

索引失效不是索引坏了，而是「能用上索引」的**三个前提**被破坏了一个：**有序性**（列被函数、运算、隐式类型转换包住，索引排序就废了）、**最左前缀**（跳过前导列，范围列之后的列只能过滤不能定位）、**成本**（优化器算完发现回表比全表扫还贵，主动放弃）。所以判断失效不能背口诀，只能看 `EXPLAIN` 的 `type / key / key_len / rows / filtered / Extra`。优化的顺序也是固定的：**先确认是不是 SQL 的问题 → 再改 SQL 形态 → 再调索引（补列、调列序、做覆盖、清冗余）→ 再动表结构（冗余列、汇总表、冷热分离）→ 最后才是架构（读写分离、ES、分库分表）**。越靠后成本越高、越难回滚，能停在前一步就不要往后走。

## 是什么

### 一、三个前提：一条 SQL 用上索引要过三关

![索引失效的三道关：有序性、最左前缀、成本；任何一关过不去，优化器就退回全表扫描](img/index-fail-check.svg)

- **第一关「有序性能用」**：B+ 树能二分，前提是「按列的值排序」。只要比较的对象不是列本身，排序就失效。
- **第二关「前缀能对齐」**：联合索引是字典序，必须从最左列开始连续匹配；中间断一节，后面的列只能做过滤（ICP），不能再缩小扫描区间。
- **第三关「成本划得来」**：前两关都过了，优化器还要算账——走索引要读索引页 + 回表 N 次，全表扫是顺序读。算下来不划算，它会主动选择全表扫。
- 三关的意义在于：**失效不是二进制状态，而是「用到了哪几列、扫了多少行、回了多少次表」的程度问题**。所以「这个查询索引失效了吗」本身是个不精确的问法，应该问「它用了几列、扫多少行」。

### 二、第一关：破坏有序性的写法

| 写法 | 为什么废 | 改法 |
|---|---|---|
| `where date(create_time) = '2026-11-03'` | 每行都要算一次函数，列值本身没参与比较 | 改成 `>= '2026-11-03 00:00:00' and < '2026-11-04 00:00:00'` |
| `where amount + 0 = 100`、`where id * 2 = 100` | 同上，表达式结果不保序 | 把运算移到等号右边 |
| `where order_no = 123456`（列是 varchar） | **字符串列被转成数字比较**，列值变了 | 加引号，参数用 String 传 |
| `where create_time = 1699000000`（列是 datetime） | 同上，隐式转换 | 用标准时间字面量 |
| `where name like '%张'`、`like '%张%'` | 前面的字符不定，无法二分定位 | 前缀匹配 `'张%'`；真要后缀匹配用反向列或 ES |
| `where a = 1 or b = 2`（b 无索引） | 一个分支用不上索引，整体退化成全表扫 | `union all` 拆成两条 |
| join 两表字符集/排序规则不一致 | 联表时做隐式转换 | 统一 `utf8mb4` + 同一 collation |

**隐式转换的方向不对称，这点必须说清**：`varchar 列 = 数字` 是**把列转成数字**，索引直接废；`int 列 = 字符串` 是**把字符串转成数字**，列值没动，索引还能用。所以「单号传成数字」是事故，「金额列传成字符串」通常没事。

### 三、第二关：最左前缀断裂

索引 `(a, b, c)`：

| 写法 | 用到哪几列 | 说明 |
|---|---|---|
| `a=? and b=? and c=?` | 三列全部定位 | 最优 |
| `a=? and b=?` | 两列定位 | 正常 |
| `a=? and c=?` | a 定位，c 走 ICP 过滤 | **不算失效**，只是 c 没帮上定位 |
| `a=? and b>? and c=?` | a、b 定位，c 走 ICP | 范围列截断后面 |
| `b=?` 或 `c=?` | 用不上 | 真正的失效 |
| `a=? order by c` | a 定位，排序要 filesort | 排序列必须紧跟在等值列之后 |
| `a=? order by b desc, c asc` | 8.0 前无法用索引排序 | 8.0 支持降序索引，但要建 `(a, b desc, c asc)` |

- **范围列是分水岭**：范围条件之后的列，在索引里只是「同一个前缀值内有序」，无法再做一次全局二分，所以只能过滤不能定位。
- **`order by` 的规则**：前面的列全是等值条件，排序才可能用上索引；一旦出现范围，后面就断了。
- **8.0.13 的 skip scan** 能在 `a` 基数很低时绕过前导列，但它有前提（不能有范围、a 的 distinct 值很少），**不能当成通用解法**。

### 四、第三关：优化器主动放弃

前两关都过了还是全表扫，通常是这几种：

- **选择性太低**：`status` 只有 5 个值，索引扫 30% 的行再回表，不如顺序读全表。判断指标是 `count(distinct col) / count(*)`，一般认为低于 10% 不适合单独建索引。
- **回表比例高**：命中行数超过表的 20%~30%，优化器的成本模型会选全表扫。这是「明明有索引却不用」最常见的原因。
- **统计信息过期**：大批量导入、大事务提交后，`innodb_stats_persistent` 里的基数还是旧的，估算失真。跑一次 `analyze table` 往往就好了。
- **索引太多选错**：单表十几个索引时，优化器在多个候选间估算出错概率上升。临时可以用 `force index` 验证，长期解法是删冗余索引。
- **`or` 走了 index merge 反而更慢**：`Using union` 看起来用上了索引，实际是两个索引各扫一遍再合并去重，不如改写。

**判断是不是第三关，看 `rows` 和 `filtered`**：`rows` 很大、`filtered` 很低，说明扫了很多行才筛出一点，优化器选全表扫是合理的——问题在数据分布，不在索引。

### 五、`key_len`：判断「用了几列」的硬办法

`EXPLAIN` 的 `key_len` 是索引里用到的字节数，能反推用了几列：

| 类型 | 占字节 |
|---|---|
| `tinyint` / `smallint` / `int` / `bigint` | 1 / 2 / 4 / 8 |
| `date` / `datetime` / `timestamp` | 3 / 5 / 4 |
| `char(n)` utf8mb4 | n × 4 |
| `varchar(n)` utf8mb4 | n × 4 + 2 |
| 可空列（NULL） | 再 +1 |

例：`(merchant_no varchar(32) not null, biz_date date not null, status tinyint not null)`
只用第一列 = 32×4+2 = **130**；加上 biz_date = **133**；再加 status = **134**。
**看到 `key_len` 只到 130，就知道第二列断了**——这比猜「是不是最左前缀问题」可靠得多。注意：`key_len` 只统计**用于定位**的列，ICP 过滤的列不计入。

### 六、优化顺序：从零成本到高成本，逐级升级

![慢 SQL 的治理顺序：改 SQL 形态 → 调索引 → 改表结构 → 改架构，越往后成本越高、回滚越难](img/sql-optimize-order.svg)

**第 0 级：先确认是不是 SQL 的问题。** 锁等待（`innodb_trx`）、主从延迟、返回数据量太大（网络传输）、应用侧序列化慢，都会表现成「SQL 慢」。这一步不做，后面全是瞎改。

**第 1 级：改 SQL 形态（零成本，首选）**

- 去掉列上的函数与运算，改成范围条件。
- `or` 拆 `union all`；`in` 列表过大改临时表或 join。
- 深分页 `limit 100000, 20` 改游标分页（`where id > last_id`）或延迟关联（先用覆盖索引取主键再回表）。
- `select *` 改成只取需要的列，为覆盖索引创造条件。
- 大查询拆批：一次查 10 万个 id 改成 200 个一批。

**第 2 级：调索引（有写入代价，但要评估）**

- 补列：把高频过滤列补进联合索引。
- 调列序：等值在前、范围在后、排序列跟着等值列。
- 做覆盖：把列表页需要的列补进索引，消掉回表。
- 清冗余：`(a)` 和 `(a, b)` 同时存在时，前者是冗余的（`sys.schema_redundant_indexes` 能查）。
- 控制总量：单表 5 个索引以内，写多读少的表更要克制。

**第 3 级：改表结构（要 DDL、要迁移）**

- 冗余字段：把频繁 join 才拿得到的名字、状态冗余过来。
- 汇总表 / 结果表：报表类查询预计算，用定时任务或 binlog 同步。
- 分区：按时间分区，让范围查询能分区裁剪。
- 冷热分离：热表只留 3 个月，历史归档，查询按时间路由。

**第 4 级：改架构（成本最高，最后考虑）**

- 读写分离：读多写少，但资金类强一致读必须回主库。
- 加缓存：热点查询，注意一致性。
- 换存储：多条件组合查询、全文检索上 ES；海量聚合上 ClickHouse。
- 分库分表：单表超过 5000 万且持续增长，接受跨片查询和分布式事务的复杂度。

**升级的判断信号**：第 1 级做完 `rows` 还是几十万 → 进第 2 级；索引已经 5 个还要加 → 进第 3 级；单表数据量本身超纲（亿级）→ 进第 4 级。**不要因为「加索引最快」就跳过第 1 级**，很多慢 SQL 改个写法就好了，加索引反而留下写放大的债。

### 七、联合索引的列序：五条规则

1. **等值列在前，范围列在后**。范围列一旦出现，后面的列就不能定位了。
2. **排序列紧跟等值列**。`where a=? order by b` → `(a, b)` 能省 filesort。
3. **区分度高的列优先**——但这条**只对范围和排序列成立**。等值列之间顺序无所谓：`(a, b)` 和 `(b, a)` 对 `a=? and b=?` 完全等价，因为两个都是精确定位。这是最容易被背错的一条。
4. **把高频查询的返回列补进来做覆盖**，但要评估宽度：`varchar(500)` 这种列补进去等于毁掉索引。
5. **控制在 3~5 列**。列越多，索引越宽，一页装的条目越少，树越高，写入维护成本越大。

## 为什么这么设计

- **优化器为什么看起来「蠢」**：它的成本模型基于统计信息估算，而统计信息是采样来的（`innodb_stats_persistent_sample_pages` 默认 20 页），基数、数据分布都可能失真；8.0 的直方图能缓解，但仍不是精确值。它算的是 IO 和 CPU，不算你的业务语义。
- **为什么不建议长期 `force index`**：执行计划被硬编码进 SQL，数据分布一变就翻车，而且后人不敢删。它只适合临时验证和救火。
- **为什么索引不是越多越好**：每个二级索引都是一棵独立的 B+ 树，insert 一行要维护 N 棵树；buffer pool 被摊薄，热数据命中率下降；优化器候选变多，选错概率上升。读的收益是线性的，写的代价是叠加的。
- **为什么优化顺序不能反**：改 SQL 是应用层变更，可灰度、可回滚、不影响其他查询；加索引要 DDL、有写入代价、要观察；改表结构和拆分是不可逆的大动作。**先做便宜且可逆的事**，是工程上的通用原则。

## 不用会怎么样

- **隐式转换**：数据量小时完全看不出来，涨到千万级突然全表扫，CPU 打满，而且不报错，只能靠监控发现。
- **函数包裹**：一条按日查询扫 800 万行，对账任务从 10 分钟变成 2 小时，第二天出账延迟，上游资金计划全乱。
- **回表过多**：`select *` 命中 20 万行，随机 IO 打满磁盘 IOPS，**同实例其他库一起变慢**——慢 SQL 的杀伤力从来不止于它自己。
- **索引太多**：单表 15 个索引，TPS 从 3000 掉到 1800，写放大 40%，且优化器开始频繁选错。
- **不分青红皂白加索引**：一条每天跑一次的报表 SQL 加了一个索引，代价是全天 40 万笔交易的写入都变慢——**用写换读之前，先算清读写比**。

## 替代方案

| 手段 | 适用 | 代价 / 风险 |
|---|---|---|
| 改写 SQL | 绝大多数场景，优先做 | 几乎无成本，可灰度可回滚 |
| 补 / 调索引 | 查询模式固定、读多写少 | 写入放大、占空间、DDL 要选低峰 |
| 函数索引（8.0.13+） | 老系统改不动 SQL | 表达式必须完全匹配才命中，索引体积不可控 |
| `force index` | 临时验证、紧急救火 | 数据分布一变就翻车，不能长期留 |
| 冗余字段 / 汇总表 | 报表、跨表聚合 | 一致性靠代码维护，容易写漏 |
| 分区 / 冷热分离 | 时间序列大表 | 跨期查询要路由，历史查询变慢 |
| ES / ClickHouse | 多条件组合、全文、海量聚合 | 同步链路与一致性问题 |
| 分库分表 | 单表 > 5000 万且持续增长 | 跨片查询、分布式事务、运维复杂度陡增 |

## 项目中如何使用

- **某银行账务流水查询**：原来按 `date_format(create_time,'%Y-%m-%d') = ?` 过滤，`type=ALL`、扫 800 万行。改成左闭右开区间后 `type=range`，扫描行数降到 1.2 万，耗时从 6s 到 80ms。**这条 SQL 一个字都没加索引，纯靠第 1 级优化。**
- **某支付公司清结算对账**：对账文件查询页把渠道号传成数字，而列是 `varchar(16)`，隐式转换导致索引失效，且平时数据少没暴露。修复是两端一起：Java 侧用 `String` 接收 + MyBatis `#{}` 预编译，同时加了 DAO 层的类型断言，防止再传错。
- **某跨境电商支付中台**：订单查询索引原为 `(status, merchant_id, gmt_create)`，`status` 只有 6 个值、区分度极低，优化器经常直接不走索引。调整成 `(merchant_id, status, gmt_create)`——商户维度区分度高且必传，`status` 作为等值列跟在后面，`gmt_create` 做范围。同时把列表页的 8 个字段补成覆盖索引，`Extra` 从 `Using where` 变成 `Using index`。
- **治理机制**：上线前 SQL 必须贴 `EXPLAIN` 过审核，`type=ALL` 且表行数过万直接打回；每月跑一次冗余索引检查；MyBatis 插件采集超过 500ms 的语句按 mapper 方法聚合告警。

## 常见陷阱

- **背「不满足最左前缀就失效」**：`(a,b,c)` 下 `where a=? and c=?` 仍然能用 a 定位、c 下推过滤，只是 c 没帮上定位。把「没完全用上」说成「失效」，面试官会立刻追问 `key_len` 是多少。
- **认为 `!=`、`not in`、`is null` 一定不走索引**：三者都能走 range，只是常因选择性差被优化器放弃。`is null` 在 InnoDB 里是可以用索引的（索引里存了 NULL）。
- **认为 `or` 一定失效**：两侧都有索引时可以走 index merge（`Using union`），只是经常不如改写快。
- **认为索引列顺序随便排**：等值列之间确实随便，**范围列和排序列的位置不能随便**。
- **只看 `key` 有值就以为没问题**：还要看 `rows`（扫了多少）、`filtered`（筛出比例）、`Extra`（有没有 filesort / temporary / 回表）。
- 面试官会接着问：**「`EXPLAIN` 显示走了索引，但查询还是慢，可能是什么原因？」** 五个方向：回表次数太多、索引区分度低扫了很多行、排序仍要 filesort、锁等待、返回数据量太大（网络与序列化）。

## 三层追问

1. **为什么隐式转换会让索引失效，而「数字列 = 字符串」不会？**——转换方向不同。`varchar 列 = 数字` 是把**列**转成数字再比，列值变了，索引里的顺序对不上；`int 列 = 字符串` 是把**常量**转成数字，列值没动，索引照常可用。
2. **为什么范围列后面的列不能用于定位？**——B+ 树在 `(a,b,c)` 上是按 a 全局有序、b 只在同一个 a 内有序。`a` 一旦是范围，`b` 就不再是全局有序的，没法做一次二分，只能在这个范围内逐条比较（也就是 ICP）。
3. **优化为什么必须先 SQL 后索引？**——SQL 形态是应用层变更，零成本、可灰度、可回滚，且不影响其他查询；索引变更要走 DDL、有写入代价、需要观察窗口；表结构和架构变更代价更高。顺序的本质是**先做便宜且可逆的事**。
