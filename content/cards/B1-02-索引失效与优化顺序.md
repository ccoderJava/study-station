## 30 秒简述

索引失效，多数时候不是索引坏了，是一条 SQL 没满足用上索引的条件，掉进了三种情况。

一是比较的东西不是列本身。列上套了函数、做了运算、被隐式转了类型，排序就废了，二分无从谈起。

二是联合索引没从最左列连续匹配。中间断一节，后面的列只能过滤不能定位；范围列后面那一截，同样是断的。

三是优化器算完账，觉得回表比全表扫还贵，主动放弃。

所以「这个查询索引失效了吗」问得不准。该问的是用了几列、扫了多少行、回了几次表，这些只能从 `EXPLAIN` 里读。

优化也别一上来加索引。先确认是不是 SQL 的问题，再改写法，再动索引，然后才是表结构和架构。越往后越贵，也越难回滚。

## 是什么

一条 SQL 要用上索引，得同时过三关。

![索引失效的三道关：有序性、最左前缀、成本；任何一关过不去，优化器就退回全表扫描](img/index-fail-check.svg)

第一关是有序性能不能用。B+ 树能二分，前提是「按列的值排序」。比较的对象一旦不是列本身，排序就没了。

第二关是前缀能不能对齐。联合索引是字典序，必须从最左列开始连续匹配。中间断一节，后面的列还能过滤（ICP），但不能再缩小扫描区间。

第三关是成本划不划得来。前两关都过了，优化器还要算：走索引要读索引页，再回表 N 次；全表扫是顺序读。算下来不划算，它就不走。

三关合起来说明一件事：失效不是开或关，是用到了哪几列、扫了多少行、回了多少次表的程度问题。

第一关怎么破的，看写法：

| 写法 | 为什么废 | 改法 |
|---|---|---|
| `where date(create_time) = '2026-11-03'` | 每行都要算一次函数，列值本身没参与比较 | 改成 `>= '2026-11-03 00:00:00' and < '2026-11-04 00:00:00'` |
| `where amount + 0 = 100`、`where id * 2 = 100` | 同上，表达式结果不保序 | 把运算移到等号右边 |
| `where order_no = 123456`（列是 varchar） | 字符串列被转成数字比较，列值变了 | 加引号，参数用 String 传 |
| `where create_time = 1699000000`（列是 datetime） | 同上，隐式转换 | 用标准时间字面量 |
| `where name like '%张'`、`like '%张%'` | 前面的字符不定，无法二分定位 | 前缀匹配 `'张%'`；真要后缀匹配用反向列或 ES |
| `where a = 1 or b = 2`（b 无索引） | 一个分支用不上索引，整体退化成全表扫 | `union all` 拆成两条 |
| join 两表字符集/排序规则不一致 | 联表时做隐式转换 | 统一 `utf8mb4` + 同一 collation |

隐式转换的方向不对称，这点值得单独记一笔。`varchar 列 = 数字`，转的是列，索引直接废；`int 列 = 字符串`，转的是常量，列值没动，索引照样能用。所以「单号传成数字」是事故，「金额列传成字符串」一般没事。

第二关，拿 `(a, b, c)` 试：

| 写法 | 用到哪几列 | 说明 |
|---|---|---|
| `a=? and b=? and c=?` | 三列全部定位 | 最优 |
| `a=? and b=?` | 两列定位 | 正常 |
| `a=? and c=?` | a 定位，c 走 ICP 过滤 | 不算失效，只是 c 没帮上定位 |
| `a=? and b>? and c=?` | a、b 定位，c 走 ICP | 范围列截断后面 |
| `b=?` 或 `c=?` | 用不上 | 真正的失效 |
| `a=? order by c` | a 定位，排序要 filesort | 排序列必须紧跟在等值列之后 |
| `a=? order by b desc, c asc` | 8.0 前无法用索引排序 | 8.0 支持降序索引，但要建 `(a, b desc, c asc)` |

范围列是分水岭。范围条件之后的列，在索引里只是「同一个前缀值内有序」，没法再做一次全局二分，所以只能过滤。

`order by` 同理。前面的列全是等值条件，排序才可能用上索引；一旦出现范围，后面就断了。

8.0.13 的 skip scan 能在 `a` 基数很低的时候绕过前导列。但它有前提，不能有范围，a 的 distinct 值还得很少。当通用解法用会翻车。

第三关，前两关都过了还是全表扫，通常是这几种：

- 选择性太低。`status` 只有 5 个值，扫 30% 的行再回表，不如顺序读全表。指标是 `count(distinct col) / count(*)`，一般低于 10% 就别单独建索引了。
- 回表比例高。命中行数超过表的 20%~30%，成本模型就会选全表扫。这是「明明有索引却不用」最常见的解释。
- 统计信息过期。大批量导入、大事务提交之后，`innodb_stats_persistent` 里的基数还是旧的，估算失真。跑一次 `analyze table` 往往就好。
- 索引太多选错。单表十几个索引，优化器在候选之间估错的概率会上升。临时用 `force index` 验证，长期解法是删冗余。
- `or` 走了 index merge 反而更慢。`Using union` 看着用上了索引，实际是两个索引各扫一遍再合并去重，不如改写。

判断是不是第三关，看 `rows` 和 `filtered`。`rows` 很大、`filtered` 很低，说明扫了很多行才筛出一点，优化器选全表扫是合理的。问题在数据分布，不在索引。

到底用了几列，`key_len` 能反推。它是索引里用到的字节数：

| 类型 | 占字节 |
|---|---|
| `tinyint` / `smallint` / `int` / `bigint` | 1 / 2 / 4 / 8 |
| `date` / `datetime` / `timestamp` | 3 / 5 / 4 |
| `char(n)` utf8mb4 | n × 4 |
| `varchar(n)` utf8mb4 | n × 4 + 2 |
| 可空列（NULL） | 再 +1 |

举个真能算的。索引 `(merchant_no varchar(32) not null, biz_date date not null, status tinyint not null)`：只用第一列是 32×4+2 = 130；带上 biz_date 是 133；再加 status 是 134。

看到 `key_len` 只到 130，就知道第二列断了。这比猜「是不是最左前缀问题」靠谱得多。要注意 `key_len` 只统计用于定位的列，ICP 过滤的列不算。

那么优化从哪下手。顺序是固定的，从零成本往高成本走。

![慢 SQL 的治理顺序：改 SQL 形态 → 调索引 → 改表结构 → 改架构，越往后成本越高、回滚越难](img/sql-optimize-order.svg)

第 0 级，先确认是不是 SQL 的问题。锁等待（看 `innodb_trx`）、主从延迟、返回数据量太大、应用侧序列化慢，都会表现成「SQL 慢」。这一步不做，后面全是瞎改。

第 1 级，改 SQL 形态。这一级零成本，能改就别往后走。去掉列上的函数和运算，换成范围条件；`or` 拆 `union all`，`in` 列表太大改临时表或 join；深分页 `limit 100000, 20` 改游标（`where id > last_id`）或者延迟关联，先用覆盖索引取主键再回表；`select *` 改成只取需要的列，给覆盖索引创造条件；大查询拆批，一次查 10 万个 id 改成 200 个一批。

第 2 级，调索引。有写入代价，动手前先评估。补列，把高频过滤列补进联合索引；调列序，等值在前、范围在后、排序列跟着等值列；做覆盖，把列表页要的列补进索引消掉回表；清冗余，`(a)` 和 `(a, b)` 同时存在时前者是冗余的（`sys.schema_redundant_indexes` 能查）；控总量，单表 5 个以内，写多读少的表更得克制。

第 3 级，改表结构。要 DDL，要迁移。冗余字段，把频繁 join 才拿得到的名字、状态挪过来；汇总表，报表查询预计算，定时任务或者 binlog 同步；分区，按时间分，让范围查询能裁剪；冷热分离，热表只留 3 个月，历史归档按时间路由。

第 4 级，改架构。最贵，最后考虑。读写分离适合读多写少，但资金类强一致读必须回主库；加缓存救热点查询，注意一致性；换存储，多条件组合查询和全文检索上 ES，海量聚合上 ClickHouse；分库分表，单表过了 5000 万还在涨才考虑，代价是跨片查询和分布式事务。

什么时候升级，看信号，不看心情。第 1 级做完 `rows` 还是几十万，进第 2 级；索引已经 5 个还要加，进第 3 级；单表数据量本身就超纲，亿级了，进第 4 级。别因为「加索引最快」就跳过第 1 级。很多慢 SQL 改个写法就完了，加索引反而留下写放大的债。

最后是联合索引的列序，五条。

1. 等值列在前，范围列在后。范围列一出现，后面的列就不能定位了。
2. 排序列紧跟等值列。`where a=? order by b` 配 `(a, b)`，filesort 就省了。
3. 区分度高的列优先，但这条只对范围和排序列成立。等值列之间顺序无所谓，`(a, b)` 和 `(b, a)` 对 `a=? and b=?` 完全等价，两个都是精确定位。这条最容易背错。
4. 把高频查询的返回列补进来做覆盖，但要算宽度。`varchar(500)` 这种列补进去，等于把索引毁了。
5. 控制在 3~5 列。列越多索引越宽，一页装的条目越少，树越高，写入维护越贵。

## 为什么这么设计

优化器为什么看起来犯蠢。它的成本模型靠统计信息估算，而统计信息是采样来的（`innodb_stats_persistent_sample_pages` 默认 20 页），基数和数据分布都可能失真，8.0 的直方图能缓解，但仍然不是精确值。它算的是 IO 和 CPU，不算你的业务语义。

为什么不建议长期 `force index`。执行计划被硬编码进 SQL，数据分布一变就翻车，而且后人不敢删。它只适合临时验证和救火。

为什么索引不是越多越好。每个二级索引都是一棵独立的 B+ 树，insert 一行要维护 N 棵树；buffer pool 被摊薄，热数据命中率往下掉；优化器候选变多，选错的概率上升。读的收益是线性的，写的代价是叠加的。

为什么顺序不能反。改 SQL 是应用层变更，能灰度、能回滚、不影响别的查询。加索引要 DDL，有写入代价，还得观察。改表结构和拆分是不可逆的大动作。先做便宜且可逆的事，这是工程上的通例。

## 不用会怎么样

隐式转换。数据量小的时候完全看不出来，涨到千万级突然全表扫，CPU 打满，而且不报错，只能靠监控发现。

函数包裹。一条按日查询扫 800 万行，对账任务从 10 分钟变成 2 小时，第二天出账延迟，上游资金计划全乱。

回表过多。`select *` 命中 20 万行，随机 IO 把磁盘 IOPS 打满，同实例其他库一起变慢。慢 SQL 的杀伤力从来不止于它自己。

索引太多。单表 15 个索引，TPS 从 3000 掉到 1800，写放大 40%，优化器开始频繁选错。

不分青红皂白加索引。一条每天跑一次的报表 SQL 加个索引，代价是全天 40 万笔交易的写入都变慢。用写换读之前，先把读写比算清楚。

## 替代方案

| 手段 | 适用 | 代价 / 风险 |
|---|---|---|
| 改写 SQL | 绝大多数场景，优先做 | 几乎无成本，可灰度可回滚 |
| 补 / 调索引 | 查询模式固定、读多写少 | 写入放大、占空间、DDL 要选低峰 |
| 函数索引（8.0.13+） | 老系统改不动 SQL | 表达式必须完全匹配才命中，索引体积不可控 |
| `force index` | 临时验证、紧急救火 | 数据分布一变就翻车，不能长期留 |
| 冗余字段 / 汇总表 | 报表、跨表聚合 | 一致性靠代码维护，容易写漏 |
| 分区 / 冷热分离 | 时间序列大表 | 跨期查询要路由，历史查询变慢 |
| ES / ClickHouse | 多条件组合、全文、海量聚合 | 同步链路与一致性问题 |
| 分库分表 | 单表 > 5000 万且持续增长 | 跨片查询、分布式事务、运维复杂度陡增 |

## 项目中如何使用

某银行的账务流水查询，原来按 `date_format(create_time,'%Y-%m-%d') = ?` 过滤，`type=ALL`，扫 800 万行。改成左闭右开区间之后变成 `type=range`，扫描行数降到 1.2 万，6 秒变 80 毫秒。这条 SQL 一个字没加索引，纯靠第 1 级。

某支付公司的清结算对账，查询页把渠道号传成了数字，列是 `varchar(16)`，隐式转换把索引废了。平时数据少没暴露，量上来才出事。修的时候两头一起动：Java 侧用 `String` 接收加 MyBatis `#{}` 预编译，DAO 层再加类型断言，防止下次又传错。

某跨境电商的支付中台，订单查询索引原来是 `(status, merchant_id, gmt_create)`。`status` 只有 6 个值，区分度太低，优化器经常干脆不走。调成 `(merchant_id, status, gmt_create)`：商户维度区分度高而且必传，`status` 作为等值列跟在后面，`gmt_create` 走范围。顺手把列表页那 8 个字段补成覆盖索引，`Extra` 从 `Using where` 变成 `Using index`。

治理机制也是靠这几步堆出来的。上线前 SQL 必须贴 `EXPLAIN` 过审核，`type=ALL` 且表行数过万直接打回；每月跑一次冗余索引检查；MyBatis 插件采集超过 500ms 的语句，按 mapper 方法聚合告警。

## 常见陷阱

- 背「不满足最左前缀就失效」。`(a,b,c)` 下 `where a=? and c=?` 仍然能用 a 定位、c 下推过滤，只是 c 没帮上定位。把「没完全用上」说成「失效」，下一句就会被问 `key_len` 是多少。
- 认为 `!=`、`not in`、`is null` 一定不走索引。三者都能走 range，只是常因选择性差被放弃。`is null` 在 InnoDB 里是能用索引的，索引里存了 NULL。
- 认为 `or` 一定失效。两侧都有索引时可以走 index merge（`Using union`），只是经常不如改写快。
- 认为索引列顺序随便排。等值列之间确实随便，范围列和排序列的位置不能随便。
- 只看 `key` 有值就以为没事。还得看 `rows` 扫了多少、`filtered` 筛出多少、`Extra` 里有没有 filesort / temporary / 回表。
- 面试官会接着问「`EXPLAIN` 显示走了索引，查询还是慢，为什么」。五个方向：回表次数太多、区分度低扫了很多行、排序仍要 filesort、锁等待、返回数据量太大。

## 三层追问

1. 为什么隐式转换会让索引失效，而「数字列 = 字符串」不会。转换方向不同。`varchar 列 = 数字` 是把列转成数字再比，列值变了，索引里的顺序对不上；`int 列 = 字符串` 是把常量转成数字，列值没动，索引照常可用。
2. 为什么范围列后面的列不能用于定位。B+ 树在 `(a,b,c)` 上是 a 全局有序、b 只在同一个 a 内有序。a 一旦成了范围，b 就不再全局有序，没法做一次二分，只能在这个范围内逐条比较，也就是 ICP。
3. 优化为什么必须先 SQL 后索引。SQL 形态是应用层变更，零成本、可灰度、可回滚，也不影响其他查询；索引变更要走 DDL、有写入代价、需要观察窗口；表结构和架构更贵。顺序的本质是先做便宜且可逆的事。
