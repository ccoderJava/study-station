## 30 秒简述

热点账户不是「大账户」，是**同一行余额记录在短时间内被大量并发写**。它危险的地方不是慢，是两件连锁的事：行锁排队占住连接池，把单账户的慢扩散成全库超时；上游超时重试又没有幂等键，同一笔被入账两次，日终出长款，多付的钱直接冲减权益。解法按**单账户峰值 TPS** 分五档：200 以下只保正确性，200 到 1000 做事务瘦身加按账户串行，1000 以上才谈缓冲合并，1 万以上才拆子账户。绝大多数真实系统停在前两档。性能方案可以换，四条不变量不能换：唯一键幂等、余额与流水同事务、每批借贷守恒、日终对账。

## 是什么

先把「热点」这个词拆开。它不是按余额大小定义的，是按**并发写落在几行上**定义的：一个只有 3000 块的商户户，结算日被 800 TPS 同时更新，它就是热点；一个躺着两亿的备付金户，一天只动三次，它就不是。

![热点账户的故障扩散：一个热点行如何演变成一次资金差错](img/hot-account-spread.svg)

### 三种热点，对策完全不同

| 类型 | 典型对象 | 读写特征 | 能不能合并 |
|---|---|---|---|
| 入账型 | 商户待结算户、分润收款户、代发收款户 | 只 `+`，不判断余额 | 能，最容易 |
| 扣款型 | 平台手续费户、渠道成本户、营销预算池 | 先判断够不够，再 `-` | 不能，合并会掩盖单笔不足 |
| 读热点 | C 端余额展示、商户后台首页 | 高频读同一行 | 能，加缓存即可 |

这个区分是整道题的分水岭。**面试里十个人有八个直接答「缓冲合并」，而缓冲合并只对入账型安全**——扣款型一旦把 100 笔合成一个净额，某笔本来余额不足也被平均数盖过去了，等于自己给自己造了个透支。

### 为什么单账户撑不住

`update account set available = available + ? where id = ?` 走的是主键定位，代价不在找行，在**持锁时间**：一次事务要更新聚簇索引、维护二级索引、写 undo 与 redo、等组提交。这段时间里，同一行的其他请求全部排队。

一个可以直接报出来的估算：**单账户 TPS 上限 ≈ 1000 ÷ 持锁毫秒数**。持锁 1ms 是 1000，持锁 3ms 就只剩 330。

更关键的是**加机器没有用**。写请求只能走主库，同一个账户按账户号分片后永远落在同一个分片上——横向扩容扩的是「不同账户」，扩不了「同一个账户」。所以这条路只有一条：减少对这一行的写次数，或者把这一行拆成几行。

### 账户性质决定你能用哪一档

这是落地时最先要问的一句话，不是所有账户都能随便优化：

| 账户性质 | 典型对象 | 可缓冲 | 可透支 | 上限 |
|---|---|---|---|---|
| 用户资金户 | 商户待结算户、用户余额户 | 可以，但必须可重放 + 可对账 | 不能 | 第 2 档封顶 |
| 自有资金户 | 手续费户、营销预算池、渠道成本户 | 可以放开 | 可以，配额度控制 | 第 4 档 |
| 过渡户 | 挂账户、待清算户、差错池 | 最适合，只增不减 | — | 第 2 档 |

用户资金户对应的是备付金，监管要求账实相符、可审计、可回溯，**余额不能只存在于内存里**。这一条红线决定了：纯内存账本那套玩法，只能用在平台自己的钱上。

## 为什么这么设计

五档方案的本质是三种资源之间换：**实时性、复杂度、扩展性**。每一档都是在拿前两个换第三个，没有白拿的。

![热点账户的五档解法：按单账户峰值 TPS 逐级升级](img/hot-account-tiers.svg)

**第 1 档用「串行」换「锁」**。把同一账户的请求 hash 到固定线程或固定 MQ 分区，让它们在应用层排队，而不是在数据库行锁上排队。区别在于：应用层排队的是一个轻量的任务对象，数据库排队的是一个占着连接和线程栈的会话。前者排 1000 个不心疼，后者排 50 个就把连接池抽干了。代价只是多一个路由函数，表结构一行不改。

**第 2 档用「实时性」换「写次数」**。100 笔聚成 1 次累加，DB 侧 update 从 800 次/秒掉到 8 次/秒。代价是那 100 笔在落库前只存在于内存里，于是必须补三样东西：批次号做幂等、待入账状态做重放、查询口径改成「已落库余额 + 在途增量」。**第三样最容易被漏**——技术上做完了，运营打开后台发现商户余额少了一截，客诉就来了。

**第 3 档用「余额是单一数字」换「线性扩容」**。拆了子账户之后，「够不够」这个问题从一次查询变成一次分布式判断：每个子户都显示够，加起来不够。这就是把库存超卖问题搬到了资金上。所以拆子户必须配套额度预分配或主户汇总，不能裸拆。

**第 4 档用「持久化保证」换「数量级」**。内存账本加异步落库，宕机就可能丢一段。只有可透支、可日终汇总的自有资金才敢这么干。

还有一条隐含的共同点：**五档降低的都是并发度，没有一档降低一致性约束**。真正保证资金不出错的东西在下面四条，跟性能方案是正交的。

## 不用会怎么样

按图里那条链走一遍，从「慢」到「错」只要四步：

1. 结算日凌晨集中入账，单账户排队，`Lock wait timeout exceeded` 开始刷屏，任务失败率 30%。
2. 等锁的会话把连接池占满，**同一个应用里的查询接口也开始超时**。故障从「入账慢」升级成「结算服务整体不可用」，本来只是慢的账户，现在谁也查不了。
3. 上游看到超时自动重试。如果明细表没有业务唯一键，同一笔被入账两次。
4. 日终对账出长款：商户余额多了 100 万，备付金里没有这 100 万。多出来的部分没有对应负债，`资产 − 负债` 直接转负，**冲的是权益**。

第 3 步是最容易在面试里被忽略的一跳：**性能问题的账单，最后往往记在正确性头上**。因为「失败」和「不确定」在上游眼里是一回事，重试是本能。

## 替代方案

按档位横向对比，重点看「成本」和「什么时候才值得」：

| 档 | 手段 | 适用量级 | 具体改什么 | 成本 | 主要风险 |
|---|---|---|---|---|---|
| 0 | 只保正确性 | 单账户 < 200 TPS | 条件更新防超扣、唯一索引幂等、余额与流水同事务 | 零 | 没有，这是底线 |
| 1 | 事务瘦身 + 按账户串行 | 200 ~ 1000 | 事务里只留两条 SQL；RPC 与通知挪到提交后；同账户 hash 到固定线程或 MQ 分区 | 一人周，不改表 | 分区数不够时串行度不够，要按账户数规划 |
| 2 | 缓冲合并 | 1000 ~ 1 万 | 明细纯 insert；按账户聚合后 100ms 刷一次；批次号幂等、待入账可重放 | 一月，改查询口径 | 内存增量丢失；余额可见性下降；财务要认可延迟 |
| 3 | 拆子账户 | 1 万 ~ 10 万 | 逻辑户拆 N 个物理子户，取模路由，余额求和，出金先汇总 | 一季，改账户模型与对账 | 「加起来不够」；子户间调拨与冻结变复杂 |
| 4 | 换账本 | > 10 万 | 内存账本 + 异步落库，或专用记账引擎；DB 只剩持久化与对账 | 半年起 | 丢实时一致性，审计要另做 |

还有几个常被当成「银弹」的方案，单独说清楚它们的位置：

- **Redis + Lua 原子累加**：单 key 也是串行的（Redis 单线程），但内存操作比 InnoDB 快一到两个数量级，单 key 十万级 ops 不稀奇。**但它只能当削峰缓冲，不能当账本**——持久化是异步的，宕机丢数据，且监管不接受余额只存在内存。所以它在图里属于第 2 档的实现手段，不是第 4 档的替代品。
- **消息队列串行消费**：本质是第 1 档的分布式版本，用分区数换串行度。适合已有 MQ 的链路，注意分区数要按账户数规划，否则不同账户挤一个分区。
- **读写分离**：对写热点完全无效，只能救读热点。别拿它答热点账户。

## 项目中如何使用

**某支付公司结算账户**。T+1 上午集中入账，单个头部商户峰值 800 TPS，最初是同步逐笔 update，锁等待告警不断。落的是第 1 档加第 2 档的组合：

- 事务瘦身：把对账文件解析、短信通知、商户后台缓存刷新全部移到事务提交之后，事务里只剩「update 余额 + insert 流水」两条。
- 按商户分桶串行：同一 `merchant_no` hash 到固定消费线程，800 并发变成 800 排队，但对 DB 是串行的。
- 100ms 批量累加：桶内攒够 100ms 或满 200 笔就刷一次，`update balance = balance + delta`。

效果：单商户 update 次数从 800 次/秒降到约 10 次/秒，P99 从 2s 降到 80ms。配套改了三处：`balance_delta` 表按批次号记录增量，实例重启扫「待入账」流水重放；明细表加 `(biz_no, seq)` 唯一索引兜幂等；余额查询接口改成「已落库余额 + 队列在途」，运营后台单独标了一列「在途」。

**某分润平台手续费户**。这是扣款型热点——所有分润都从平台手续费户扣，一天几十万笔全打一行。这里**没有用缓冲合并**，用的是**额度预分配**：按分润任务向主户申请一段额度（号段式，一次领 1000 笔的量），任务内部本地扣减，用完再领。扣减不落同一行，主户只在领额度时被写一次。

代价是两个：一是未用完的额度要回收，回收前这部分钱不能被别处用（相当于预占）；二是日终要把「已发额度 − 实际消耗」对上，否则主户余额虚低。这个方案能用，前提是**手续费户是平台自有资金，允许短暂的不精确**——换成商户待结算户就不能这么做。

**某银行代发**。批次动辄上万笔，同一个付款账户是天然热点。做法是批次内先按收款账户聚合（同一收款人多笔合并成一笔），再用线程池分片。这里有个踩过的坑：**分片键一开始选的是付款账户，结果所有分片都打到同一个付款户上，等于没分**。改成按收款账户分片，付款户的扣减单独走一次汇总，才真正并行起来。

单个支付的关键约束，落库这一层是这样的：

```java
// 条件更新：把「判断够不够」和「扣减」压成一条 SQL，靠行锁保证原子
@Update("update t_account set available = available - #{amt}, frozen = frozen + #{amt} " +
        "where account_no = #{no} and available >= #{amt}")
int freeze(@Param("no") String no, @Param("amt") long amt);
// 返回 0 就代表余额不足，不要先 select 再判断——那是两个时刻

// 幂等靠唯一索引兜底，不靠应用层 if-exists
// insert into t_account_entry(biz_no, seq, ...) 唯一键 (biz_no, seq)
// 冲突 = DuplicateKeyException = 这笔已经记过，直接返回成功
```

批量累加那一层，关键不是合并本身，是**合并前的落库顺序**：

```java
// 先落明细（状态=待入账），再攒批，再刷余额，最后回写状态
// 顺序反了，进程一挂就丢增量且无法重放
for (Entry e : batch) {
    entryMapper.insert(e);              // 纯 insert，不竞争
}
AccountDelta d = aggregate(batch);       // 内存按账户聚合
accountMapper.addBalance(d.acct, d.amt); // 一次 update
entryMapper.markApplied(d.batchNo);      // 回写状态，供重启重放
```

## 常见陷阱

- **一上来就答「上 Redis 缓冲」**。面试官接着问「Redis 挂了这段增量在哪」，答不出就是负分。资金场景里 Redis 只能做削峰，真相必须在库里。
- **把缓冲合并用在扣款型热点上**。这是最隐蔽的错：合并后的净额可能是正的，把某笔余额不足盖过去了，等于系统性地放行透支。
- **合并了却没改查询口径**。运营看到的余额比实际少一截，一线就会报「钱丢了」。技术做对了，体验是错的。
- **限流维度选错**。按接口总 QPS 限流，热点账户照样被打穿；必须按账户维度限，超出的快速失败让上游稍后查。
- **分片键选成付款账户**。代发、批量付款场景的老坑，所有分片打同一行，等于没分片。
- **面试官会追问：「你怎么知道该升到第几档」**。标准答案是三组数，不是感觉：压测出来的单账户上限（含真实事务长度）、峰值时是「一个账户热」还是「全站热」、尖峰持续多久。持续几小时该拆账户，一分钟的尖峰排队削峰就够。
- **面试官还会追问：「余额什么时候对用户可见」**。必须给出量级（百毫秒 / 秒级）和读取口径（余额 + 在途），含糊过去就说明没真正落过地。

## 三层追问

1. **缓冲合并的内存增量丢了怎么办？**——三件事：明细先落库并带「待入账」状态，增量按批次号入库，实例启动时扫待入账批次重放。重放要幂等，靠批次号唯一键。
2. **同一账户既有入账又有出账，能合并吗？**——不能直接合并成净额。正负混合会掩盖单笔余额不足，必须逐笔串行（第 1 档）或按方向分开缓冲（只合并正向，负向逐笔）。
3. **拆了子账户，出金怎么判断余额够不够？**——必须在主户或汇总视图上判断，不能看单个子户。要么额度预分配（先占后扣），要么主户实时汇总（汇总本身又成了读热点，需要缓存加版本号）。
4. **为什么不用 Redis 直接当账本？**——持久化是异步的，宕机丢一段就再也找不回来；而且监管要求账实相符、可审计。Redis 可以是缓冲层，账必须落库，这是用户资金户的红线。
