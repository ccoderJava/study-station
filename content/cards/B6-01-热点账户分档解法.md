## 30 秒简述

热点账户跟账户里有多少钱没关系。看的是同一行余额记录，短时间内被多少并发写。只有三千块的商户户，结算日被八百个请求同时更新，它就是热点；躺着两亿的备付金户一天动三次，没人管它。

麻烦也不在慢。行锁一排队，连接池就被占满，一个账户的慢变成整个服务查不了。上游超时之后是本能的重试，没做幂等的就重复入账，日终长款，多出来的钱没有对应负债，只能冲权益。

按单账户峰值 TPS 分五档。200 以下只保正确性，200 到 1000 做事务瘦身加按账户串行，1000 以上才谈缓冲合并，1 万以上才拆子户。真实系统大多停在前两档。

性能方案随便换，四条不变量一条不能动：唯一键幂等、余额和流水同事务、每批借贷守恒、日终对账。

## 是什么

先把「热点」这个词拆开。它不按余额定义，按并发写落在几行上定义。

![热点账户的故障扩散：一个热点行如何演变成一次资金差错](img/hot-account-spread.svg)

| 类型 | 典型对象 | 读写特征 | 能不能合并 |
|---|---|---|---|
| 入账型 | 商户待结算户、分润收款户、代发收款户 | 只 `+`，不判断余额 | 能，最容易 |
| 扣款型 | 平台手续费户、渠道成本户、营销预算池 | 先判断够不够，再 `-` | 不能，合并会掩盖单笔不足 |
| 读热点 | C 端余额展示、商户后台首页 | 高频读同一行 | 能，加缓存即可 |

这三种混着答，是最常见的翻车点。多数人张口就是「加缓冲」，可缓冲只对纯入账安全。扣款型把一百笔合成一个净额，某笔本来就余额不够，被平均数一盖就过去了，等于自己给自己开了个透支的口子。

那一行为什么扛不住？`update account set available = available + ? where id = ?`，主键定位，找行不慢。慢在持锁的那几毫秒：改聚簇索引、维护二级索引、写 undo 和 redo、等组提交。这几毫秒里，同一行的请求全在排队。

能直接报出来的数：单账户 TPS 大概就是 1000 除以持锁毫秒数。1ms 是 1000，3ms 就剩 330。

加机器也救不了。写只走主库，同一个账户按账户号分片之后永远落在同一片，横向扩容扩的是「不同账户」，扩不了「同一个账户」。剩下的路只有两条：少写这一行，或者把这一行拆成几行。

还有一条比 TPS 更靠前：这账是谁的钱。

| 账户性质 | 典型对象 | 可缓冲 | 可透支 | 上限 |
|---|---|---|---|---|
| 用户资金户 | 商户待结算户、用户余额户 | 可以，但必须可重放 + 可对账 | 不能 | 第 2 档封顶 |
| 自有资金户 | 手续费户、营销预算池、渠道成本户 | 可以放开 | 可以，配额度控制 | 第 4 档 |
| 过渡户 | 挂账户、待清算户、差错池 | 最适合，只增不减 | — | 第 2 档 |

用户资金户背后是备付金，监管要账实相符、可审计、可回溯，余额不能只活在内存里。这条红线一划，纯内存账本那套就只剩平台自己的钱能用。

## 为什么这么设计

五档其实就三种资源互相换：实时性、复杂度、扩展性。每一档都是拿前两个换第三个，没有白拿的。

![热点账户的五档解法：按单账户峰值 TPS 逐级升级](img/hot-account-tiers.svg)

第一档拿串行换锁。同一账户的请求 hash 到固定线程，或者固定 MQ 分区，让它们在应用层排队，而不是去抢数据库的行锁。差别在排的是什么：应用层排的是个轻量任务对象，数据库里排的是占着连接和线程栈的会话。前者排一千个不心疼，后者排五十个连接池就干了。代价是多一个路由函数，表结构一行不改。

第二档拿实时性换写次数。一百笔聚成一次累加，DB 侧 update 从 800 次/秒掉到 8 次/秒。可那 100 笔在落库之前只在内存里，于是得补三样：批次号做幂等、待入账状态做重放、查询口径改成「已落库 + 在途」。第三样最常漏。技术上做完了，运营打开后台发现余额少一截，客诉就来了。

第三档拿「余额是个单一数字」换线性扩容。拆了子户，「够不够」就从一次查询变成分布式判断：每个子户都显示够，加起来不够。库存超卖那套问题，原样搬到资金上。所以拆子户必须配额度预分配或者主户汇总，裸拆就是给自己挖坑。

第四档拿持久化换量级。内存账本加异步落库，宕机可能丢一段。只有能透支、能日终汇总的自有资金敢这么干。

五档降的全是并发度。没有哪一档敢降一致性约束。

## 不用会怎么样

顺着图里那条链走，从慢到错，四步。

1. 结算日凌晨集中入账，单账户排队，`Lock wait timeout exceeded` 刷屏，任务失败率 30%。
2. 等锁的会话把连接池占满，同一个应用里的查询接口跟着超时。故障从「入账慢」升级成「结算服务整体不可用」，本来只是慢的账户，现在谁都查不了。
3. 上游看超时，自动重试。明细表要是没有业务唯一键，同一笔就入了两次。
4. 日终对账长款：商户余额多出 100 万，备付金里没有这 100 万。多出来的没有对应负债，`资产 − 负债` 转负，冲的是权益。

第三步最容易被跳过。性能问题最后往往记在正确性的账上，因为在上游眼里，「失败」和「不确定」是一回事，而重试是本能。

## 替代方案

按档位摆开，重点看成本和「什么时候才值得」：

| 档 | 手段 | 适用量级 | 具体改什么 | 成本 | 主要风险 |
|---|---|---|---|---|---|
| 0 | 只保正确性 | 单账户 < 200 TPS | 条件更新防超扣、唯一索引幂等、余额与流水同事务 | 零 | 没有，这是底线 |
| 1 | 事务瘦身 + 按账户串行 | 200 ~ 1000 | 事务里只留两条 SQL；RPC 与通知挪到提交后；同账户 hash 到固定线程或 MQ 分区 | 一人周，不改表 | 分区数不够时串行度不够，要按账户数规划 |
| 2 | 缓冲合并 | 1000 ~ 1 万 | 明细纯 insert；按账户聚合后 100ms 刷一次；批次号幂等、待入账可重放 | 一月，改查询口径 | 内存增量丢失；余额可见性下降；财务要认可延迟 |
| 3 | 拆子账户 | 1 万 ~ 10 万 | 逻辑户拆 N 个物理子户，取模路由，余额求和，出金先汇总 | 一季，改账户模型与对账 | 「加起来不够」；子户间调拨与冻结变复杂 |
| 4 | 换账本 | > 10 万 | 内存账本 + 异步落库，或专用记账引擎；DB 只剩持久化与对账 | 半年起 | 丢实时一致性，审计要另做 |

三个常被当成银弹的，单独摆一下位置。

Redis 加 Lua 原子累加，单 key 也是串行的（Redis 自己单线程），内存操作比 InnoDB 快一到两个数量级，十万级 ops 不稀奇。但它只能削峰，不能当账本：持久化是异步的，宕机丢一段找不回来，监管也不接受余额只存在内存。它属于第二档的实现手段，不是第四档的替代品。

消息队列串行消费，就是第一档的分布式版本，用分区数换串行度。链路里已经有 MQ 的最省事，但分区数得按账户数规划，不然不同账户挤进一个分区，白分。

读写分离对写热点完全无效，只救读热点。别拿它答这道题。

## 项目中如何使用

某支付公司的结算账户，T+1 上午集中入账，单个头部商户峰值 800 TPS，最初是同步逐笔 update，锁等待告警没停过。落的是第一档加第二档的组合。

事务先瘦身。对账文件解析、短信通知、商户后台缓存刷新，全挪到提交之后，事务里只剩「update 余额」和「insert 流水」两条。

然后按商户分桶串行。同一个 `merchant_no` hash 到固定消费线程，800 并发变成 800 排队，对 DB 来说就是串行。

再攒批。桶内满 100ms 或者满 200 笔就刷一次，`update balance = balance + delta`。

单商户 update 次数从 800 次/秒掉到约 10 次/秒，P99 从 2s 到 80ms。配套动了三处：`balance_delta` 表按批次号记增量，实例重启扫「待入账」流水重放；明细表加 `(biz_no, seq)` 唯一索引兜幂等；余额查询改成「已落库余额 + 队列在途」，运营后台单独标了一列「在途」。

某分润平台的手续费户是另一种。这是扣款型热点，所有分润都从它扣，一天几十万笔全打一行。这里没用缓冲合并，用的是额度预分配：按任务向主户申请一段额度，号段式，一次领一千笔的量，任务内部本地扣，用完再领。扣减不落同一行，主户只在领额度的时候被写一次。

代价两个。没用完的额度要回收，回收之前这部分钱不能被别处用，相当于预占；日终还得把「已发额度 − 实际消耗」对上，对不上主户余额就虚低。这方案能用，前提是手续费户属于平台自有资金，允许短暂不精确。换成商户待结算户就不能这么干。

某银行的代发，批次动辄上万笔，同一个付款账户是天然热点。做法是批次内先按收款账户聚合，同一收款人多笔合成一笔，再拿线程池分片。这里踩过坑：分片键一开始选的付款账户，结果所有分片都打到同一个付款户上，等于没分。改成按收款账户分片，付款户的扣减单独走一次汇总，才真正并行起来。

单个支付的关键约束，落库这一层长这样：

```java
// 条件更新：把「判断够不够」和「扣减」压成一条 SQL，靠行锁保证原子
@Update("update t_account set available = available - #{amt}, frozen = frozen + #{amt} " +
        "where account_no = #{no} and available >= #{amt}")
int freeze(@Param("no") String no, @Param("amt") long amt);
// 返回 0 就代表余额不足，不要先 select 再判断——那是两个时刻

// 幂等靠唯一索引兜底，不靠应用层 if-exists
// insert into t_account_entry(biz_no, seq, ...) 唯一键 (biz_no, seq)
// 冲突 = DuplicateKeyException = 这笔已经记过，直接返回成功
```

批量累加那一层，关键不在合并本身，在落库顺序：

```java
// 先落明细（状态=待入账），再攒批，再刷余额，最后回写状态
// 顺序反了，进程一挂就丢增量且无法重放
for (Entry e : batch) {
    entryMapper.insert(e);              // 纯 insert，不竞争
}
AccountDelta d = aggregate(batch);       // 内存按账户聚合
accountMapper.addBalance(d.acct, d.amt); // 一次 update
entryMapper.markApplied(d.batchNo);      // 回写状态，供重启重放
```

## 常见陷阱

- 一上来就答「上 Redis 缓冲」。追问一句「Redis 挂了这段增量在哪」就卡住。资金场景里 Redis 只能削峰，真相必须在库里。
- 把缓冲合并用在扣款型上。这个错最隐蔽，合并后的净额可能是正的，某笔余额不足就被盖过去了，等于系统性地放行透支。
- 合并了却没改查询口径。运营看到的余额比实际少一截，一线就会报「钱丢了」。技术做对了，体验是错的。
- 限流维度选错。按接口总 QPS 限，热点账户照样被打穿，必须按账户维度限，超出的快速失败让上游稍后查。
- 分片键选成付款账户。代发、批量付款的老坑，所有分片打同一行，等于没分片。
- 面试官大概率追问「你怎么知道该升到第几档」。答案得是三个数，不是感觉：压测出来的单账户上限（含真实事务长度）、峰值时是一个账户热还是全站热、尖峰持续多久。持续几小时的该拆账户，一分钟的尖峰排队削掉就够了。
- 还会追问「余额什么时候对用户可见」。得报得出量级（百毫秒还是秒级）和读取口径（余额加在途），含糊过去就露馅了。

## 三层追问

1. 缓冲合并的内存增量丢了怎么办。三件事：明细先落库带「待入账」状态，增量按批次号入库，实例启动扫待入账批次重放。重放本身要幂等，靠批次号唯一键。
2. 同一账户既有入账又有出账，能合并吗。不能直接合净额，正负混在一起会掩盖单笔余额不足。要么逐笔串行（第一档），要么按方向分开缓冲，只合并正向的。
3. 拆了子户，出金怎么判断够不够。必须在主户或者汇总视图上判断，看单个子户没意义。要么额度预分配，先占后扣；要么主户实时汇总，但汇总本身又成了读热点，得配缓存加版本号。
4. 为什么不用 Redis 直接当账本。持久化异步，宕机丢一段就再也找不回来，监管也要求账实相符、可审计。它可以当缓冲层，账必须落库。这是用户资金户的红线。
