## 30 秒简述

上划和下拨的差别，不在钱往哪边走，在谁往外掏钱。

上划是平台收钱。钱到账才记一笔应付，晚记一点没有风险。下拨反过来，平台是付钱的，钱一出账资产就少了，可商户到底收没收到，得等银行回执。这段空窗里，负债不能减，也不能让这笔钱被再动一次。

所以得先冻住。冻结不是扣钱，是把负债从「可用」挪到「冻结」，总额一分没变。等到账确认，负债才和资产一起减。全程资产等于负债加权益。

少了这一步，同一笔应付会被兑现两次：超时重试再下一单、下拨在途又发起提现、退票了没冲回。多付的那部分没有对应负债，最后冲的是权益。

产品上配了三样：四态余额、带未知态的单据状态机、日终三方对账。缺一个，冻结都兜不住。

## 是什么

「冻结」这个词一直含混，是因为三个层次被混着说了。

| 层次 | 谁维护 | 记什么 | 典型对象 |
|---|---|---|---|
| 实体户 | 银行 | 真实余额，能对外收付 | 平台备付金户、手续费户、商户结算户 |
| 内部户 | 平台系统 | 虚拟余额，是平台对某方的应付 | 商户待结算户、商户可用户、商户冻结户、平台过渡户 |
| 会计科目 | 财务 | 资产负债表科目 | 银行存款、其他应收款、应付账款、主营业务收入 |

内部户上的余额，在会计上是负债，不是资产。平台代收的商户资金存在备付金户里，法律上归商户，账上记「应付账款—商户待结算」。平台只是代持。这笔钱从来不是平台的收入。

`Σ 内部户余额 = 应付账款 = 平台对商户的负债`

叫法各地不一样，方向只有两个。上划是资金往上走：子公司的钱归到集团主户，商户实体户的钱归到平台备付金户，平台在这头是收款的。下拨是往下走：平台把结算款打给商户，集团给子公司拨款，这头平台是付钱的。

协议支付接上清结算，两头正好首尾相接。用户卡代扣进备付金户，内部户记「欠商户 100 万」；到结算日再把这 100 万打到商户卡上，先冻结、再出账、到账后扣减。

这两笔在商户内部户上碰头。① 把负债加 100，② 先冻住、到账再减 100。中间那段「钱已经出去了、商户还没收到」的时间，就是要冻结的全部理由。

顺带说个容易绕晕的地方。不同系统里「内部户」挂的地方不一样，有的挂商户名下（待结算户、可用户），有的挂平台名下（待拨付户、过渡户）。但冻结的永远是付款侧那本账。钱从谁那儿出，就锁谁的可用。收款侧只等入账，不用锁。

![上划和下拨的对称性：收钱一侧只需延迟记账，付钱一侧必须先把负债锁住](img/transfer-updown-freeze.svg)

余额有四个格子：

| 状态 | 含义 | 能否出金 | 典型来源 |
|---|---|---|---|
| 可用 | 可自由支配 | 是 | 代扣入账、结算转入 |
| 冻结 | 已锁定、等待结果 | 否 | 下拨在途、提现审核、风控止付 |
| 在途 | 钱已出账、未确认到账 | 否 | 银行处理中、跨行清算窗口 |
| 待结算 | 已收款、未到结算日 | 否 | T+1 结算前的商户余额 |

`账面余额 = 可用 + 冻结 + 在途 + 待结算`

只有「可用」能发起出金。冻结、在途、待结算，都不是钱没了，是钱在、但这一笔不能动。

下拨走到哪一步，余额和科目就跟着变哪一步：

| 状态 | 内部户变化 | 会计分录 | 失败怎么办 |
|---|---|---|---|
| `INIT` | 受理，不动余额 | 无 | 直接拒绝，不动账 |
| `FROZEN` | 冻结：可用 −100，冻结 +100 | 无（负债总额不变） | 余额不足则拒单 |
| `SENT` | 出账：冻结不变 | 借：其他货币资金—在途 100；贷：银行存款 100 | — |
| `SUCCESS` | 到账：冻结 −100 | 借：应付账款—商户 100；贷：其他货币资金—在途 100 | — |
| `FAILED` | 退票：冻结 −100，可用 +100 | 借：银行存款 100；贷：其他货币资金—在途 100 | 自动解冻，可重发 |
| `UNKNOWN` | 未知：冻结保持不动 | 出账分录照记（钱可能已出） | 定时查证 + 日终对账兜底 |

`UNKNOWN` 那一行最容易漏。调银行超时，既不能置成功也不能置失败，只能落未知态，靠查询接口和日终对账单把状态收敛回来。冻结在这儿最值钱：状态不明的时候，钱还锁着，没人能再动一次。

## 为什么这么设计

确认负债有两个时点可选，义务发生时，或者钱实际收付时。资金业务要可验证，普遍按实际资金流走。于是两个方向的做法正好相反。

收钱这边，钱没到就什么都不记，到了才给商户加余额。晚记一笔应付，平台没有风险，补上就行。

付钱这边，钱一出去资产就少了，可对方收没收到得等回执。这期间负债不能减，人家没收到，债还在；也不能让这笔债被再用一次，那就是重复清偿。

一个延后，一个提前。所有的不对称都从这儿来。

那冻结到底动了什么？账上就是可用减 X、冻结加 X，负债总额一分没变。所以三件事同时成立：平台还欠着这笔钱，审计上依然是应付；商户提不走，可用已经扣了；平台也不能拿去付别人，它不在可用池里。

负债真正减少要到到账确认那一刻，而且必须和资产减少同时发生。冻结干的事，就是把这两个动作拆开，各归各位。

![下拨四个时点的会计恒等式：冻结期间权益一分不动，到账确认时资产和负债同向减少](img/transfer-ledger-identity.svg)

拿个数跑一遍。商户余额 100 万，备付金 120 万，自有资金 20 万。

| 时点 | 资产 | 负债 | 权益 | 说明 |
|---|---|---|---|---|
| 初始 | 120 | 100 | 20 | 备付金 120，欠商户 100 |
| 冻结 | 120 | 100 | 20 | 只是可用转冻结，三项都不动 |
| 出账 | 120 | 100 | 20 | 备付金 20 + 在途 100，资产换形态 |
| 到账 | 20 | 0 | 20 | 资产和负债同时减 100，权益不变 |
| 退票 | 120 | 100 | 20 | 原路回滚 |

跑完五个时点，`资产 − 负债` 一直是 20。权益一次都没被碰过。这就是冻结要护的东西。

那能不能先扣减、退票了再冲回？能，代价不小。商户会先看到余额少一笔，钱还在路上；冲回得多一条补偿链路，补偿自己失败就是账实不符；退票一多，账务来回抖，对账的时候哪笔是原始、哪笔是冲正，说不清。冻结是锁定一次、等一个结果，比先扣后冲少一个中间态。

## 不用会怎么样

不冻结不会当场报错。它会在某个时刻集中爆，而且爆的方式都一样：权益被击穿。

先说超时重试。财务点下拨 100 万，网关超时，页面报错。人以为没成功，再点一次。两笔都成了。

```
资产 120 − 200 = −80    负债 0    权益 −80
```

从 +20 到 −80。多付的 100 万没有对应负债，只能平台自己填。备付金受监管不得挪用，填不上就是资金缺口。

再说在途提现。下拨 100 万已经发出去了，内部户还显示 100 万可用。商户这时候发起提现，两笔都成，结果一样。冻结的作用，就是让第二次请求在余额校验那一步就被拒掉，不用等到日终。

还有退票没冲回。下拨 100 万被银行退回，钱回到备付金，资产 +100；内部户那 100 已经扣了，没冲回。

```
资产 120    负债 0    权益 120
```

看着像多赚了 100 万，实际是账实不符。审计一查，要么调账，要么认账务差错。

最后一条不在账上。客户备付金必须全额存管、不得挪用。多付的缺口如果拿备付金去补，性质就从账务差错变成挪用备付金。那是监管红线，不是内控问题。

## 替代方案

| 方案 | 做法 | 优点 | 风险 / 代价 |
|---|---|---|---|
| 直接扣减 + 退票冲回 | 出账即扣负债，失败再补 | 实现最简单，一个状态位就够 | 余额展示错误、需要冲正链路、对账难解释 |
| 冻结（推荐） | 可用转冻结，到账后扣减 | 任何时刻恒等式成立，可重入 | 多一张冻结明细表，要处理冻结超时 |
| 只记流水、余额实时汇总 | 不维护余额字段，每次按流水求和 | 天然无余额漂移 | 高并发下性能不可接受，必须配缓存 |
| 预授权 / 预占额度 | 先占额度，实际扣款时转正式 | 适合先冻结后分次扣（酒店、加油） | 额度与余额两套模型，复杂度翻倍 |
| 延迟记账（只在上划用） | 钱到账才记负债 | 收款侧最省事 | 不能用于付款侧，会造成负债与资产脱节 |

## 项目中如何使用

某支付公司的清结算平台，协议代扣的钱进备付金户，日终按商户汇总出结算单，T+1 下拨到商户卡上。

余额表拆成 `available / frozen / in_transit` 三列。冻结另有一张 `t_freeze_detail`，记业务单号、账户、金额、冻结时间、释放时间。释放按明细逐笔核销，不做「冻结总额相减」，那样对不上到底是哪一笔。

下拨单的状态机是 `INIT → FROZEN → SENT → SUCCESS / FAILED / UNKNOWN`，每次跃迁带上前置状态做条件更新，`where status = 'FROZEN'`，重复请求直接被影响行数挡掉。

冻结用条件更新，不做「先查余额再改」：

```sql
-- 影响行数为 0 就是可用不足，不需要先 select 再判断
update t_account
   set available = available - #{amt},
       frozen    = frozen + #{amt},
       version   = version + 1
 where account_no = #{acct}
   and available >= #{amt};
```

冻结和单据状态放在同一个事务里，哪一步失败整体回滚：

```java
@Transactional
public void freeze(String bizNo, String acct, long amt) {
    // 1. 幂等：唯一索引兜底，已冻结过直接返回
    Order o = orderMapper.selectForUpdate(bizNo);
    if (o.getStatus() != INIT) return;

    // 2. 条件扣减，余额不足时影响行数为 0
    if (accountMapper.freeze(acct, amt) == 0) {
        throw new BizException("可用余额不足");
    }

    // 3. 冻结明细 + 单据状态，同一事务
    frozenMapper.insert(bizNo, acct, amt);
    orderMapper.casStatus(bizNo, INIT, FROZEN);
}
```

日终核三组。银行对账单对银行存款科目；Σ 内部户余额对应付账款科目；`资产 − 负债` 对权益。第三组是兜底，前两组都平了它还不平，说明有科目串了。

冻结超时怎么办。超过 30 分钟还是 `SENT` 的，自动转 `UNKNOWN` 并发起银行查证。连续三次查证失败转人工，不自动解冻。宁可挂着，不可猜。

某分润平台，分销商的分润余额在内部户，下拨到银行卡同样走冻结。差别在批量，一次几百笔，所以冻结按批次汇总扣、按明细释放，不然几百次行锁排队。

某跨境电商的支付中台，多币种下冻结要带币种维度，`(account_no, currency)` 才是账户唯一键。曾经只按账户号冻结、没区分币种，美元户一冻，把人民币户的可用额度也占住了，当天 7 笔提现被误拒。

## 常见陷阱

- 把冻结说成「扣钱」。这是最典型的错答。冻结不减负债，只减可用。说成扣钱，就解释不了退票为什么能原路回来。
- 觉得上划也要冻结。判据是资金流向，不是业务的名字。平台是收款方就不用冻，往外付钱才要，下拨、提现、退款、代付都算。
- 不提未知态。问「调银行超时了怎么办」，答「置失败重试」就是事故答案。银行可能已经扣了，重试就是重复付款。
- 只说冻结、不说释放。冻结明细得逐笔核销。只维护一个冻结总额，退票时根本不知道该释放哪一笔。
- 面试官接着问「冻结期间这笔钱算谁的」。会计上仍是平台对商户的负债，法律上仍是商户的钱，只是可用性被限制。平台不能拿去付别人，商户也提不走。

## 三层追问

1. 为什么上划不用冻结。上划平台是收款方，钱没到就什么都不记，到了才确认负债，不存在「已经承诺但还没兑现」的债，也就没有重复兑现的风险。付款侧反过来，钱一出去资产就少，负债得等回执才能减，中间只能锁住。
2. 冻结和直接扣减差在哪。冻结改的是负债的内部结构，可用转冻结、总额不变；直接扣减改的是负债总额。前者任何时点都满足 `资产 = 负债 + 权益`，后者退票时要靠冲正把等式补回来，补不回来就是权益虚增或者虚减。
3. 冻结超时了怎么办。不自动解冻。转 `UNKNOWN`，按退避查银行，日终对账兜底。只有查到「银行无此笔」才允许解冻重发，而且必须沿用同一个业务流水号，保证幂等。
4. 怎么保证不会重复下拨。三层。业务单号唯一索引；状态机条件更新，`where status = 'INIT'`；冻结金额本身占住可用余额。前两层防重复提交，第三层防并发下的余额穿透。
5. 内部户余额和备付金余额为什么会对不上。正常情况下 `Σ内部户余额 = 应付账款`，`备付金余额 = 银行存款`，差额是平台自有资金和未达账项。真对不上，一般三类原因：在途未确认、退票未冲回、手工调账没留痕。先看差额是不是等于「在途 + 冻结超时」，再看挂账池。
