## 30 秒简述

上划和下拨的差别不在资金方向，在**谁往外掏钱**。上划是平台收钱，钱到账才记负债，等得起；下拨是平台付钱，钱一出账资产就少了，商户是否收到却要等银行回执，这段时间负债既不能减、也不能被重复动用，只能先冻结。冻结不是扣钱，是**负债的内部结构调整**：可用减、冻结加，负债总额不变，资产等于负债加权益全程成立。少了这一步，同一笔应付会被兑现两次——超时重试再下一单、下拨在途又发起提现、退票后没冲回，多付的部分直接冲减权益。产品上要配齐四态余额、带未知态的单据状态机、日终三方对账，冻结才兜得住。

## 是什么

先把三个层次分开，否则「冻结」这个词会一直含混。

### 三层账户：实体户、内部户、会计科目

| 层次 | 谁维护 | 记什么 | 典型对象 |
|---|---|---|---|
| 实体户 | 银行 | 真实余额，能对外收付 | 平台备付金户、手续费户、商户结算户 |
| 内部户 | 平台系统 | 虚拟余额，是平台对某方的应付 | 商户待结算户、商户可用户、商户冻结户、平台过渡户 |
| 会计科目 | 财务 | 资产负债表科目 | 银行存款、其他应收款、应付账款、主营业务收入 |

**内部户余额在会计上是负债，不是资产。** 平台代收的商户资金放在备付金户里，法律上归商户、会计上记「应付账款—商户待结算」。平台只是代持，这笔钱从来不是平台的收入。

`Σ 内部户余额 = 应付账款 = 平台对商户的负债`

### 上划与下拨：方向相反、会计处理也不对称

不同系统里叫法不一样，本质只有两个方向：

- **上划（归集）**：资金由下往上走。子公司的钱归到集团主户、商户实体户的钱归到平台备付金户、分支机构的钱归到总部。**平台是收款方。**
- **下拨（拨付）**：资金由上往下走。平台把结算款打给商户、集团给子公司拨款、总部给分支机构调头寸。**平台是付款方。**

在「协议支付 + 清结算」的链路里，两者是首尾相接的：

- **① 代扣收款（上划）**：用户银行卡 → 平台备付金户。钱进平台，内部户记「欠商户 100 万」。
- **② 结算出款（下拨）**：平台备付金户 → 商户结算卡。平台把欠的钱还到商户卡上，先冻结、再出账、到账后扣减。

两笔在商户内部户上相遇：① 把负债加 100，② 把负债先冻住、到账后再减 100。中间那段「钱已经出去了、商户还没收到」的时间，就是需要冻结的全部原因。

一个容易含混的点：不同系统里「内部户」的归属不一样——有的挂在商户名下（商户待结算户、可用户），有的挂在平台名下（待拨付户、过渡户）。但冻结的永远是**付款侧**那一本账：钱从谁那里出，就锁谁的可用余额。收款侧只等入账，不需要锁。

![上划和下拨的对称性：收钱一侧只需延迟记账，付钱一侧必须先把负债锁住](img/transfer-updown-freeze.svg)

### 余额四态：冻结是其中一格，不是「扣掉」

| 状态 | 含义 | 能否出金 | 典型来源 |
|---|---|---|---|
| 可用 | 可自由支配 | 是 | 代扣入账、结算转入 |
| 冻结 | 已锁定、等待结果 | 否 | 下拨在途、提现审核、风控止付 |
| 在途 | 钱已出账、未确认到账 | 否 | 银行处理中、跨行清算窗口 |
| 待结算 | 已收款、未到结算日 | 否 | T+1 结算前的商户余额 |

`账面余额 = 可用 + 冻结 + 在途 + 待结算`

四态里只有「可用」能发起出金。冻结、在途、待结算都不是「钱没了」，而是「钱在但这一笔不能动」——这是和「直接扣减」最本质的区别。

### 下拨的六步：每一步都对应一次余额或科目的变化

| 状态 | 内部户变化 | 会计分录 | 失败怎么办 |
|---|---|---|---|
| `INIT` | 受理，不动余额 | 无 | 直接拒绝，不动账 |
| `FROZEN` | 冻结：可用 −100，冻结 +100 | 无（负债总额不变） | 余额不足则拒单 |
| `SENT` | 出账：冻结不变 | 借：其他货币资金—在途 100；贷：银行存款 100 | — |
| `SUCCESS` | 到账：冻结 −100 | 借：应付账款—商户 100；贷：其他货币资金—在途 100 | — |
| `FAILED` | 退票：冻结 −100，可用 +100 | 借：银行存款 100；贷：其他货币资金—在途 100 | 自动解冻，可重发 |
| `UNKNOWN` | 未知：冻结保持不动 | 出账分录照记（钱可能已出） | 定时查证 + 日终对账兜底 |

最后一行 `UNKNOWN` 是最容易被漏掉的一步。调用银行超时，既不能置成功也不能置失败，只能落 UNKNOWN，靠查询接口和日终对账单把状态收敛回来。**冻结在这里的价值最大：状态不明的时候，钱还锁着，不会被人再动一次。**

## 为什么这么设计

### 核心：收款可以晚确认，付款必须早锁定

会计上确认负债有两个可选时点：义务发生时（权责发生制）或资金实际收付时（收付实现制）。资金类业务出于可验证性和谨慎性，普遍按「以实际资金流为准」处理，于是两个方向出现了完全相反的策略：

- **上划（收钱）**：钱没到就什么都不记，钱到了才给商户加余额。晚确认负债，对平台没有任何风险——最多是少记了一笔应付，补记即可。
- **下拨（付钱）**：钱一出去资产就减少，但「商户是否收到」要等银行回执。这段时间负债不能减（对方没收到，债还在），也不能让这笔负债被再动用一次（否则就是重复清偿）。

**一个延后、一个提前，这是全部不对称的根源。**

### 冻结为什么不是「扣钱」：它改的是负债的结构

冻结在账务上的动作是 `可用 −X、冻结 +X`，负债总额一分没变。这意味着：

- 平台仍然欠商户这笔钱（负债没减，审计上依然是应付）
- 商户不能提走它（可用已扣）
- 平台也不能拿它去付别人（不在可用池里）

真正的「负债减少」发生在到账确认那一刻，且必须和「资产减少」同时发生。冻结的作用，就是把这两个动作拆开、各归各位。

![下拨四个时点的会计恒等式：冻结期间权益一分不动，到账确认时资产和负债同向减少](img/transfer-ledger-identity.svg)

四个时点的数字（示例：商户余额 100 万、备付金 120 万、自有资金 20 万）：

| 时点 | 资产 | 负债 | 权益 | 说明 |
|---|---|---|---|---|
| 初始 | 120 | 100 | 20 | 备付金 120，欠商户 100 |
| 冻结 | 120 | 100 | 20 | 只是可用转冻结，三项都不动 |
| 出账 | 120 | 100 | 20 | 备付金 20 + 在途 100，资产换形态 |
| 到账 | 20 | 0 | 20 | 资产和负债同时减 100，权益不变 |
| 退票 | 120 | 100 | 20 | 原路回滚 |

**全程 `资产 − 负债 = 20`，权益一次都没被碰过。** 这就是冻结要保护的东西。

### 为什么不能「先扣减、退票再冲回」

能实现，但代价明显：

- 扣减后商户看到的余额是错的：钱没到卡，账上已经少了
- 退票冲回要额外一条补偿链路，补偿失败就是账实不符
- 频繁退票会让账务反复抖动，对账时说不清哪笔是原始、哪笔是冲正
- 冻结是「一次锁定、二分结果」，比「先扣后冲」少一个中间态

## 不用会怎么样

不冻结不会立刻报错，它会在某个时刻集中爆发，且爆发的形式是**权益被击穿**。

### 路径一：超时重试，同一笔付两次

财务点下拨 100 万，网关超时，页面报错。以为失败，再点一次。两笔都成功。

```
资产 120 − 200 = −80    负债 0    权益 −80
```

从 +20 万到 −80 万。多付的 100 万没有对应的负债，只能由平台自有资金填——备付金受监管不得挪用，实际就是平台自己掏钱，填不上就是资金缺口。

### 路径二：下拨在途，商户同时提现

下拨 100 万已发出，内部户还是 100 万可用。商户此时发起提现 100 万，两笔都成功。结果同上。

**冻结在这里的作用是让第二次请求在余额校验阶段就被拒掉**，而不是等到日终对账才发现。

### 路径三：退票未冲回，权益虚增

下拨 100 万，银行退票，钱回到备付金（资产 +100），但内部户已经扣了 100（负债 −100），没有冲回。

```
资产 120    负债 0    权益 120
```

看起来多赚了 100 万，实际是账实不符。审计一查，要么调账、要么被认定为账务差错。

### 还有一条不是账的问题

客户备付金必须全额存管、不得挪用。多付造成的缺口如果用了备付金的钱去补，性质就从「账务差错」变成「挪用备付金」，是监管红线，不是内控问题。

## 替代方案

| 方案 | 做法 | 优点 | 风险 / 代价 |
|---|---|---|---|
| 直接扣减 + 退票冲回 | 出账即扣负债，失败再补 | 实现最简单，一个状态位就够 | 余额展示错误、需要冲正链路、对账难解释 |
| 冻结（推荐） | 可用转冻结，到账后扣减 | 任何时刻恒等式成立，可重入 | 多一张冻结明细表，要处理冻结超时 |
| 只记流水、余额实时汇总 | 不维护余额字段，每次按流水求和 | 天然无余额漂移 | 高并发下性能不可接受，必须配缓存 |
| 预授权 / 预占额度 | 先占额度，实际扣款时转正式 | 适合先冻结后分次扣（酒店、加油） | 额度与余额两套模型，复杂度翻倍 |
| 延迟记账（只在上划用） | 钱到账才记负债 | 收款侧最省事 | 不能用于付款侧，会造成负债与资产脱节 |

## 项目中如何使用

**某支付公司清结算平台**：协议代扣收款进备付金户，日终按商户汇总生成结算单，T+1 下拨到商户结算卡。

- 余额表拆 `available / frozen / in_transit` 三列，冻结另有一张 `t_freeze_detail`（业务单号、账户、金额、冻结时间、释放时间），释放时按明细逐笔核销，不做「冻结总额相减」——那样对不上是哪一笔。
- 下拨单状态机 `INIT → FROZEN → SENT → SUCCESS / FAILED / UNKNOWN`，每次状态跃迁带上前置状态做条件更新（`where status = 'FROZEN'`），重复请求直接被影响行数挡掉。
- 冻结用条件更新，不做「先查余额再改」：

```sql
-- 影响行数为 0 就是可用不足，不需要先 select 再判断
update t_account
   set available = available - #{amt},
       frozen    = frozen + #{amt},
       version   = version + 1
 where account_no = #{acct}
   and available >= #{amt};
```

- 一次下拨的冻结与单据状态在同一事务里落库，任一步失败整体回滚：

```java
@Transactional
public void freeze(String bizNo, String acct, long amt) {
    // 1. 幂等：唯一索引兜底，已冻结过直接返回
    Order o = orderMapper.selectForUpdate(bizNo);
    if (o.getStatus() != INIT) return;

    // 2. 条件扣减，余额不足时影响行数为 0
    if (accountMapper.freeze(acct, amt) == 0) {
        throw new BizException("可用余额不足");
    }

    // 3. 冻结明细 + 单据状态，同一事务
    frozenMapper.insert(bizNo, acct, amt);
    orderMapper.casStatus(bizNo, INIT, FROZEN);
}
```

- 日终三组核对：银行对账单 vs 银行存款科目、Σ 内部户余额 vs 应付账款科目、`资产 − 负债` vs 权益。第三组是兜底，前两组都平了它还不平，说明有科目串了。
- 冻结超时兜底：超过 30 分钟仍是 SENT 的，自动转 UNKNOWN 并发起银行查证；查证连续失败 3 次转人工，不自动解冻——**宁可挂着，不可猜**。

**某分润平台**：分销商的分润余额在内部户，下拨到银行卡时同样走冻结。这里的差异是批量下拨（一次几百笔），冻结按批次汇总扣、按明细释放，避免几百次行锁排队。

**某跨境电商支付中台**：多币种场景下冻结要带币种维度，`(account_no, currency)` 才是账户唯一键。曾经因为只按账户号冻结、不区分币种，导致美元户冻结把人民币户的可用额度也占了，当天有 7 笔提现被误拒。

## 常见陷阱

- **把冻结说成「扣钱」**：这是最典型的错答。冻结不减少负债，只减少可用；说成扣钱，就解释不了「为什么退票能原路回来」。
- **认为上划也要冻结**：判据是资金流向，不是业务名称。只要平台是收款方，就不需要冻结；只有往外付钱的动作（下拨、提现、退款、代付）才需要。
- **不提未知态**：面试官问「调银行超时了怎么办」，答「置失败重试」就是事故答案——银行可能已经扣款，重试就是重复付款。
- **只说冻结、不说释放**：冻结明细必须逐笔核销，不能只维护一个冻结总额，否则退票时不知道该释放哪一笔。
- **面试官会接着追问**：「冻结期间这笔钱算谁的？」——会计上仍是平台对商户的负债，法律上仍是商户的钱，只是可用性被限制；平台既不能拿它去付别人，商户也不能提走。

## 三层追问

1. **为什么上划不用冻结？**——上划时平台是收款方，钱没到就什么都不记，钱到了才确认负债；不存在「已经承诺但还没兑现」的负债，也就没有重复兑现的风险。付款侧相反：钱一出去资产就减少，负债必须等回执才能减，中间只能锁住。
2. **冻结和直接扣减的本质区别？**——冻结改的是负债的内部结构（可用→冻结，总额不变），直接扣减改的是负债总额。前者在任何时点都满足 `资产 = 负债 + 权益`，后者在退票时要靠冲正把等式补回来，补不回来就是权益虚增或虚减。
3. **冻结超时了怎么办？**——不自动解冻。转 UNKNOWN，按退避查询银行，日终对账兜底；只有查到「银行无此笔」才允许解冻并重发，且必须沿用同一个业务流水号保证幂等。
4. **怎么保证不会重复下拨？**——三层：业务单号唯一索引、状态机条件更新（`where status = 'INIT'`）、冻结金额本身占住可用余额。前两层防重复提交，第三层防并发下的余额穿透。
5. **内部户余额和备付金余额为什么会对不上？**——正常情况下 `Σ内部户余额 = 应付账款`，`备付金余额 = 银行存款`，两者差额是平台自有资金和未达账项。对不上通常是三类原因：在途未确认、退票未冲回、手工调账未留痕。先看差额是不是等于「在途 + 冻结超时」，再看挂账池。
