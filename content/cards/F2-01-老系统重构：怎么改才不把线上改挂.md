## 30 秒简述

重构的最大风险不是「写不出新代码」，而是「新旧交替期间的不一致」。安全路径只有一条：**先建可验证的等价性（流量回放/双写比对）→ 再小流量切（灰度，按机构/租户/用户）→ 每一步都有回切开关 → 数据迁移双向兼容**。四条纪律：**不改业务语义（先等价迁移，后优化）**、**不一次性切全量**、**回切要能在 5 分钟内完成**、**旧系统保留到对账连续 N 天无差异**。反过来最常见的失败是「大爆炸式重写 + 一次性上线」——这类项目十有八九延期或出事。

## 是什么

五种迁移模式，按侵入从小到大：

1. **绞杀者模式（Strangler Fig）**：新功能写在新系统，老功能逐步搬，通过路由层把流量一点点引过去，最终老系统自然死亡。**最推荐**，风险最低。
2. **双写 + 双读比对**：新老系统同时写，读走老的，比对两边结果。用于验证等价性，成本是两倍写入。
3. **流量回放**：录制生产流量（或日志），回放到新系统（影子库，不写真实账务），比对响应与落库结果。**验证覆盖率最高**，是重构的杀手锏。
4. **影子库/影子表**：新系统连影子库，读写都在影子侧，不影响真实数据。用于验证 SQL 和事务逻辑。
5. **蓝绿/灰度切流**：按维度（机构号、租户、用户 ID 哈希）逐步引流，观察指标后放量。**回切只需改路由**。

配套的四件事：
- **数据迁移**：双写过渡期 → 全量迁移 → 增量追平 → 校验（条数、金额、关键字段哈希）→ 切读 → 老库只读保留。
- **兼容性**：新老版本的接口/报文/表结构必须双向兼容（加字段可空、删字段分两次发布）。
- **可观测**：新老版本的同接口错误率、P99、成功率对比，按维度（机构/渠道）拆开看。
- **回切预案**：不是「理论上能回」，是**演练过、有开关、5 分钟能切回去**。

## 为什么这么设计

因为**重构的本质是「在飞行中换发动机」**：业务不能停，数据不能错，用户无感知。这意味着你无法通过「停服迁移」来消除风险，只能把风险**切分成很多个可观测、可回退的小步**。

等价性验证之所以是核心：重构的隐含目标函数是「行为不变」，但没人能靠读代码证明两套系统行为一致——只能靠**回放真实流量、比对真实结果**。这是唯一可信的证据。

## 不用会怎么样

- 大爆炸重写：开发 6 个月，上线当天发现某个边界场景（比如跨行退汇）逻辑不一致，回滚也回不去（数据已经写进新库）。
- 没有等价性验证：测试用例覆盖 200 个，生产真实场景有 20 万个组合，漏掉的那个恰好是资金最大的客户。
- 一次切全量：发现问题是「费率算错 0.01%」，100 万笔已经错完，追回成本极高。
- 没有回切：出问题时只能「往前修」，修的过程中又引入新问题，故障时间从 10 分钟变 2 小时。
- 数据只迁一次：迁移当天的增量没同步，切换后少了 4 小时的数据，靠对账补了三天。

## 替代方案

| 模式 | 风险 | 成本 | 适用 |
|---|---|---|---|
| 绞杀者（逐步搬） | 低 | 中（长期双系统） | 大多数重构，**首选** |
| 大爆炸重写 | 极高 | 低（一次性） | 系统极小或无人使用 |
| 双写 + 比对 | 低 | 高（双倍写） | 资金类，验证期 |
| 流量回放 | 低（不写生产） | 中（要录流量） | 有真实流量可录，**必做** |
| 影子库 | 低 | 中 | 验证 SQL/事务 |
| 蓝绿部署 | 中（资源翻倍） | 高 | 基础设施层变更 |
| 数据库先行（先换库再换应用） | 中 | 中 | 拆分/上云 |

我的实践路径固定是：**流量回放验证 → 影子库比对 → 双写观察 → 按维度灰度 → 全量 → 老系统只读保留 3 个月**。

## 项目中如何使用

- **某银行 C9→C10 重构**（本卡片的主要来源）：
  - **等价性验证**：录了 3 天生产流量（约 40 万笔请求），回放到新系统的影子库，逐笔比对「响应码 + 关键金额字段 + 落库结果」。第一轮回放差异率 6.2%，其中大部分是时间戳/流水号这类无害差异，但**有 37 笔是金额精度差异**（老系统用 double 累加，新系统用 BigDecimal，分位处理不同）。这 37 笔就是重构的真正风险点，如果不做回放，它们会在生产上变成对账差异。
  - **灰度维度**：按机构号灰度（1 家 → 5 家 → 8 家 → 全量），每档观察 24 小时。**没有按用户 ID 随机灰度**——因为机构维度的资金行为更有代表性，且出问题影响面可控。
  - **一次真实回切**：灰度到 8 家时，发现新系统「跨行转账」P99 是老系统的 3 倍。链路追踪定位到新拆出的「渠道适配服务」每次调用都重建连接（连接池配置漏了）。改配置需要发版，于是**先回切**：改一个路由开关，5 分钟切回老系统，第二天修好再灰度。这次回切没有造成任何资金差错，因为双写期间两套系统数据都在。
  - **数据迁移**：双写过渡 2 周 → 全量迁移（分批，每批 50 万）→ 增量追平（binlog 同步）→ 三方校验（条数、金额汇总、关键字段 MD5）→ 切读 → 老库只读保留 90 天。
  - **教训**：老系统里有 12 个「没人知道干什么用」的定时任务，迁移时漏了 2 个，导致某类对账文件少了。**重构前必须做「隐性依赖盘点」**，包括定时任务、触发器、存储过程、外部系统直连。
- **某跨境电商加解密 SDK 2.0**：对外 SDK 的重构比内部系统更麻烦，因为**你无法控制调用方何时升级**。做法是新老 API 并存 + 新 API 内部兼容老报文格式，老 API 打上 `@Deprecated` 但保留 12 个月，用调用量监控决定下线时间（而不是拍脑袋定日期）。
- **一条纪律**：**重构不改业务语义**。C9→C10 期间所有「顺便优化」的需求全部排到重构完成后——两个变量一起变，出了问题分不清是重构引入的还是优化引入的。

## 常见陷阱

- **重构顺便改需求**：最常见的死法。行为变了，等价性验证就失去意义（差异无法归因）。
- **只测正常流程**：重构的风险 90% 在异常分支（超时、重复、退汇、冲正、边界金额）。
- **回切没演练**：以为改个开关就行，真出事发现新库已经写了老库不认识的数据。
- **数据迁移只做一次**：迁移窗口内的增量必须持续同步，直到切读完成。
- **忽视隐性依赖**：定时任务、触发器、存储过程、报表直连、其他系统的「偷偷查库」。**迁移前要用 DB 审计日志反查所有访问来源**。
- **老系统下线太早**：对账连续 30 天无差异再下线，且要保留只读一段时间（监管/审计可能回溯）。
- **灰度维度选错**：按用户 ID 随机灰度，可能把同一个机构的不同用户分到两边，机构级对账直接对不上。**灰度维度要和资金归属维度一致**。

## 三层追问

1. **流量回放怎么做才不会污染生产数据？**——三件事：回放流量打到的库是影子库（或影子表，表名加前缀）；外部渠道调用全部 mock（否则真的会发交易）；时间戳/流水号做规则化处理（否则唯一索引冲突）。**关键是「外部副作用必须全部切断」**。
2. **新老系统差异怎么判断是「无害」还是「有害」？**——先定义比对规则：哪些字段必须一致（金额、状态、账户）、哪些允许不同（时间戳、自增 ID、流水号）。**必须一致的字段出现差异就是有害**，逐笔归因。没有规则化的比对，回放会产出几万条噪音，最后没人看。
3. **怎么说服业务方接受灰度期的不便？**——用数据和预案说话：灰度只影响 X% 用户、回切 5 分钟内完成、每档观察 24 小时有明确放量/回切标准。**业务方反对的往往不是灰度，是「不知道什么时候出问题、出了问题怎么办」**。
