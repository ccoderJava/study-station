## 30 秒版
线程池用 corePoolSize / maximumPoolSize / workQueue / keepAlive / 拒绝策略 五个维度控制资源。**它的提交流程是"核心线程 → 队列 → 非核心线程 → 拒绝"，队列一旦是无界队列，maximumPoolSize 永远不生效**，所以批量任务必须用有界队列 + 明确的拒绝策略（CallerRuns，让提交端反压），并配合自定义线程名、监控和优雅关闭。

## 是什么（核心机制）
- 提交任务：核心线程未满 → 建核心线程；已满 → 入队；队列满 → 建非核心线程（≤ max）；再满 → 拒绝策略。
- 四种拒绝策略：AbortPolicy（抛异常，默认）、CallerRunsPolicy（调用线程执行，天然反压）、DiscardPolicy（静默丢弃，危险）、DiscardOldestPolicy（丢最老的）。
- 关键：`Executors.newFixedThreadPool` 用的是无界 LinkedBlockingQueue，等于 max 无效 + 可能 OOM；`newCachedThreadPool` 的 max 是 Integer.MAX_VALUE，等于可能线程爆炸。**生产不直接用 Executors**。

## 为什么这么设计（权衡）
核心/非核心的二分是为了"平时省资源、峰值能扛"，但只有队列有界时这个设计才成立——JDK 默认给出无界队列，是为了让开发者不遇到拒绝异常，代价是把压力藏成内存增长。所以工程上要主动换成有界队列，把"拒绝"显式暴露出来。

## 不用它会怎样
对账批量任务如果用无界队列：白天任务持续堆积，堆内存上涨 → Full GC 频繁 → 服务响应变慢 → **K8s 探活超时 → Pod 重启**（我在招银云创就处理过一次探活失败重启，根因是队列积压）。

## 替代方案对比
| 方案 | 适用 | 代价 |
|---|---|---|
| 有界队列 + CallerRuns | 批量任务、可反压 | 提交慢，但不会丢任务 |
| 有界队列 + Abort + 上层重试 | 允许失败的异步任务 | 需要重试与补偿机制 |
| 独立线程池按业务隔离 | 多业务混跑（代发/对账/回放） | 需要更多线程资源 |
| 消息队列削峰 | 跨进程、需持久化 | 引入中间件，核心支付链路慎用 |

## 项目里怎么用（陈聪）
- 招银云创对账批量按"银行 + 业务类型"分片提交，线程数按机器核数与 IO 占比定（IO 密集经验值 2N+1，实际还要看银行渠道限流配额）。
- 拒绝策略选 CallerRuns，让调度线程自己跑，形成反压，避免任务丢失；同时打点监控 activeCount / queueSize。
- 回放任务集中在夜间 20:00–06:00，与日间交易错峰，单独线程池隔离，防止回放把生产侧资源吃掉。

## 三层追问
1. 核心线程数怎么定？——按任务类型（CPU 密集 N+1，IO 密集 2N+1）+ 外部依赖配额（银行限流、DB 连接池），不是拍脑袋。
2. 线程池里的任务抛异常了会怎样？——submit 吞掉异常到 Future，execute 会打线程的 UncaughtExceptionHandler，所以要么用 execute 配 Handler，要么统一 try-catch + 告警。
3. 服务重启时正在跑的任务怎么处理？——shutdown() + awaitTermination 优雅关闭，配合任务幂等与状态表，重启后按状态补偿。

## 常见陷阱
- 说"核心线程数设成 CPU 核数"——面试官会追问 IO 等待怎么办。
- 说"用 DiscardPolicy 就行，丢的不重要"——支付/资金场景丢任务等于丢钱。
- 忘记提优雅关闭与监控，显得只背了参数。
