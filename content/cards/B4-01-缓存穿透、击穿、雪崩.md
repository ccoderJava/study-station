## 30 秒简述

三个问题对应三种失效形态：**穿透**（查不存在的数据，缓存不命中直接打库）→ 空值缓存 + 布隆过滤器 + 参数校验；**击穿**（单个热点 key 过期瞬间大量请求打库）→ 逻辑过期 / 互斥重建 / 热点永不过期；**雪崩**（大量 key 同时失效或 Redis 挂掉）→ 过期时间加随机、多级缓存、限流降级、Redis 高可用。

## 是什么

- 穿透：请求的 key 在 DB 也不存在，缓存永远不会写，每次越过缓存。
- 击穿：key 存在但过期，重建期间并发穿透（高并发下多个线程同时回源）。
- 雪崩：大面积 key 同时过期（批量预热同一 TTL）或实例故障，流量瞬间压到 DB。

## 为什么这么设计

缓存本质是"用空间和一致性换性能"，它对不存在的 key 天然无防护，对过期瞬间天然无保护——所以防护手段都是在缓存层加"兜底语义"：空值缓存是拿存储换穿透防护，布隆过滤器是拿内存和误判率换，互斥重建是拿延迟换一致性。

## 不用会怎么样

支付渠道配置缓存击穿 → 一次性几百个请求回源 → 配置库连接被打满 → 支付主链路超时。这类事故在交易高峰期最容易发生。

## 替代方案

| 问题 | 方案 | 代价 |
|---|---|---|
| 穿透 | 空值缓存（TTL 短） | 内存占用、脏数据期 |
| 穿透 | 布隆过滤器 | 有误判、不支持删除 |
| 击穿 | 逻辑过期 + 异步重建 | 短暂脏读 |
| 击穿 | 互斥锁（本地/分布式） | 延迟增加、需防死锁 |
| 雪崩 | TTL 加随机（±10%） | 简单有效 |
| 雪崩 | 多级缓存（Caffeine + Redis） | 一致性复杂 |

## 项目中如何使用

- 渠道与费率配置：本地 Caffeine 一级 + Redis 二级，逻辑过期 + 后台线程重建，保证支付链路读配置不回源。
- 热点账户余额/状态：不缓存"金额"，只缓存配置类只读数据——资金数据缓存带来的一致性风险远大于性能收益。
- 对账结果查询：空结果缓存 60 秒，防止清算人员刷页面打穿到库。

## 常见陷阱

- 三个概念混为一谈——面试官会直接打断纠正。
- 只答方案不讲代价，显得是背的。

## 三层追问

1. 空值缓存怎么防止脏数据长期存在？——短 TTL（30~60s）+ 数据变更时主动删除。
2. 布隆过滤器为什么不能删除元素？——位数组由多个 hash 置位，删除会误伤其他元素；可用计数布隆或换 Set。
3. 逻辑过期和互斥重建怎么选？——允许短暂脏读、强调可用性选逻辑过期；强一致选互斥重建。
