## 30 秒简述

InnoDB 在 RR 下的行锁有三种：**记录锁（Record Lock，锁索引记录）、间隙锁（Gap Lock，锁索引记录间的空隙，只阻插入）、Next-Key Lock（记录 + 前面的间隙，左开右闭）**，组合起来防幻读。间隙锁只在 RR 且走索引时生效，RC 下退化为记录锁。死锁的四要素 MySQL 会自检并在 `show engine innodb status` 的 LATEST DETECTED DEADLOCK 里打印，常规解法是**统一加锁顺序 + 缩短事务 + 命中索引避免锁范围扩大**。

## 是什么

- 加锁对象是索引，不是行——**唯一索引等值命中退化为记录锁；非唯一索引等值命中加 Next-Key + 间隙；范围查询扩大间隙**。
- 无索引的 update → 全表扫描 → 锁所有记录 + 所有间隙，等于表级锁，是线上最危险的操作。
- 死锁处理：InnoDB 自动回滚代价较小的事务，业务侧要能识别 1213 错误并重试（重试必须幂等）。

## 为什么这么设计

间隙锁牺牲并发换取"可重复读 + 防幻读"的语义完整性。业务上很多场景其实能接受 RC（如互联网高并发交易），阿里系普遍把默认隔离级别改为 RC，就是为了减少间隙锁与死锁，代价是必须靠业务或 binlog row 格式处理一致性问题。

## 不用会怎么样

没有间隙锁，RR 下同一事务两次范围查询可能看到新插入的行（幻读），对账统计会出现"总数对不上"的诡异问题。

## 替代方案

| 方案 | 适用 | 说明 |
|---|---|---|
| 唯一索引 + 等值更新 | 账户/单据状态更新 | 锁粒度最小，首选 |
| 乐观锁（version） | 冲突少的更新 | 无锁等待，失败重试 |
| RC 隔离级别 | 高并发交易 | 减少间隙锁，需评估一致性 |
| 分布式锁串行化 | 跨库/跨服务 | 见 Redis 分布式锁 |

## 项目中如何使用

- 批量结算按"账户 ID 排序后顺序更新"，避免两个批次交叉加锁形成环。
- 资金相关 update 全部要求命中唯一索引（业务参考号），杜绝全表扫描式加锁。
- 死锁报错在应用层统一捕获 + 幂等重试（次数上限 + 退避），并打点到监控。

## 常见陷阱

- 说"死锁只要重试就行"——不解决加锁顺序，重试还会死锁。
- 忽略"无索引更新锁全表"这个最常见的生产事故来源。

## 三层追问

1. 为什么唯一索引等值查询不需要间隙锁？——能唯一定位到一条记录，不会插入到"同一值"，无需防幻读。
2. 死锁和锁等待超时的区别？——死锁是循环等待（自动检测回滚），锁等待超时是长时间拿不到锁（默认 50s）。
3. 如何定位是哪两条 SQL 死锁？——看 LATEST DETECTED DEADLOCK 的事务 1/2 的 SQL、持有锁与等待锁。
