## 30 秒简述

线程池干三件事：**复用线程**（省掉创建销毁开销）、**限制上限**（线程数不会失控）、**解耦提交与执行**（能排队、能拒绝、能监控）。

它由七个参数控制：`corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`workQueue`、`threadFactory`、`handler`，加上构造器外的 `allowCoreThreadTimeOut`。提交流程是**核心线程 → 队列 → 非核心线程 → 拒绝**，顺序固定，所以**队列容量决定了 `maximumPoolSize` 有没有意义**：无界队列会让后两道闸门永远不触发。

生产上不用 `Executors` 工厂方法，自建 `ThreadPoolExecutor` + 有界队列 + 明确的拒绝策略 + 业务化线程名 + 四指标监控 + 优雅关闭。

## 是什么

### 一、七个参数，各自管一件事

| 参数 | 管什么 | 生产上怎么定 | 常见错法 |
|---|---|---|---|
| `corePoolSize` | 常驻线程数，默认不回收 | 用「下游配额 ÷ 单任务耗时」反推，不是拍 CPU 核数 | 直接写 `Runtime.availableProcessors()` |
| `maximumPoolSize` | 峰值上限，**只在队列满后生效** | 按「下游能承受的最大并发」定，通常 2~4 倍 core | 设成 `Integer.MAX_VALUE` |
| `keepAliveTime` | 非核心线程空闲多久退出 | 突发型任务 60s 起；配合 `allowCoreThreadTimeOut` 才管核心线程 | 设 1s，导致线程反复创建 |
| `workQueue` | 排队区，决定反压形态 | **必须有界**，容量按「可容忍积压量 × 单任务内存」估算 | `new LinkedBlockingQueue()` 无参 |
| `threadFactory` | 创建线程、命名 | 带业务前缀 + 序号，排查 dump 靠它 | 用默认 `pool-1-thread-3` |
| `handler` | 满了怎么办 | 资金类用 `CallerRunsPolicy`（反压）或自定义（落库补偿） | `DiscardPolicy` 静默丢 |
| `allowCoreThreadTimeOut` | 核心线程是否也超时回收 | 低频池（夜间批处理）开，常驻池不开 | 不知道有这个开关 |

### 二、内部就是「一个数字 + 一个队列 + 一堆 Worker」

```java
public class ThreadPoolExecutor extends AbstractExecutorService {
    // 一个 AtomicInteger 同时存两样东西：高 3 位运行状态，低 29 位线程数
    private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));
    private final BlockingQueue<Runnable> workQueue;
    private final HashSet<Worker> workers = new HashSet<>();
    private volatile int corePoolSize;
    private volatile int maximumPoolSize;
}
```

- **`ctl` 是整张卡最容易被追问的点**：`int` 32 位，高 3 位存 `RUNNING / SHUTDOWN / STOP / TIDYING / TERMINATED` 五个状态，低 29 位存线程数（上限约 5 亿）。一个 CAS 就能同时保证状态和线程数的原子性，不用两把锁。
- **`Worker` 继承 `AQS`**，本身是一把不可重入锁：`lock()` 表示「正在执行任务」，`shutdown()` 时用 `tryLock()` 判断这个 Worker 是不是空闲——空闲才能中断，正在跑的要等它跑完。
- **状态变化**：`shutdown()` → SHUTDOWN（不接新任务，跑完队列）；`shutdownNow()` → STOP（中断所有线程，返回队列里没跑的任务）；两者最后都会走到 TIDYING → TERMINATED。

### 三、提交流程：四道闸门，顺序不能错

![execute 的四道闸门：核心线程、队列、非核心线程、拒绝策略](img/threadpool-submit-flow.svg)

记住两个反直觉的点：

1. **队列满了才会创建非核心线程**，不是「任务多就扩容」。所以 `max` 到底能不能用上，全看队列会不会满。
2. **核心线程默认永不退出**（`allowCoreThreadTimeOut = false`），哪怕它已经空闲了一整天。一个池子只要被撑到过 core，就一直占着这些线程。

### 四、任务进池之后：线程在哪儿等着

提交只是把任务放进队列，真正的执行是所有 Worker 在跑同一个循环：

```java
final void runWorker(Worker w) {
    Runnable task = w.firstTask;
    w.firstTask = null;
    w.unlock();                        // 允许中断
    while (task != null || (task = getTask()) != null) {
        w.lock();                      // 标记「正在执行」，shutdown 时靠 tryLock 判断是否空闲
        try {
            task.run();
        } finally {
            w.unlock();
        }
        task = null;
    }
    processWorkerExit(w, completedAbruptly);
}
```

关键在 `getTask()`——它决定这个线程是「永久阻塞」「超时等待」还是「退出」：

```java
private Runnable getTask() {
    boolean timedOut = false;
    for (;;) {
        int wc = workerCountOf(ctl.get());
        // 线程数超过 core、或者开了 allowCoreThreadTimeOut → 这个线程是「可超时」的
        boolean timed = allowCoreThreadTimeOut || wc > corePoolSize;
        if ((wc > maximumPoolSize || (timed && timedOut)) && (wc > 1 || workQueue.isEmpty())) {
            return null;                         // 返回 null → runWorker 退出 → 线程被回收
        }
        Runnable r = timed ? workQueue.poll(keepAliveTime, TimeUnit.NANOSECONDS)
                           : workQueue.take();
        if (r != null) return r;
        timedOut = true;
    }
}
```

三个连锁结论，正好解释前面几个「反直觉」：

- **核心线程为什么永不退出**：`timed = false` 时走 `workQueue.take()`，队列空就永久阻塞，不存在超时。
- **非核心线程怎么退**：`wc > corePoolSize` 时 `timed = true`，走 `poll(keepAliveTime)`；超时返回 null，`timedOut = true`，下一轮直接返回 null，`runWorker` 退出，线程被回收。
- **`shutdown()` 为什么能唤醒空闲线程**：`interruptIdleWorkers()` 中断阻塞在 `take()` 上的线程，`take()` 抛 `InterruptedException` 被 `getTask` 捕获，循环继续，发现状态是 SHUTDOWN 且队列空 → 返回 null → 线程优雅退出。

**追问常从这里开始**：「核心线程能回收吗？」默认不能，因为 `take()` 不超时；`allowCoreThreadTimeOut(true)` 之后核心线程也走 `poll`，空闲超时才退——但要求 `keepAliveTime > 0`，否则构造/调用时直接抛 `IllegalArgumentException`。

### 五、线程数怎么定：别背 2N+1，去算下游

公式本身没错：

```text
线程数 = CPU 核数 × 目标利用率 × (1 + 等待时间 / 计算时间)
```

CPU 密集：等待≈0 → N+1；IO 密集：等待是计算的数倍 → 2N+1 起。但真实系统里卡住你的通常是**下游配额**：

```text
下游给的 QPS 上限 × 单任务耗时(s) = 需要的并发数   （Little's Law）
```

举例：某渠道通知回调限 200 QPS，单笔处理 50ms → 理论上 `200 × 0.05 = 10` 个线程就够。这时候把线程数开到 64，不会变快，只会让 64 个线程一起堵在同一个下游上，超时率更高。**线程数超过下游承载力，就是把排队从「你的队列」搬到「下游的连接池」。**

所以定的顺序是：先算下游允许的并发 → 再压测验证 → 最后留 30% 余量。公式只是起点。

### 六、生产上的固定动作

**1）不用 `Executors`**，四个工厂方法各有坑：

| 工厂方法 | 坑 |
|---|---|
| `newFixedThreadPool` | 队列是 `LinkedBlockingQueue` 无参 → 无界，`max` 无效，会 OOM |
| `newSingleThreadExecutor` | 同上，单线程 + 无界队列，积压更隐蔽 |
| `newCachedThreadPool` | `max = Integer.MAX_VALUE`，队列是 `SynchronousQueue` → 线程数无上限 |
| `newScheduledThreadPool` | `max` 也是无限，`DelayedWorkQueue` 无界 |

**2）线程要命名**，否则 `jstack` 里全是 `pool-1-thread-7`，只能靠猜：

```java
ThreadFactory named = new ThreadFactory() {
    private final AtomicInteger seq = new AtomicInteger(1);
    public Thread newThread(Runnable r) {
        Thread t = new Thread(r, "dai-fa-batch-" + seq.getAndIncrement());
        t.setDaemon(false);                 // 业务线程不要设 daemon，否则退出期被直接掐掉
        t.setUncaughtExceptionHandler((th, e) ->
            log.error("task crash in {}", th.getName(), e));
        return t;
    }
};
```

**3）有界队列 + 明确拒绝**。资金、对账这类不能丢的任务，用 `CallerRunsPolicy` 让提交线程自己跑，形成反压；能容忍失败的异步任务用 `AbortPolicy` 配合上层重试；要落库补偿的，自定义 handler 记一条待补偿记录。

**4）监控四个数 + 一个拒绝计数**。JDK 没暴露拒绝次数，得自己在 handler 里打点：

```java
public class MonitoredRejectHandler implements RejectedExecutionHandler {
    private final Counter rejected;   // 接监控系统
    public void rejectedExecution(Runnable r, ThreadPoolExecutor p) {
        rejected.increment();
        log.warn("pool={} rejected, active={} queue={}",
                 p, p.getActiveCount(), p.getQueue().size());
        throw new RejectedExecutionException("pool saturated");
    }
}
```

| 指标 | 含义 | 告警阈值 |
|---|---|---|
| `getActiveCount()` | 正在跑的线程数 | 持续 > 80% core 说明该扩容 |
| `getQueue().size()` | 积压量 | > 容量 70% 预警，> 90% 严重 |
| `getCompletedTaskCount()` | 累计完成 | 长时间不涨 = 卡住了 |
| `getLargestPoolSize()` | 历史峰值 | 等于 max 说明撞过上限 |
| 拒绝计数 | 溢出了多少 | 非 0 就该看 |

**5）优雅关闭**，别让进程退出时把跑到一半的任务掐了：

```java
@PreDestroy
public void shutdown() throws InterruptedException {
    pool.shutdown();                                    // 不接新任务，跑完队列
    if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
        pool.shutdownNow();                             // 超时才中断
        log.warn("pool forced shutdown, {} tasks dropped", pool.getQueue().size());
    }
}
```

K8s 上还要配 `preStop: sleep 15`，让 Endpoints 先摘掉、流量停下来，再走关闭流程（退出期的完整时序见「守护线程」那篇）。

**6）上下文传递与隔离**。跨线程的 `ThreadLocal` 会丢（见 ThreadLocal 那篇），线程池要么用 `TaskDecorator` 包装，要么用 TTL。另外**按业务拆池**：代发、对账、回放各一个池，互不抢占——回放是夜间的重活，混在交易池里就是事故。

## 为什么这么设计

**core / max 二分**：平时只养核心线程省资源，峰值再扩。代价是**扩容滞后**——必须等队列满了才扩，而队列满的时候压力已经进来了，所以这个设计对「突发流量」是不友好的，突发场景要把 `core` 直接设高，或者用 `SynchronousQueue`（不排队，直接扩线程，但容易失控）。

**默认无界队列**：JDK 的取舍是「宁可积压，也不让新手遇到 `RejectedExecutionException`」。代价是把资源问题从「明确的拒绝」推迟成「隐性的内存增长」，出问题时更难查——队列积压不会立刻报错，只会在某次 Full GC 后突然探活失败。

**拒绝策略外置**：框架不替你决定「丢了要不要报错」，因为这件事只有业务能判断。代价是默认值（`AbortPolicy`）在很多场景并不合适，必须显式选。

**参数是 final 之外的 volatile**：`corePoolSize` / `maximumPoolSize` 都留了 setter，为动态调参留了口子——但**队列容量没有**，因为 `LinkedBlockingQueue.capacity` 是 `final`。这是动态线程池最大的坑，见「动态线程池」那篇。

## 不用会怎么样

- **每次 `new Thread()`**：8 核机器上开两千个线程，每个线程默认栈 1MB（`-Xss`），光是栈就吃 2GB，直接 `OutOfMemoryError: unable to create new native thread`；同时上下文切换把 CPU 打满，吞吐反而下降。
- **无界队列**：白天任务持续堆积 → 堆内存上涨 → Full GC 频繁 → 服务响应变慢 → **K8s 探活超时 → Pod 重启**。我在某银行就处理过一次探活失败重启，根因是队列积压，重启还把队列里的任务全丢了。
- **共用线程池**：回放任务在交易池里跑，300 个回放分片把 core 占满，真实交易排队 → 交易超时率从 0.1% 涨到 7%，资金侧直接告警。
- **不命名**：`jstack` 看到 200 个 `pool-3-thread-*`，不知道哪个是回放、哪个是交易，排查时间从 5 分钟变 1 小时。

## 替代方案

| 方案 | 适用 | 代价 / 风险 |
|---|---|---|
| 有界队列 + `CallerRuns` | 批量、可反压、不能丢 | 提交线程被拖慢，调度线程可能被业务占住 |
| 有界队列 + `Abort` + 上层重试 | 允许失败、有重试通道的异步任务 | 要有幂等与重试上限，否则重试风暴 |
| 按业务拆多池 | 多业务混跑（代发 / 对账 / 回放） | 线程资源翻倍，要算总账 |
| 消息队列削峰 | 跨进程、需持久化、可延迟 | 引入中间件；核心支付链路引入 MQ 要评估顺序与重复 |
| 虚拟线程（JDK 21） | IO 密集、任务量巨大 | `synchronized` 块里会 pinning，`ThreadLocal` 百万级内存，监控方式全变 |
| **动态线程池** | 参数要随流量调整 | 配置一致性、生效边界，见「动态线程池」那篇 |

## 项目中如何使用

**某银行代发批量**（8 核 16G，core 16 / max 32 / queue 2000 / `CallerRunsPolicy`）：

- 分片维度是「银行 + 业务类型」，一个分片 5000 笔。提交端是调度线程，工作线程按分片拉数据。
- 队列容量 2000 是算出来的：队列里放的是分片任务对象（一个分片元信息约 200KB），2000 × 200KB ≈ 400MB，压在堆内存的 1/8 以内，不至于堆积时先把自己撑爆。
- 拒绝策略选 `CallerRuns`：调度线程自己跑分片，提交速度自然降到处理速度，任务不丢。
- 监控 `activeCount` 与队列水位。去年账期日曾经 core 打满、队列涨到 1500，靠这条告警提前 20 分钟发现，把 core 从 16 调到 32——当时还得走一次发版，**这就是后来做动态线程池的直接原因**。

**某支付公司清结算对账**：夜间 22:00 起跑，单独一个池 `core 8 / max 8 / queue 1000`，因为下游是对账文件系统，并发再高也没用，反而会把 IO 打满。固定 8 线程，稳定跑 40 分钟。

**某跨境电商支付中台的回调处理**：`core 32 / max 64 / queue 5000`，回调是外部驱动的突发流量，白天峰值 QPS 800、单笔 40ms → 并发需求约 32；`max 64` 是留给渠道批量推送的尖峰。拒绝策略是自定义的：记一条补偿记录，由定时任务重试，绝不静默丢。

## 常见陷阱

- **只背七个参数，不说提交流程**。面试官问「`max` 什么时候生效」，答「任务多了就扩容」就露馅了——正确答案是「队列满了之后」。
- **说「核心线程数设成 CPU 核数」**。CPU 密集才这么算，IO 密集要放大；更要命的是没提下游配额这个真实约束。
- **说「用 `DiscardPolicy`，丢的不重要」**。在支付、资金、对账场景，丢任务就是丢钱、账不平。
- **忘记 `shutdown`**。JVM 里非 daemon 线程不退出，代码里 `main` 结束了进程还挂着；Spring 里不关池，滚动发布会直接掐断在跑的任务。
- **用 `submit` 提交却不管异常**。`submit` 把异常吞进 `Future`，不 `get` 就永远看不到；`execute` 才会走 `UncaughtExceptionHandler`。统一做法是任务体内部 `try-catch` 兜底并上报。
- **面试官会接着问**：「线程池里的线程抛了异常，这个线程会死吗？」——不会。`runWorker` 的 `finally` 一定会走 `processWorkerExit`，只要池子还在 RUNNING，就会补一个新 Worker，线程数不变；只有 `shutdown` 之后才会真的少线程。所以「异常导致线程池越跑越少」这个说法是错的。

## 三层追问

1. **是什么**：线程池怎么决定一个任务在哪个线程上跑？
   七个参数 + 四道闸门。`execute` 先看 `workerCount < corePoolSize` 就直接 `addWorker`；否则 `workQueue.offer`；offer 失败再 `addWorker(非核心)`；都失败走 `handler`。
2. **为什么这么设计**：为什么线程数不用一个参数，非要 core 和 max 两个？
   为了「平时省资源 + 峰值能扛」。单参数没法表达「常驻多少」和「最多多少」两层语义。但代价是扩容依赖队列满，所以 JDK 又把队列设计成可插拔的——想激进扩容就给 `SynchronousQueue`，想稳住就给有界队列。
3. **不用会怎么样**：如果所有任务都 `new Thread` 会怎样？
   线程创建要走内核态、分配栈内存，QPS 1000 的系统一天创建上千万线程，CPU 大量耗在创建销毁上；线程数无上限时直接 `unable to create new native thread`。线程池把「线程」变成可复用、可计数的资源，这是它存在的第一性理由。
