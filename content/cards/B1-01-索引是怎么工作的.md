## 30 秒简述

InnoDB 的索引是一棵按索引列排好序的 B+ 树。**表本身就是一棵树**——聚簇索引，叶子节点就是整行数据；其余的二级索引是另外的树，叶子只存「索引列 + 主键」。所以走二级索引要查两棵树：先在二级索引里定位到主键，再拿主键回聚簇索引取整行，这一步叫**回表**，是随机 IO。要查的列全在二级索引里，就不用回表，这是**覆盖索引**；where 里还有索引内的列但用不上定位（典型是范围条件之后的列），可以让引擎在二级索引上先过滤掉不匹配的记录再回表，这是**索引下推**。三个概念其实是同一条查询链上的三个截断点：停在第一棵树是覆盖，第一棵树后先过滤是下推，走到第二棵树是回表。

## 是什么

### 一、索引的本质：给数据定一个顺序

- InnoDB 以**页（16KB）**为单位和磁盘交互，一次 IO 读一页，不是读一行。
- 页内记录按索引列有序排列，页尾有 slot 数组做页目录，页内查找是二分。
- 页之间组成 B+ 树：**非叶子节点只存「键 + 页号」，叶子节点存数据，叶子之间用双向链表串联**。
- 所以「索引」不是一张额外的表，而是**同一批数据按另一个顺序重排的一份目录**；目录里存的东西越少，一页能装的条目越多，树越矮，IO 越少。

一页能放多少，现场可以算：16KB 页，bigint 主键 8 字节 + 页号 6 字节 ≈ 14 字节，非叶子一页约 1170 个键；假设一行 1KB，叶子一页放 16 行。三层树 ≈ 1170 × 1170 × 16 ≈ **2100 万行**，也就是千万级表查一次只要 3 次页访问（根页常驻内存，实际 2 次磁盘 IO）。

### 二、两棵树：聚簇索引与二级索引

| | 聚簇索引（主键索引） | 二级索引（普通索引） |
|---|---|---|
| 叶子存什么 | **整行数据** | **索引列 + 主键值** |
| 一张表有几个 | 有且只有一个 | 想建几个建几个 |
| 顺序由谁定 | 主键（无主键用第一个唯一非空索引，再没有用隐藏 rowid） | 建索引时指定的列 |
| 一次查询要访问几棵树 | 1 棵 | 2 棵（除非覆盖） |
| 范围查询 | 叶子链表顺序扫 | 先扫二级索引，再逐条回表（顺序变成随机） |

一句话记住区别：**聚簇索引的叶子就是表，二级索引的叶子是一张「键 → 主键」的映射表。**

### 三、一条等值查询走过的三段路

以 `select * from t_order where merchant_no = 'M123'` 为例，索引是 `idx_merchant(merchant_no, biz_date)`：

1. **优化器选索引**：估算 `idx_merchant` 的命中行数，如果只占表的百分之几，就选它；占比太高会直接全表扫。
2. **第一棵树定位**：从根页开始二分，找到 `merchant_no='M123'` 对应的叶子页，顺着叶子链表取出所有命中的索引项，每一项拿到一个**主键 id**。
3. **第二棵树回表**：拿 id 去聚簇索引再二分一次，取出整行。**每一条命中记录都要回一次，且这些 id 在聚簇索引里不连续**——这就是回表贵的根本原因。

![一条二级索引查询的三段路：第一棵树定位主键，第二棵树回表取整行；覆盖索引停在第一棵树，索引下推在第一棵树之后先过滤](img/index-query-path.svg)

### 四、回表为什么是随机 IO

- 二级索引按 `merchant_no` 有序，命中的主键是**乱序**的；聚簇索引按主键有序，只有主键相邻的记录才在同一页。
- 于是 N 条命中 ≈ N 次随机页访问（除非页已经在 buffer pool 里）。
- 机械盘上随机 IO 比顺序 IO 慢两个数量级；SSD 上差距小些，但 IOPS 依然是瓶颈。**回表次数是比「有没有走索引」更值得看的指标。**
- 经验值：命中行数超过表的 20%~30%，优化器往往直接放弃索引改全表扫——顺序读整表比「索引扫 + 大量随机回表」便宜。这不是 bug，是成本模型算出来的。

### 五、覆盖索引：在第一棵树就结束

- 定义：**查询需要返回和过滤的所有列，都在使用的索引里**，不需要回表。
- 标志：`EXPLAIN` 的 `Extra` 出现 `Using index`。
- 例：索引 `(merchant_no, biz_date)`，查 `select merchant_no, biz_date from t_order where merchant_no = ?` → 只读一棵树。
- 几个容易记错的点：
  - `select *` 永远不可能是覆盖索引。
  - `count(*)` 走二级索引也算覆盖（只数索引项，不取整行），所以 `count(*)` 比 `count(普通列)` 快，后者要判断非空。
  - 覆盖索引不是「把列加到索引里就完事」——索引变宽，一页装的条目变少，树变高，写入要多维护一份，是拿写换读。

### 六、索引下推（ICP）：两棵树之间加一道过滤

5.6 引入、默认开启（`optimizer_switch` 里的 `index_condition_pushdown`）。它解决的问题是：

- 联合索引 `(name, age)`，SQL 是 `where name like '张%' and age = 25`。
- `name like '张%'` 是范围条件，**`age` 用不上定位**（B+ 树在 age 上只在同一个 name 内有序）。
- 没有 ICP：引擎把所有「张」开头的记录逐条回表，把整行交给 server 层，server 层再判 `age=25`。命中 1000 条只要 20 条 → **1000 次回表，980 次白跑**。
- 有 ICP：`age` 就在索引里，引擎在**二级索引上**顺手把 `age=25` 判掉，只对剩下的 20 条回表。**回表次数从 1000 降到 20。**
- 标志：`Extra` 出现 `Using index condition`。
- 三个必须说清的边界：
  - 它**不减少索引扫描行数**，`name like '张%'` 该扫 1000 条还是 1000 条，减少的只是回表。
  - 条件下推的列必须在**当前使用的索引里**，不要求是最左前缀。
  - 条件里不能有子查询、存储函数；5.6 的分区表不支持，5.7 之后才修好。

![索引下推：同一个 SQL，没有 ICP 时回表 1000 次、980 次白跑；有 ICP 时在二级索引上先过滤，只回表 20 次](img/index-icp.svg)

### 七、联合索引：列的顺序决定了能用哪几列

`(a, b, c)` 的排序规则是**字典序**：先按 a 排，a 相同按 b 排，b 相同按 c 排。由此推出三条实用结论：

- **能定位的列必须从最左开始连续**：`where a=? and b=?` 能用两列；`where b=?` 用不上；`where a=? and c=?` 只有 a 能定位，c 靠 ICP 过滤。
- **一个范围条件会截断后面的定位**：`where a=? and b>? and c=?`，a、b 定位，c 只能 ICP；`where a>? and b=?`，只有 a 定位。
- **排序要用索引，得「前面的列都是等值，排序从下一个列开始」**：`where a=? order by b` 能省掉 filesort；`where a>? order by b` 不行。
- 8.0.13 起有 **skip scan**：`(a, b)` 索引在 `where b=?` 时，如果 a 的基数很低，可以跳跃扫描每个 a 值下的 b。但它依赖基数、不能有范围条件，**不能当成「最左前缀失效了」的通用解法**。

### 八、顺带一个：MRR

`Multi-Range Read` 把「二级索引拿到的乱序主键」先排序，再按主键顺序回表，把随机 IO 变成接近顺序的 IO。默认关闭（`mrr=off`），因为排序本身有 CPU 开销，且效果依赖主键与页的局部性。知道它存在即可，面试被问到「回表能不能优化」时能多一个答案。

## 为什么这么设计

- **二级索引为什么不存整行**：一张表 5 个索引就是 5 份数据，写一次要写 5 遍，缓冲池也装不下。存主键是「用一次额外的随机 IO 换 N 倍的存储和写入成本」，绝大多数场景划算。
- **叶子为什么用双向链表**：范围查询和 `order by` 只要顺着链表走，不用回到父节点做中序遍历，这是 B+ 树相对 B 树在范围查询上的核心优势。
- **为什么非叶子不存数据**：同样一页能塞更多键 → 扇出更大 → 树更矮 → IO 更少。代价是任何查询都必须走到叶子，等值查询也不能提前结束。
- **ICP 为什么放在引擎层**：server 层和引擎层是**按行**交互的，少传 980 行就少 980 次跨层调用和条件求值。代价是引擎层要理解更多表达式，耦合变重，所以有些条件（子查询、存储函数）它不接。
- **为什么不用哈希索引**：等值 O(1) 很香，但范围、排序、最左前缀全部失效，而业务查询九成带范围或排序条件。

## 不用会怎么样

- **没有索引**：千万行流水表按业务号查一次是秒级；更糟的是全表扫会把 buffer pool 里的热页挤出去，缓存命中率从 99% 掉到 70%，**同实例上的所有查询一起变慢**。
- **有索引但回表太多**：`select * from t_order where merchant_no=?` 命中 5 万行 → 5 万次随机 IO，实测比全表扫还慢 2 倍，这就是「加了索引反而更慢」最常见的真相。
- **该下推没下推**（5.5 及更早）：`name like '张%'` 命中 10 万、实际只要 200 条，回表放大 500 倍，一条查询把磁盘 IOPS 打满。
- **把大字段放进索引**：`(merchant_no, remark)` 这种索引，一页装不下几条，树高一层，等于白建。

## 替代方案

| 方案 | 适用 | 代价 / 风险 |
|---|---|---|
| B+ 树索引 | 范围、等值、排序，默认选择 | 写入维护成本，索引越多写越慢 |
| 覆盖索引 | 高频固定列查询（列表页、对账） | 索引变宽，占空间，写入放大 |
| 哈希索引 | 纯等值（Memory 引擎、自适应哈希） | 不支持范围与排序 |
| 全文索引 / ES | 文本检索、多条件组合 | 中文要分词；外部组件有一致性问题 |
| 列存（ClickHouse） | 海量聚合、报表 | 不适合点查与事务更新 |
| 增加冗余列 | 避免回表又不愿加宽索引 | 一致性要靠代码维护，容易写漏 |

## 项目中如何使用

- **某银行账务流水查询**：核心条件是「账户 + 日期区间 + 状态」，建联合索引 `(account_no, biz_date, status)`——account_no 等值、biz_date 范围、status 放最后。列表页只需要 6 列，全部补进索引做成覆盖索引，`Extra` 从 `Using where` 变成 `Using index`，P99 从 800ms 降到 90ms。这里有个细节：status 在范围列后面，**定位用不上，但 ICP 能过滤**，所以它没白放。
- **某支付公司清结算对账**：商户对账单列表原先是 `select *`，一页 20 条但 `count` 要扫 3 万行并逐条回表。改成两步：先用覆盖索引 `select id from ... limit 20` 拿主键，再一次 `where id in (...)` 批量取详情，3 万次随机回表变成 150 次批量查询。
- **幂等兜底**：支付流水表 `uk_biz(biz_no)` 唯一索引，重复请求直接撞唯一约束报 `DuplicateKeyException`，比「先查再插」少一次回表、也没有并发窗口。

## 常见陷阱

- **「二级索引叶子存的是行地址」**——InnoDB 存的是**主键值**，MyISAM 才是行号。这个区别直接决定了 InnoDB 必须有聚簇索引。
- **「走了索引就一定快」**——回表 5 万次比全表扫慢，判断标准是 `rows` 和回表比例，不是 `key` 有没有值。
- **「索引下推能减少扫描行数」**——只减少回表次数，索引该扫多少还是多少。这个答错，面试官会立刻追问「那它到底省了什么」。
- **「覆盖索引就是把要查的列都塞进索引」**——塞进去的列会撑宽索引页，`varchar(500)` 这种列塞进去等于毁掉这个索引。
- 面试官会接着问：**「`Using index` 和 `Using index condition` 有什么区别？」** 前者是覆盖、根本不回表；后者是下推、仍然要回表，只是回表次数少了。

## 三层追问

1. **为什么 InnoDB 一张表只能有一个聚簇索引？**——数据在磁盘上只能按一种顺序物理组织一次；其他顺序只能另建一棵树，而另建的树里没法放整行（放整行就是又一份数据）。
2. **回表能不能彻底避免？**——能避免就三条路：覆盖索引（最常用）、延迟关联（先取主键再批量取详情）、把过滤条件补齐到索引里让 ICP 先把量降下来。三条路的本质都是「减少随机 IO 次数」。
3. **覆盖索引和索引下推能同时生效吗？**——覆盖索引时根本不回表，ICP 就没有意义了。实际是二选一：**能覆盖就覆盖，不能覆盖才靠下推减少回表**。面试里能把这句话说出来，说明你真理解了两者的位置关系。
