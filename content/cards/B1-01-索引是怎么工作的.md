## 30 秒简述

InnoDB 的索引，就是一棵按索引列排好序的 B+ 树。

但一张表不止一棵树。主键那棵叫聚簇索引，叶子直接是整行，表本身就是它。其余的二级索引是另外的树，叶子只放「索引列 + 主键」。

所以走二级索引要查两棵。先在第一棵里定位到主键，再拿主键回聚簇索引取整行。后一步叫回表，是随机 IO，贵就贵在这。

要查的列全在二级索引里，第一棵就结束了，这是覆盖。where 里还有索引内的列、但用不上定位，可以让引擎在索引上先筛一遍再回表，这是索引下推。

三个词其实是一条路上的三个截断点。停在第一棵是覆盖，第一棵之后先筛是下推，走到第二棵是回表。

## 是什么

从盘上到底放了什么说起。

InnoDB 跟磁盘打交道以页为单位，一页 16KB，一次读一页，不是读一行。页里的记录按索引列排好序，页尾有个 slot 数组当页目录，页内查找走二分。页和页之间才组成 B+ 树。

非叶子节点只存「键 + 页号」。叶子存数据，叶子之间拿双向链表串着。

所以索引不是另建一张表，是同一批数据按另一个顺序排出来的一份目录。目录里塞的东西越少，一页装得越多，树就越矮，IO 越少。

一页能装多少，当场能算。16KB 的页，bigint 主键 8 字节，页号 6 字节，差不多 14 字节一个键，非叶子一页放得下 1170 个。假设一行 1KB，叶子一页放 16 行。三层就是 1170 × 1170 × 16，约 2100 万行。千万级的表查一次，三次页访问，根页还常驻内存，实际两次磁盘 IO。

| | 聚簇索引（主键索引） | 二级索引（普通索引） |
|---|---|---|
| 叶子存什么 | **整行数据** | **索引列 + 主键值** |
| 一张表有几个 | 有且只有一个 | 想建几个建几个 |
| 顺序由谁定 | 主键（无主键用第一个唯一非空索引，再没有用隐藏 rowid） | 建索引时指定的列 |
| 一次查询要访问几棵树 | 1 棵 | 2 棵（除非覆盖） |
| 范围查询 | 叶子链表顺序扫 | 先扫二级索引，再逐条回表（顺序变成随机） |

区别一句话就够：聚簇索引的叶子就是表，二级索引的叶子是一张「键 → 主键」的映射。

拿 `select * from t_order where merchant_no = 'M123'` 走一遍，索引是 `idx_merchant(merchant_no, biz_date)`。

优化器先估 `idx_merchant` 大概命中多少行。只占表的百分之几就用它，占比太高就直接全表扫。

然后进第一棵树。从根页开始二分，找到 `merchant_no='M123'` 那个叶子页，顺着链表把命中的索引项全取出来，每一项带一个主键 id。

接着第二棵树。拿 id 回聚簇索引再二分一次，取整行。每条命中记录都要回一次，而且这些 id 在聚簇索引里是乱的。

![一条二级索引查询的三段路：第一棵树定位主键，第二棵树回表取整行；覆盖索引停在第一棵树，索引下推在第一棵树之后先过滤](img/index-query-path.svg)

为什么乱？二级索引按 `merchant_no` 有序，命中的主键自然不连续；聚簇索引按主键有序，只有主键挨着才可能落在同一页。于是 N 条命中差不多就是 N 次随机页访问，除非页正好都在 buffer pool 里。

机械盘上随机 IO 比顺序慢两个数量级。SSD 好一点，但 IOPS 照样是瓶颈。所以回表次数，比「有没有走索引」更值得看。

有个经验值：命中行数超过表的 20%~30%，优化器往往直接放弃索引。顺序读整表，比「索引扫一遍再加一堆随机回表」便宜。这不是 bug，是算出来的。

三个截断点，一个个说。

覆盖停在第一棵。查询要返回和过滤的列全在索引里，就不用回表，`Extra` 会出现 `Using index`。索引 `(merchant_no, biz_date)`，查 `select merchant_no, biz_date from t_order where merchant_no = ?`，只读一棵树。

几个容易记错的。`select *` 永远不可能是覆盖。`count(*)` 走二级索引也算覆盖，它只数索引项不取整行，所以比 `count(普通列)` 快，后者要判非空。还有，覆盖不是「把列加进索引就完事」，索引一宽，一页装的条目变少，树变高，写入还要多维护一份，是拿写换读。

下推在第一棵之后。5.6 加的，默认开着，开关是 `optimizer_switch` 里的 `index_condition_pushdown`。

场景是这样：联合索引 `(name, age)`，SQL 写 `where name like '张%' and age = 25`。`name like '张%'` 是范围，`age` 用不上定位，B+ 树在 age 上只在同一个 name 内部有序。

没有 ICP 的时候，引擎把所有「张」开头的记录逐条回表，把整行交给 server 层，server 层再判 `age=25`。命中 1000 条，实际只要 20 条，1000 次回表里 980 次白跑。

有 ICP 就不一样。`age` 本来就在索引里，引擎在二级索引上顺手判掉，只对剩下那 20 条回表。回表 1000 降到 20，`Extra` 显示 `Using index condition`。

三个边界得说清。它不减少索引扫描行数，`name like '张%'` 该扫 1000 条还是 1000 条，省掉的只是回表。下推的列必须在当前用的索引里，但不要求是最左前缀。条件里不能有子查询和存储函数，5.6 的分区表还不支持，5.7 才修好。

![索引下推：同一个 SQL，没有 ICP 时回表 1000 次、980 次白跑；有 ICP 时在二级索引上先过滤，只回表 20 次](img/index-icp.svg)

最后是联合索引本身。`(a, b, c)` 是字典序，先按 a 排，a 相同按 b，b 相同按 c。三条结论都从这儿推出来。

能定位的列，必须从最左开始连续。`where a=? and b=?` 用两列；`where b=?` 用不上；`where a=? and c=?` 只有 a 能定位，c 靠 ICP 过滤。

一个范围会截断后面的定位。`where a=? and b>? and c=?`，a、b 定位，c 只能 ICP；`where a>? and b=?`，只有 a。

排序想用索引，前面得全是等值，排序从下一个列开始。`where a=? order by b` 能省掉 filesort，`where a>? order by b` 不行。

8.0.13 起有 skip scan。`(a, b)` 上查 `where b=?`，如果 a 的基数很低，可以挨个 a 值跳着扫 b。但它依赖基数，也不能带范围条件，别当成「最左前缀失效」的通用解法。

还有个 MRR，Multi-Range Read。把二级索引拿到的乱序主键先排个序，再按主键顺序回表，随机 IO 就变成接近顺序了。默认关着（`mrr=off`），因为排序本身吃 CPU，效果还看主键和页的局部性。知道它存在就行，被问「回表能不能优化」时多一个答案。

## 为什么这么设计

二级索引为什么不存整行。一张表 5 个索引就是 5 份数据，写一次写 5 遍，缓冲池也装不下。存主键是拿「多一次随机 IO」换「N 倍的存储和写入成本」，绝大多数场景划算。

叶子为什么用双向链表。范围查询和 `order by` 顺着链表走就行，不用回父节点做中序遍历。这是 B+ 树比 B 树强的地方。

非叶子为什么不存数据。同样一页塞更多键，扇出更大，树更矮，IO 更少。代价是任何查询都得走到叶子，等值查询也不能提前收工。

ICP 为什么放在引擎层。server 层和引擎层是按行交互的，少传 980 行就少 980 次跨层调用和条件求值。代价是引擎层得理解更多表达式，耦合变重，有些条件它就不接了。

为什么不用哈希索引。等值 O(1) 确实香，可范围、排序、最左前缀全废，而业务查询九成带着范围或者排序。

## 不用会怎么样

没有索引。千万行流水表按业务号查一次是秒级。更糟的是全表扫会把 buffer pool 里的热页挤出去，命中率从 99% 掉到 70%，同实例上所有查询一起慢。

有索引但回表太多。`select * from t_order where merchant_no=?` 命中 5 万行，就是 5 万次随机 IO，实测比全表扫还慢两倍。这就是「加了索引反而更慢」最常见的真相。

该下推没下推，5.5 及更早。`name like '张%'` 命中 10 万、实际只要 200，回表放大 500 倍，一条查询把磁盘 IOPS 打满。

把大字段放进索引。`(merchant_no, remark)` 这种，一页装不下几条，树高一层，等于白建。

## 替代方案

| 方案 | 适用 | 代价 / 风险 |
|---|---|---|
| B+ 树索引 | 范围、等值、排序，默认选择 | 写入维护成本，索引越多写越慢 |
| 覆盖索引 | 高频固定列查询（列表页、对账） | 索引变宽，占空间，写入放大 |
| 哈希索引 | 纯等值（Memory 引擎、自适应哈希） | 不支持范围与排序 |
| 全文索引 / ES | 文本检索、多条件组合 | 中文要分词；外部组件有一致性问题 |
| 列存（ClickHouse） | 海量聚合、报表 | 不适合点查与事务更新 |
| 增加冗余列 | 避免回表又不愿加宽索引 | 一致性要靠代码维护，容易写漏 |

## 项目中如何使用

某银行的账务流水查询，核心条件是「账户 + 日期区间 + 状态」。建的是联合索引 `(account_no, biz_date, status)`：account_no 等值，biz_date 范围，status 放最后。列表页只要 6 列，全补进索引做成覆盖，`Extra` 从 `Using where` 变成 `Using index`，P99 从 800ms 到 90ms。这里有个细节，status 在范围列后面，定位用不上，但 ICP 能过滤，所以它没白放。

某支付公司的清结算对账，商户对账单列表原来是 `select *`，一页 20 条，可 `count` 要扫 3 万行、逐条回表。改成两步：先用覆盖索引 `select id from ... limit 20` 拿主键，再一次 `where id in (...)` 批量取详情。3 万次随机回表变成 150 次批量查询。

还有个顺手用的地方，幂等兜底。支付流水表建 `uk_biz(biz_no)` 唯一索引，重复请求直接撞唯一约束报 `DuplicateKeyException`，比「先查再插」少一次回表，也没有并发窗口。

## 常见陷阱

- 以为二级索引叶子存的是行地址。InnoDB 存的是主键值，MyISAM 才是行号。这个区别直接决定了 InnoDB 必须有聚簇索引。
- 以为走了索引就一定快。回表 5 万次能比全表扫还慢，判断标准是 `rows` 和回表比例，不是 `key` 有没有值。
- 以为索引下推能减少扫描行数。它只减少回表，索引该扫多少还是多少。这个答错，下一句就是「那它到底省了什么」。
- 以为覆盖索引就是把要查的列都塞进索引。塞进去的列会撑宽索引页，`varchar(500)` 塞进去等于把这个索引毁了。
- 面试官会接着问「`Using index` 和 `Using index condition` 差在哪」。前者是覆盖，根本不回表；后者是下推，仍然要回表，只是回表次数少了。

## 三层追问

1. 为什么一张表只能有一个聚簇索引。数据在磁盘上只能按一种顺序物理组织一次。别的顺序要另建树，而另建的树里放不下整行，放整行就是又一份数据了。
2. 回表能不能彻底避免。三条路：覆盖索引，最常用；延迟关联，先取主键再批量取详情；把过滤条件补齐到索引里，让 ICP 先把量降下来。本质都是减少随机 IO 次数。
3. 覆盖和下推能同时生效吗。覆盖的时候根本不回表，下推就没意义了。实际是二选一：能覆盖就覆盖，覆盖不了才靠下推减少回表。这句话能顺出来，说明两者的位置关系是真懂了。
