## 30 秒简述

结论：**分库分表不是第一选择**，先回答「为什么拆」，**分片键选错，后面全是补丁**。只有单表两千万行以上、索引和数据超出 buffer pool、单库写入或连接数成瓶颈才值得拆，否则索引优化、冷热归档、读写分离收益更高，而拆完会**失去跨库 join、跨库强事务、全局排序**，运维和 DDL 复杂度翻倍。真拆就三件事：**选分片键**，要求九成以上查询都带它、分布均匀、和业务强相关；**选路由算法**，hash 均衡但扩容难，range 易扩但有热尾；处理跨库分页、全局 ID、分布式事务和迁移这些副作用。实际项目是按商户号 hash 拆 16 库乘 128 表，流量回放比对一致后才按商户灰度切流。

## 是什么

- **两种拆法**：垂直拆（按业务拆库拆表，如支付库/对账库）；水平拆（同表按分片键散到多库多表）。生产上通常两者组合。
- **分片键**：必须进查询条件，否则路由到全部分片（广播查询，N 倍放大）。商户号、用户 ID 这类「同主体数据聚在一起」的字段优先；用时间做分片键会导致写入永远落在最新一片（热尾）。
- **路由算法**：`hash(分片键) % 分片数`（均衡，扩容要 rehash）；`range` / 时间（易扩容，有热尾）；一致性 hash（扩容影响面小，实现复杂）；**基因法**（把分片位编码进订单号，用订单号也能直接路由，省掉二次查询）。
- **全局唯一 ID**：雪花（时间 + 机器 + 序列，趋势递增对 B+ 树友好）、号段模式（DB 批量取号，减少 DB 压力）、Redis `incr`、UUID（无序，页分裂，不推荐做主键）。
- **中间件**：ShardingSphere-JDBC（客户端 jar，直接改 SQL 路由，无额外跳数）vs ShardingSphere-Proxy（独立代理，多语言友好，多一跳）。
- **跨库查询的解法**：冗余字段（把商家名冗余进订单）、广播表（字典/费率配置每个库一份）、绑定表（同分片键的表 join 可下推）、异构索引（Canal 同步到 ES 做多维查询）。
- **跨库分页**：`limit offset, n` 在各分片取 `offset+n` 再归并，越翻越慢；深分页改用「按 ID 游标」或「二次查询法」。
- **分布式事务**：同分片内仍是本地事务；跨分片只能最终一致（本地消息表 / 事务消息 + 幂等消费）。

## 为什么这么设计

分片是为了突破单机的**存储上限、写入上限、连接数上限**。代价极其明确：失去跨库 join、失去跨库强事务、失去全局排序与全局自增、运维与发布复杂度翻倍（DDL 要逐片执行，扩容要迁数据）。所以判断标准是「单机优化已经没有空间」，不是「表大了就拆」。

选 hash 而不是 range，是拿「扩容难」换「分布均匀」；选 range 则相反。业务上如果查询几乎都带商户号，hash 商户号最划算——同商户的流水、账单、对账明细都落在同一片，本地事务和本地 join 都还能用。

## 不用会怎么样

- 单表过亿后 DDL 加索引锁表数小时，业务只能停写窗口做；索引维护成本高，`buffer pool` 命中率下降，P99 从 20ms 涨到几百毫秒。
- 单库连接数打满，一条慢 SQL 拖垮整个库，故障半径覆盖所有业务线。
- 归档不做、只靠索引优化硬扛，最终还是会撞上磁盘与备份窗口（1TB 的库做一次全备要几小时）。

## 替代方案

| 方案 | 适用 | 说明 / 风险 |
|---|---|---|
| 索引优化 + SQL 治理 | 数据量 < 2000 万 | 成本最低，先做这个；治不了写入瓶颈 |
| 冷热分离 + 历史归档 | 查询集中在近期数据 | 主表变小，效果立竿见影；跨期查询要合并 |
| 读写分离 | 读多写少 | 缓解读压力；主从延迟会导致「刚写读不到」 |
| 分区表（Partition） | 按时间清理的场景 | 单机内解决，运维简单；跨分区查询仍慢 |
| 分库分表 | 单机确实到顶 | 主流方案；副作用最多，必须有中间件与迁移方案 |
| NewSQL（TiDB 等） | 想保留 SQL 能力又要水平扩展 | 省掉应用层拆分；引入新组件，团队要能运维 |

## 项目中如何使用

- **某银行 C9→C10 重构**：支付流水与对账明细是两张最大的表，按 `商户号 hash` 拆 16 库 × 128 表，同一商户的流水、明细、差错落在同一片，本地事务仍可用；对账明细再叠加「账期月份」做子分区，方便按月归档。中间件用 ShardingSphere-JDBC，业务代码基本无感。
- **拆分前用流量回放验证**：把生产脱敏报文回放到新链路，比对「响应报文 + 落库结果 + 分片路由」三处一致性，跑了约两周生产流量才切流；切流按商户灰度，先 1% 再 10%，异常可一键回切旧链路。
- **跨库统计不打到分片库**：多维汇总与报表走 Canal 同步的 ES，联机查询只按分片键走精准路由；费率、渠道字典做广播表，每库一份，避免跨库 join。
- **某支付公司交易流水**：按「账期 + 商户」双维度，历史按月归档到冷库，热表只保留近 6 个月，查询先按账期定位再按商户路由。

## 常见陷阱

- 分片键选时间：写入全压在一个分片，等于没拆，还把查询搞复杂了。
- 用非分片键查询：中间件广播到所有分片再归并，QPS 放大 16 倍，慢查询更容易打满连接池。
- 继续用 `auto_increment` 做主键：各分片自增会撞号，必须换雪花或号段。
- 跨库 `count(*)` 与深分页：`limit 100000, 20` 在每片取 100020 条再归并，内存与网络直接爆。
- 面试官会追问「怎么平滑扩容」：答「成倍扩容 + 双写 + 历史数据迁移 + 双向校验 + 灰度读切换」，不要只说「加机器」。

## 三层追问

1. **为什么不能一上来就拆？**——拆完失去 join 与强事务，很多原本一条 SQL 的事要改成应用层拼装；而 80% 的慢查询其实靠索引和归档就能解决。
2. **分片键能改吗？**——技术上能（重建表 + 数据迁移 + 双写切换），代价接近重做一次拆分，所以选型阶段就要按「未来三年的查询模式」定，别按当下的报表需求定。
3. **拆分后对账怎么做？**——按分片维度并行跑：每个分片独立跑「本地流水 ↔ 本地渠道单」的撮合，汇总层只合并差错结果，避免跨库大 join。
