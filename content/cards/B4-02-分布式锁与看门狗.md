## 30 秒简述

Redis 分布式锁的三个必要条件：**加锁原子性（SET key value NX PX）、唯一标识（value 存 UUID/线程标识）、释放原子性（Lua 校验后删除）**。业务执行时间不确定 → 需要看门狗自动续期（Redisson 默认 30s 租期、每 10s 续一次）。但要清楚：**Redis 锁是"效率锁"，不是"正确性锁"**——主从异步复制下锁可能丢失，真正的资金安全必须靠 DB 唯一约束或状态机兜底。

## 是什么

- 加锁：`SET lock:key uuid NX PX 30000`，返回 OK 才算拿到。
- 解锁：Lua 脚本 `if redis.call('get',KEYS[1]) == ARGV[1] then return redis.call('del',KEYS[1]) end`。
- 看门狗：加锁成功后启动定时任务（默认 1/3 租期）检查持有并续期；JVM 挂了则不再续期，锁自然过期。
- 可重入：Redisson 用 Hash 结构记录 `锁名 -> {线程ID: 重入次数}`。

## 为什么这么设计

用 Redis 做锁是因为性能高、实现简单，但它牺牲的是"强一致"：主从切换、网络分区都可能导致两个客户端同时持锁。所以工程上的正确姿势是**锁负责降低冲突概率，数据库负责保证最终正确**。

## 不用会怎么样

没有唯一 value → A 的锁过期后 B 拿到，A 执行完把 B 的锁删了，互斥彻底失效；没有 Lua → get 和 del 之间可能插入别人的加锁；没有续期 → 长事务未完成锁先过期。

## 替代方案

| 方案 | 一致性 | 性能 | 适用 |
|---|---|---|---|
| Redis（Redisson） | 弱（主从丢失） | 高 | 防重复提交、任务互斥 |
| RedLock | 争议大，仍非强一致 | 中 | 不推荐用于资金 |
| ZooKeeper / etcd | 强（CP） | 中低 | 需要严格互斥的调度 |
| DB 唯一索引/乐观锁 | 强 | 中 | **资金类首选兜底** |

## 项目中如何使用

- "一锁二判断三更新"：Redisson 锁按"租户 + 业务参考号"加锁 → 判断是否已有在途单据（状态机 + 幂等表）→ 更新状态并提交银行。
- 锁粒度不放大到租户级，否则同租户并发性能骤降；同时用 DB 唯一索引做最后一道防线，锁失效也不会产生二次扣款。
- 看门狗开启（业务含银行 HTTP 调用，耗时不定），并配合接口超时上限，避免无限续期。

## 常见陷阱

- 答"用 setnx + expire"，不说原子性与误删问题。
- 把分布式锁当作资金安全的唯一保障——这是最容易被资深面试官否掉的点。

## 三层追问

1. 锁超时时间设多少？——预估 P99 耗时的 2~3 倍 + 续期；不能设成"永不过期"，否则宕机即死锁。
2. Redis 主从切换丢锁怎么办？——资金场景不能只靠锁，靠唯一约束；或降低锁的作用域（只做防重，不做正确性保证）。
3. Redisson 可重入怎么实现的？——Hash 记录线程与计数，释放时递减到 0 才删除。
