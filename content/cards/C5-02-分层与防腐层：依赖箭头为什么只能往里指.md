## 30 秒简述

四层分层的关键是依赖方向：接入层调应用层，应用层调领域层，基础设施层实现领域层声明的接口，箭头只往里指。领域服务不知道 Feign，也不知道 MyBatis，它只认 `AccountStatusRepository` 这个接口；具体怎么查库、怎么调直连中心，由基础设施层的实现决定，Spring 启动时注入。下游的异常和 DTO 停在防腐层：Feign 抛异常时转成空 Map 放行，租户开关读不到按未开启处理，领域层看不到 HttpException。代价是每接一个下游多两个类，唯一一次跨层调用（CRUD 后立刻刷新关键词缓存）只能靠注释和评审收口。

## 是什么

![Scout 的四层：接入、应用、领域、基础设施，加两个外部系统；虚线是接口实现与唯一一处跨层调用](img/scout-components.png)

四个边界：

| 边界 | 放什么 | 依赖谁 |
|---|---|---|
| 接入层 adapter | Controller，校验入参、组装 ApiResponse | 应用层 |
| 应用层 application | 用例编排：批量、TTL 过滤、分流、事务边界 | 领域层 |
| 领域层 domain | 规则本体：按位取数、告警归集、清位打标、Trie 匹配、状态位合并；仓储接口声明 | 只依赖自己的接口 |
| 基础设施层 infrastructure | 仓储实现、Mapper、Feign 客户端、定时任务、缓存 | 实现领域层接口 |

依赖方向的一条规矩：`domain` 里不出现 `feign`、`mybatis`、`HttpClient` 的 import。领域服务注入的是接口，不是实现类。

两处防腐层，作用是把下游语言翻译成领域语言：

- `DirectCenterSupportImpl`：Feign 调直连中心批量查状态。正常返回转成领域对象；抛 `FeignException` 时记日志、返回空 Map，不往上抛。领域层拿到的永远是这批状态，不是 HTTP 500。
- `TenantSwitchServiceImpl`：从远端配置读租户位开关，Caffeine 缓存。读不到或超时按未开启处理，领域层只看到布尔值，不知道远端配了个什么。

三张表对应三个仓储接口，实现各挂一个 MyBatis Mapper。Mapper 只写 SQL，不加业务判断；换存储只要换实现类。Feign 的超时、重试、幂等细节见 `C5-01 Feign 超时、重试与幂等`。

唯一一处跨层：`KeywordConfigApplicationService` 在 CRUD 之后直接调基础设施层的 `KeywordConfigRefresher.refreshNow()`，不等 30 秒定时。这是需求逼出来的——运维改完关键词要立刻生效——但方向确实反了，规范做法是在领域层声明一个刷新接口，让应用层依赖接口。

图上还有两个缺口：`TimeoutExecutor` 只有 Bean 声明，没有任何类注入它，3 秒超时熔断没接进预检链路；设计文档写的 Kafka 消费端不存在，交易终态只经 `EngineMessageController` 的 HTTP 回调进来。Bean 注册了为什么没被注入，属于生命周期问题，见 `C1-01 Spring 内核：Bean 生命周期、循环依赖与代理陷阱`。

## 为什么这么设计

**依赖倒置让领域可测。** 领域服务的单测不需要起 Spring、不需要数据库、不需要 wiremock，把仓储接口用匿名类或 mock 塞进去就能跑。代价是接口和实现各写一份，同样的字段映射写两遍：领域对象一遍，持久化对象一遍。

**防腐层把下游故障挡在外面。** Feign 超时、配置中心不可用，这些在基础设施层就转成领域能理解的值（空 Map、未开启）。代价是异常被吞掉之后，日志和指标必须跟上，否则放行会变成失明：系统看起来正常，实际一直在降级。

**边界按变化频率切。** 表结构、报文格式变得快，放基础设施层；校验规则相对稳定，放领域层。代价是这条线有主观性，同一个类放哪一层经常要吵，团队得定期对账，否则半年后边界就模糊了。

**跨层调用显式化。** 整个服务只有 `refreshNow()` 一处跨层，注释写明原因、范围、替代方案。代价是靠人守，构建工具拦不住；一处开了口子，后面就容易变成三处。

## 不用会怎么样

- 领域服务直接 new Feign 客户端：单测要起 wiremock，改一个下游影响所有测试。
- 下游 DTO 直接进领域：银行字段改名，领域层跟着改，连锁到应用层。
- 没有防腐层：Feign 异常直接冒到 Controller，一次下游抖动变成一批 500。
- 逻辑全塞 Controller：规则散在入口，换一个入口就漏一套判断。

## 替代方案

| 方案 | 适用场景 | 风险或代价 |
|---|---|---|
| 传统三层（Controller-Service-Mapper） | 小系统、CRUD 为主 | 业务逻辑和 SQL 混在 Service，换存储要改业务 |
| DDD 四层加仓储接口（本项目） | 领域规则复杂、下游多 | 类多、映射多，简单 CRUD 会显得过度设计 |
| 事务脚本加独立网关 | 逻辑简单、下游少 | 网关成为新单点，规则还是散在脚本里 |
| 直接依赖具体客户端，不做防腐层 | 原型、一次性脚本 | 下游异常和 DTO 长进业务，后面改不动 |

## 项目中如何使用

某银行财资系统的支付失败率治理服务，Spring Boot 3.2，四个边界按包分：`adapter`、`application`、`domain`、`infrastructure`。domain 里只有领域服务和仓储接口，三个接口对应三张表（`keyword_config`、`t_account_status_config`、`t_account_limit_config`）。

两处防腐层的实际参数：直连中心批量查询走 Feign，失败返回空 Map；租户开关走 Caffeine 缓存，TTL（待补充），读不到按未开启。预检入口收到的是账号列表，应用层批量编排，领域层按位取数，越权判断留在应用层。

测试策略跟着边界走：领域服务纯单测，仓储实现用真实 MySQL 容器（待补充），防腐层用 mock 的 Feign 客户端验证异常转空 Map。这套分法让预检的领域规则可以在几毫秒内跑完单测，不用等 Spring 上下文。

面试怎么讲：先画依赖箭头，再举一个防腐层的例子（Feign 异常转空 Map），主动交代那处跨层调用和两个缺口。面试官对你知道哪里不干净的注意力，通常比对你的架构很干净更大。

## 常见陷阱

1. 把分层做成目录分层。包分了四层，领域服务照样 import Feign 客户端，箭头实际上是双向的。
2. 仓储接口放基础设施层。依赖方向反了，领域层被迫依赖实现，单测还得起数据库。
3. 防腐层吞异常不打日志。fail-open 变成失明，降级了半年没人知道。
4. Bean 注册了没注入。`TimeoutExecutor` 只有声明没有使用方，文档里的 3 秒熔断从来没生效；这类缺口要靠链路图对代码，不能信文档。
5. 面试官会接着问什么：为什么 `refreshNow()` 算跨层、怎么改才算干净、领域事件和直接调用的取舍、防腐层和 API 网关的区别、仓储接口和 MyBatis Mapper 的边界在哪。

## 三层追问

**第一层，是什么**：四个边界各放什么，依赖只往里指；两处防腐层负责把下游异常和配置翻译成领域语言。

**第二层，为什么**：为什么接口放领域层？依赖倒置让领域不依赖实现，单测不需要基础设施。为什么异常要转成空 Map？预检的业务语义是拿不到状态就不拦，转空 Map 比抛异常更接近语义。

**第三层，不用会怎么样**：下游一改，业务跟着改；单测起一整套环境；一处下游抖动扩散成一批 500。
