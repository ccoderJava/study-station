## 30 秒简述

结论：动态线程池的核心不是调参 API，JDK 本来就有 setter，真正要解决的是**配置存哪、怎么进内存、谁来改**这三件事。做法是一张配置表 `t_dynamic_thread_pool_config` 加一张审计表，主键是应用名加池名，同一个组几个微服务共用一张，**应用名就是服务之间的隔离边界**；每个实例起一个守护线程，每 5 秒全量拉一遍，跟内存快照比对，有变化才逐项调 setter；管理页面或 SQL 只写表，不直接改内存，保证**一个池子只有一个真相来源**。最容易踩的坑不是怎么改，而是「**以为改了**」：表里字段改了、代码还是写死队列容量，配置就是装饰。

## 是什么

### 一、JDK 给了哪些口子，边界在哪

| 参数 | 有 setter 吗 | 改大的效果 | 改小的效果 |
|---|---|---|---|
| `corePoolSize` | ✓ `setCorePoolSize` | **立刻补线程**（内部 `addWorker` 补齐差值） | 不立刻回收，空闲线程到 `keepAlive` 才退；核心线程要开 `allowCoreThreadTimeOut` 才退 |
| `maximumPoolSize` | ✓ `setMaximumPoolSize` | 立刻，但只在下次「队列满扩容」判断时体现 | 正在跑的线程不受影响，只影响后续判断 |
| `keepAliveTime` | ✓ `setKeepAliveTime` | 立刻 | 已经在 `poll(timeout)` 里等待的线程仍按旧值醒来 |
| `RejectedExecutionHandler` | ✓ `setRejectedExecutionHandler` | 立刻 | 立刻，但对队列里已排队的任务无效 |
| `threadFactory` | ✗ 无 setter | — | 线程名在创建时定死，改不了 |
| `workQueue` 容量 | ✗ 无 setter | — | `capacity` 是 `final`，见下面「可变容量队列」 |
| `allowCoreThreadTimeOut` | ✓ | 立刻 | 立刻 |

两个必须记住的实现细节：

**1）`core ≤ max` 这个不变式会抛异常，所以改的顺序有讲究。**

```java
// setMaximumPoolSize 里有校验：maximumPoolSize < corePoolSize 直接抛 IllegalArgumentException
// 所以调大时：先 max、后 core；调小时：先 core、后 max —— 保证任何中间态都合法
if (targetMax > targetCore) {
    p.setMaximumPoolSize(targetMax);
    p.setCorePoolSize(targetCore);
} else {
    p.setCorePoolSize(targetCore);
    p.setMaximumPoolSize(targetMax);
}
```

顺序写反了会抛异常，而且**异常只发生在调小 max 的那一次**，测试环境线程数少不一定复现。

**2）`setCorePoolSize` 调大的实现是「补线程」，不是「改个数」。** 源码里会算出 `delta = corePoolSize - workerCount`，然后循环 `addWorker(null, true)`；调小时只把字段改小，多余的线程要靠空闲超时自然退出——如果 `allowCoreThreadTimeOut=false`（默认），**这些线程永远不会退**，你以为调小了，实际只是新任务来得少了。

### 二、表怎么设计

实际在用的是这么一张配置表，字段不多，但每个都对应一个真实约束：

```sql
CREATE TABLE t_dynamic_thread_pool_config (
  application_name   VARCHAR(50)  NOT NULL COMMENT '应用名称',
  pool_name          VARCHAR(30)  NOT NULL COMMENT '线程池名称',
  pool_function      VARCHAR(100) NOT NULL COMMENT '线程池功能，给人看的',
  core_pool_size     INT          NOT NULL COMMENT '核心线程数（目标值）',
  max_pool_size      INT          NOT NULL COMMENT '最大线程数（目标值）',
  min_pool_size      INT          NOT NULL COMMENT '最小线程数（下限保护）',
  adjust_size        INT          NOT NULL COMMENT '单次调整步长',
  queue_capacity     INT          NOT NULL COMMENT '队列容量',
  keep_alive_seconds INT          NOT NULL COMMENT '空闲线程存活秒数',
  create_by          VARCHAR(200) NOT NULL COMMENT '创建人',
  create_date        DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_date        DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (application_name, pool_name)
) COMMENT '线程池配置';
```

再加一张审计表，否则出事只能翻 binlog：

```sql
CREATE TABLE t_dynamic_thread_pool_log (
  id            BIGINT       NOT NULL AUTO_INCREMENT,
  application_name VARCHAR(50) NOT NULL,
  pool_name     VARCHAR(30)  NOT NULL,
  before_value  JSON         NOT NULL COMMENT '改前整行',
  after_value   JSON         NOT NULL COMMENT '改后整行',
  reason        VARCHAR(200) NOT NULL COMMENT '变更原因，值班填',
  operator      VARCHAR(64)  NOT NULL,
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_pool (application_name, pool_name, id)
) COMMENT '线程池参数变更审计';
```

设计上六个取舍，每个都能被追问：

- **复合主键 `(application_name, pool_name)` 而不是自增 id**。这张表不是「一个服务一张」，而是**一个领域内几个微服务共用的底座**：一个组四五个服务，每个服务两三个池，全组都读这一张。`application_name` 不是装饰字段，它是**服务之间的隔离边界**——A 服务只取自己那几行，B 服务往表里加池子不会影响 A。
  用组合主键意味着**同一个服务不可能有两个同名池**（数据库帮你挡了），插入即声明，不用先查再插；代价是改 `pool_name` 等于删了再插，关联查询要带两个字段。
  **为什么不给每个服务建一张表**：这张表的价值就在于「同一份刷新器代码、同一条救火路径、同一套审计」，拆成 N 张表等于把这三样复制 N 份，最后每个服务的刷新间隔、字段含义、校验规则都不一样。真到几百个服务、几千行的量级，`application_name` 天然就是分片键，加一层路由或分库就行，业务代码不用动。反过来，**不同领域（不同组）各建一张**，结构一模一样但数据不互通——没有人需要跨领域查别人家的线程池。
- **没有 `version` 字段，因为这张表不需要增量同步**。几十行数据，每 5 秒全量 `SELECT` 一次是几毫秒，而增量方案要引入「单调递增列 + 每实例水位 + 同秒多条 + 主从延迟」四个问题。**数据量小的时候，全量拉是更正确的工程选择**，不是偷懒。真涨到几万行（比如每个租户一个池），再补 `version` 或按主键游标分页。
- **`update_date` 只给人看，不做同步水位**。`ON UPDATE CURRENT_TIMESTAMP` 秒级精度，同一秒改两行就分不出先后；主从延迟时 `WHERE update_date > ?` 还会漏。用它做水位是这类设计最经典的坑。
- **`min_pool_size` 是防手滑的**。核心线程数可以由自动伸缩或人工调整，但不能低于它——一次压测后缩容，有人把 `core` 填成 4，第二天早上业务就排队了。
- **`adjust_size` 是单次调整步长，不是调整量**。它让「16 → 48」这个变更变成 4 次、每次 +8 的渐进过程，监控上能看到每个台阶的队列水位和下游 RT。一次跳满的问题不是线程建不出来，而是**你失去了观察窗口**：真出问题时已经 48 个线程在压下游了。
- **`pool_function` 只存描述，不参与逻辑**。值班看到「代发批量分片处理」比看到 `pay-batch-shard` 更容易判断该不该调；它不进任何判断分支，所以可以不严谨。

### 三、守护线程怎么把配置刷进内存

刷新器做三件事：**启动时加载、运行期轮询、关闭时先停**。三个时机都比方法体本身重要。

```java
@Component
public class PoolConfigRefresher implements SmartInitializingSingleton, SmartLifecycle {

    private static final Logger log = LoggerFactory.getLogger(PoolConfigRefresher.class);
    private static final long INTERVAL = 5;

    private final JdbcTemplate jdbc;
    private final DynamicPoolRegistry registry;   // "application:pool" -> 池实例
    /** 已下发到位的目标配置，key 与 registry 一致 */
    private final Map<String, PoolConfig> applied = new ConcurrentHashMap<>();

    private ScheduledExecutorService scheduler;

    /** 首轮：所有单例创建完、端口还没开始监听时加载，读不到就直接启动失败 */
    @Override
    public void afterSingletonsInstantiated() {
        load(true);
    }

    @Override
    public void start() {
        scheduler = Executors.newSingleThreadScheduledExecutor(r -> {
            Thread t = new Thread(r, "pool-config-refresher");
            t.setDaemon(true);          // 不阻止 JVM 退出，也不会在数据源关掉之后醒来
            return t;
        });
        // fixedDelay：上一次跑完再等 5 秒，库慢的时候任务不会堆积
        scheduler.scheduleWithFixedDelay(() -> load(false), INTERVAL, INTERVAL, TimeUnit.SECONDS);
    }

    /** phase 大于数据源：先停刷新线程，再让容器去关连接池 */
    @Override public int getPhase() { return Integer.MAX_VALUE - 1000; }
    @Override public boolean isRunning() { return scheduler != null; }

    @Override
    public void stop() {
        if (scheduler != null) {
            scheduler.shutdownNow();
            scheduler = null;
        }
    }

    private void load(boolean failFast) {
        List<PoolConfig> rows;
        try {
            rows = jdbc.query("SELECT * FROM t_dynamic_thread_pool_config", POOL_CONFIG_MAPPER);
        } catch (Exception e) {
            if (failFast) {
                throw new IllegalStateException("首轮加载线程池配置失败，拒绝启动", e);
            }
            log.warn("load pool config failed, keep current values", e);
            return;                                  // 库挂了沿用内存值，不重建线程池
        }
        for (PoolConfig cfg : rows) {
            try {
                apply(cfg);
            } catch (Exception e) {                  // 一条配错不该让整轮停摆
                log.error("apply failed: {}", cfg.key(), e);
            }
        }
    }

    private void apply(PoolConfig cfg) {
        String key = cfg.key();                      // "pay-settle:recon-file"
        DynamicPool pool = registry.get(key);
        if (pool == null) {
            log.warn("配置表里有本实例不存在的池子，跳过: {}", key);
            return;
        }
        // 没有 version，就用整行字段当指纹：全等说明这轮没变化，一个 setter 都不用调
        if (cfg.equals(applied.get(key))) {
            return;
        }
        cfg.validate();                              // core/max/min/queue 关系 + 硬上限

        ThreadPoolExecutor p = pool.executor();
        int core = approach(p.getCorePoolSize(), cfg.getCorePoolSize(), cfg.getAdjustSize());
        int max  = approach(p.getMaximumPoolSize(), cfg.getMaxPoolSize(), cfg.getAdjustSize());

        if (max >= p.getCorePoolSize()) {            // 保证任何中间态都满足 core ≤ max
            p.setMaximumPoolSize(max);
            p.setCorePoolSize(core);
        } else {
            p.setCorePoolSize(core);
            p.setMaximumPoolSize(max);
        }

        if (p.getQueue() instanceof CapacityAdjustable) {
            ((CapacityAdjustable) p.getQueue()).setCapacity(cfg.getQueueCapacity());
        }
        p.setKeepAliveTime(cfg.getKeepAliveSeconds(), TimeUnit.SECONDS);

        boolean arrived = core == cfg.getCorePoolSize() && max == cfg.getMaxPoolSize();
        if (arrived) {
            applied.put(key, cfg);                   // 到位才记指纹，没到位下轮接着走
        }
        log.info("pool {} core {}/{} max {}/{} queue {} {}", key,
                core, cfg.getCorePoolSize(), max, cfg.getMaxPoolSize(),
                p.getQueue().size(), arrived ? "已到位" : "继续逼近");
    }

    /** 一次只走 adjust_size 步：扩容过程看得见，也给下游留反应时间 */
    private static int approach(int current, int target, int step) {
        if (current == target) return target;
        int d = Math.max(1, step);
        return target > current ? Math.min(target, current + d) : Math.max(target, current - d);
    }
}
```

**为什么是守护线程。** 刷新线程不该影响进程的生死：它只是个后台轮询，业务线程（线程池里的 Worker）是非 daemon 的，该活着还活着。反过来，如果它是非 daemon 线程，容器关了它还在跑，JVM 就不退出——**而且它会在数据源关闭之后醒来查库**，日志里冒出一串 `HikariDataSource has been closed`，把一次正常的停机变成一次看起来像故障的停机。所以三件事一起做：`setDaemon(true)`、`stop()` 里主动 `shutdownNow()`、`getPhase()` 设成比数据源大（phase 大的先停）。

**为什么首轮放在 `afterSingletonsInstantiated`。** 它晚于所有单例创建、早于 Web 端口监听。放在 `@PostConstruct` 里，其他池子可能还没注册进来；放在 `ApplicationRunner` 里，端口已经开始接流量，第一批请求会撞上「池子还是默认参数」甚至「池子还没建」。这条和守护线程那张卡里讲的启动时序是同一个结论。

**`ScheduledExecutorService` 有一个静默失败。** 任务抛出未捕获异常时，后续调度会被**静默取消**，日志里只有第一次的堆栈，看起来「定时任务只跑了一次就再没动过」。所以 `load()` 必须自己把所有异常吃掉——外层一次 `try-catch` 兜数据库，内层每行一次 `try-catch` 兜单条配置。

### 四、管理页面：只写表，不碰内存

页面本身很轻，重要的是它**不直接调 setter**。

```java
@RestController
@RequestMapping("/admin/thread-pools")
public class PoolConfigController {

    @GetMapping
    public List<PoolView> list(@RequestParam(required = false) String application) { ... }

    @PostMapping("/{application}/{pool}/adjust")
    public AdjustResult adjust(@PathVariable String application,
                               @PathVariable String pool,
                               @RequestBody AdjustRequest req,
                               @RequestHeader("X-Operator") String operator) {
        configService.adjust(application, pool, req, operator);
        return AdjustResult.of("已提交，%d 秒内分批生效", 5 * req.stepsToTarget());
    }
}
```

服务层只做三件事：加锁读旧值、校验新值、写表 + 写审计。

```java
@Transactional
public void adjust(String app, String pool, AdjustRequest req, String operator) {
    PoolConfig old = repo.lockByKey(app, pool);       // SELECT ... FOR UPDATE，挡住并发改同一个池
    PoolConfig now = old.merge(req);                  // 只覆盖请求里出现的字段
    now.validate(limits);                             // 与刷新器共用同一份校验规则
    repo.update(now);
    auditRepo.insert(old, now, operator, req.getReason());
}
```

页面上该显示什么，比有哪些输入框更值得想。四列信息，每列对应一个判断：

| 列 | 内容 | 用来判断什么 |
|---|---|---|
| 现状 | `poolSize / activeCount / queue.size / 队列容量 / 每分钟拒绝数` | 该不该改，改哪个参数 |
| 目标 | 表里的 `core / max / queue` | 上一轮改的是什么 |
| 实际 | 内存里的 `getCorePoolSize()` 等实时值 | **是不是真生效了**，还差几步 |
| 历史 | 审计表最近 5 条（谁、何时、原因） | 为什么变过，要不要回滚 |

「目标」和「实际」两列必须分开显示。只显示配置值时，一旦某个池没注册进 `registry`（拼错了 `pool_name`），页面看起来一切正常，实际一点没变；两列并排，差一步没到位也能一眼看出来。

写权限按池子分级：普通池子值班可改，金额相关（代发、清结算）要求双人确认，单次幅度超 50% 走审批。这些都落在 `adjust` 方法里，不是靠页面上把按钮置灰——按钮能绕过，接口绕不过。

**为什么坚持「页面只写表」。** 如果页面直接调 `setCorePoolSize`，表里还是旧值，就出现了两套状态：这一小时跑得好好的，下次发布重启回到旧值，值班以为「改的丢了」。而且这时 DBA 用 SQL 改表，还会被内存里的旧值覆盖。**一个池子只能有一个真相来源**，就是这张表。

### 五、队列容量：唯一改不动的参数

`LinkedBlockingQueue` 的 `capacity` 是 `final`，构造完就锁死。要让它可调，两条路，**区别在「能不能往大调」**。

**路 1：继承 + 自己判断（只能调小）**

```java
/** 只能缩、不能扩：super(capacity) 里的 capacity 是硬上限，扩容无效 */
public class ShrinkableLinkedBlockingQueue<E> extends LinkedBlockingQueue<E> {
    private volatile int capacity;

    public ShrinkableLinkedBlockingQueue(int capacity) {
        super(capacity);                 // 父类的 capacity 是 final，钉死在这里
        this.capacity = capacity;
    }

    @Override
    public boolean offer(E e) {
        if (size() >= capacity) return false;   // 先用可变容量卡一道
        return super.offer(e);                  // 再走父类（父类按旧容量判断）
    }

    public void setCapacity(int c) {     // 自定义方法，不是重写，不能加 @Override
        if (c > remainingCapacity() + size()) {
            throw new IllegalArgumentException("超出父类硬上限，调不大");
        }
        this.capacity = c;
    }
}
```

这条路能用的前提是「只往小调」——大促前调小队列来提前拒绝，是常见需求；但反过来想在大促前**放宽**队列就不行了，`super.offer` 会在旧容量处直接返回 `false`。另外 `put()` 走的是父类的等待逻辑，也得同样重写，否则阻塞路径仍按老容量走。

**路 2：把 `capacity` 变成 `volatile`（可扩可缩，生产选这个）**

思路是把 `LinkedBlockingQueue` 的源码抄一份，只改一个地方：把 `private final int capacity` 改成 `private volatile int capacity`，再补一个 `setCapacity`。`offer` / `put` / `remainingCapacity` 全部原样保留，因为它们本来就在读这个字段。

开源实现里，Hippo4j 的 `VariableLinkedBlockingQueue`、Dynamic-TP 的 `TaskQueue` 都是这个做法。代价是要维护一份 JDK 类的拷贝，JDK 升级时得跟着对一遍。

两个实现都实现同一个接口，刷新器就不用关心具体类型：

```java
public interface CapacityAdjustable {
    void setCapacity(int capacity);
}
```

**为什么非改不可**：队列容量是线程池里最影响「积压还是拒绝」的参数。前面「七个参数」那篇说过，无界队列会让 `max` 失效；同样地，队列开小了会拒绝、开大了会积压。这个数在大促前后差好几倍，改不了就等于动态线程池只做了一半。

### 六、安全阀：动态调参是「线上改代码」，必须有刹车

| 闸门 | 规则 | 作用 |
|---|---|---|
| 关系校验 | `min ≤ core ≤ max`，`queue ≥ 0`，步长 ≥ 1 | 挡住写错的配置 |
| 硬上限 | `core ≤ 256`、`max ≤ 512`、`queue ≤ 100000` | 挡住「手滑多打一个零」 |
| 幅度限制 | 单次变更超 ±50% 要求审批或二次确认 | 挡住「一把梭」 |
| 变更审计 | 写 `t_dynamic_thread_pool_log`，必须填原因 | 出事能查谁改的、为什么改 |
| 一键回滚 | 把 `before_value` 写回，再记一条审计 | 30 秒内恢复 |
| 生效观察 | 变更后 1 分钟内看拒绝数、队列水位、下游 RT | 发现「改了更糟」 |

校验放在**服务端且只有一份**：页面调用和刷新器调用同一个 `validate()`。页面校验是体验，服务端校验才是防线——有人直接跑 SQL 改表，刷新器也得拦得住。

## 为什么这么设计

**为什么落 DB，不落配置中心？** 内网环境里引入 Nacos / Apollo 要走采购和运维审批，而 DB 是现成的；DBA 改一行 SQL 就能救火，不需要懂配置中心的命名空间；DB 天然可审计、可回滚、可写 `WHERE` 条件批量改。代价是**没有推送**，只能轮询，延迟 5 秒起。

**为什么轮询，不搞推送？** 轮询的代码是 30 行，没有长连接、没有客户端 SDK、不怕网络抖动、断线重连这些都不存在。线程数这种「软参数」延迟几秒完全无感。代价是**每个实例每 5 秒查一次库**——50 个实例就是 10 QPS，对配置表这种小表可以忽略，但如果实例上千就要调大间隔或加本地缓存。

**为什么表里不加 `version`？** 因为增量同步的收益在这里是零。一个组几个服务、每个服务几个池，这张表几十行、几个月才改几次，全量拉的带宽和耗时都可以忽略；换来的是**没有水位可错**——不存在同秒多条只拉到一条、主从延迟导致水位倒退、实例间水位不一致这些事。判断依据不是「哪个方案更高级」，是「数据量和变更频率撑不撑得起增量方案的复杂度」。真到了几万行再补。

**为什么是「按步长逼近」而不是「直接设成目标值」？** `16 → 48` 一次跳过去，线程在 1 秒内建完，下游压力瞬间翻三倍，而你看到监控异常时已经晚了。分 4 步、每步间隔一个刷新周期，等于强制留出三个观察点：第一步之后下游 RT 有没有抬头、队列有没有回落、拒绝数是不是停了。**把一次不可逆的变更拆成几个可中断的小步**，这是所有线上变更都该遵守的规则，不只是线程池。

**为什么不用 Hippo4j / Dynamic-TP？** 它们功能更全（自带看板、告警、变更历史），但要多部署一个 server、多一套账号权限、多一份升级维护。自研几百行能嵌进现有的告警和审批体系，出问题自己看得懂。代价是**没有现成的看板**，得自己写页面。

**这套设计的固有代价**：多实例之间最多差一个轮询周期（5 秒），这段时间里两台机器线程数不一样。对线程池来说这是可接受的——线程数是「软约束」，差 5 秒不会造成数据问题，只会让监控曲线有个台阶。

## 不用会怎么样

- **调参 = 发版**：账期前发现线程数不够，走发布流程要 30 分钟，期间队列一直在涨。更糟的是**发版本身有风险**——重启会丢掉队列里没跑的任务，本来只是「慢」，重启变成「丢」。
- **参数写死在 `@Bean` 里**：每次调整都要改代码、过评审、全量发布。久而久之没人愿意调，池子要么长期偏小（扛不住），要么长期偏大（浪费资源、打爆下游）。
- **只敢调大不敢调小**：扩容要发版，缩容也要发版，于是按峰值配置常年挂着，DB 连接池被这些空闲线程占着。
- 真实场景：某支付公司清结算夜间对账，8 线程硬编码，账期日积压 40 万笔，值班同学想改发现只能重启，重启又怕丢任务，最后是临时挂了台机器分担分片——**动态线程池要解决的就是这种「明明知道该改哪个数，却改不了」的场面**。

## 替代方案

| 方案 | 适用 | 代价 / 风险 |
|---|---|---|
| **DB 表 + 守护线程轮询**（本篇） | 已有 DB、要审计、不能加中间件 | 秒级延迟、每实例周期性查库 |
| 配置中心 + 监听回调 | 团队已有 Nacos / Apollo | 多一套依赖；回调要自己做防抖（一次发布可能触发多次） |
| Hippo4j / Dynamic-TP | 想开箱即用、要可视化看板 | 部署 server、版本与 Spring Boot 绑定、内网适配 |
| Arthas `ognl` 临时改 | 排障时救急 | 不持久，重启即失效，容易忘记改回去 |
| 滚动发布改环境变量 | 一年调一两次 | 慢、有风险，本质还是发版 |
| 不做，靠容量规划留足余量 | 流量平稳、可预测 | 成本高，且应对不了突发 |

## 线上是怎么用的：三个场景

### 场景一：账期日，队列水位打到 1800

某银行代发批量，账期日早上 09:12。调度在 09:05 开始灌分片任务，池子配置是 `core 16 / max 32 / queue 2000`，拒绝策略 `CallerRunsPolicy`。

09:12 监控告警：队列水位 1800，三分钟内拒绝 47 次。值班打开管理页面，四列数据摆在一起就很清楚了——「现状」里队列 1800/2000、活跃线程 16，「目标」还是 16/32/2000，「实际」也是 16，说明**这个池子已经顶到核心线程数在硬扛，队列快满，扩 core 是有效的**。

他在页面把 `core` 填成 32、`queue_capacity` 填成 3000，原因写「账期日积压，队列 1800/2000」。提交后页面提示「预计 10 秒后生效，2 步到位」——`adjust_size` 是 8，16 到 32 要走两个刷新周期。日志里因此有两条，中间隔 5 秒：

```text
pool pay-settle:daifu-batch core 24/32 max 32/32 queue 1800 继续逼近
pool pay-settle:daifu-batch core 32/32 max 32/32 queue 1520 已到位
```

09:40 队列回落到 600。

有两点当时是特意确认过的：

- **47 次拒绝没有丢任务**。拒绝策略是 `CallerRuns`，被拒的任务由调度线程自己跑，提交速度自然降到处理速度，那 47 次其实是「调度线程亲自下场」。如果这里配的是 `Abort`，3 分钟丢 47 个分片，事后要人工补——**同一个拒绝数，在不同策略下是完全不同的事故等级**。
- **队列没有跟着翻倍**。有人提议 `queue_capacity` 一并加到 4000，最后只加到 3000：队列是缓冲不是产能，加太深只会把积压藏起来，真正该加的是线程。这次 `core` 敢一次走到 32，是因为这个池的下游是行内系统、RT 稳定在 20ms 左右；换成外部渠道就不会这么干（见场景二）。

第二天上午账期跑完，页面上点「按审计记录回滚」，`core` 回到 16、队列回到 2000，审计表里两条记录一前一后，谁在什么时候扩的、什么时候缩的、原因写的什么，全查得到。

### 场景二：大促前，把压测算出来的数落到表里

某跨境电商支付中台的回调处理池。压测结论：12000 TPS 时 `queue 5000` 在 30 秒内打满，之后开始拒绝。按下游渠道限流 800 TPS、单笔平均 60ms 算，理论上 48 个线程刚好打满配额。

但没人敢一次把 `core` 从 32 改到 48——渠道那边 RT 一直是 50~70ms 之间飘，一次加 16 个线程压上去，很可能把 RT 推到 100ms 以上，然后触发渠道自己的熔断。

最后落到表里的不是「48」，是这么一组值：

| 字段 | 值 | 为什么 |
|---|---|---|
| `min_pool_size` | 24 | 大促结束后缩容，最低不低于这个数，防止有人填 4 |
| `core_pool_size` | 48 | 算出来的目标值 |
| `adjust_size` | 8 | 每个刷新周期最多走 8 个线程，48 需要 4 个周期 ≈ 20 秒 |
| `queue_capacity` | 12000 | 队列和线程要一起加，只加线程等于让队列更快填满 |

改完之后值班盯的不是线程数，是**渠道 RT 和本池的拒绝数**：走到 40 的时候 RT 从 60ms 涨到 78ms，于是在页面上把 `core` 目标临时改成 40，刷新器走到 40 就停了，不再继续。大促当天这个值一直保持 40，拒绝数 0。

这个例子说明 `adjust_size` 的另一层价值：**它让「改到一半发现不对」成为可行操作**。如果一步到位到 48，中途没有停下来的机会。

### 场景三：一次缩容把拒绝数打上去了

大促结束第三天，把回调池的 `queue_capacity` 从 12000 改回 5000，想把内存还回去。改完 10 分钟，拒绝数从 0 涨到每分钟 300 多。

原因不是线程不够——**队列缩容只影响新任务，已经排队的 11000 个任务一个都不会消失**。`queue.size()` 还是 11000，`offer` 在 `size() >= 5000` 处直接返回 false，于是所有新任务立刻被拒。真正堆在队列里的那 11000 个任务还在按原速消费，缩容没有让它们变快，只是让新任务进不来了。

后来补了两条规则，写进管理页面的校验里：

- **队列缩容单次不超过 30%**，12000 → 8400 → 5900 分三步；
- **只在队列水位低于 20% 时才允许缩容**，`queue.size() > capacity * 0.2` 直接拒绝提交，提示「先等积压消化」。

这两条规则都不是「技术限制」，是**用规则把踩过的坑封住**。动态调参最危险的地方在于它太好用：点一下就生效，点错了也是点一下就生效。

顺带说一个「不自动化」的决定：清结算夜间对账池白天 `core 4`、夜间 `core 16`，这个切换**没有写定时任务**，是值班表里的一条待办。因为工作日和节假日的跑批时间不同，定时任务在节假日会按时触发、在对账文件还没到的时候把线程拉满，然后空转到早上。**能用一条有上下文的待办解决的，别写成没有上下文的定时任务。**

## 常见陷阱

- **「假动态」**：表里加了 `queue_capacity` 字段，代码还是 `new LinkedBlockingQueue(1000)`，改了没反应。这是最常见的一种，面试里说出来反而加分——说明真做过。
- **刷新任务抛异常不捕获**：`ScheduledExecutorService` 遇到未捕获异常会**静默取消后续调度**，表现是「定时任务只跑了一次」。日志里只有第一次的堆栈，很容易误判成「配置没改」。
- **守护线程没设 daemon、关停时没 shutdown**：容器关闭后它还在跑，且在数据源关闭之后查库，日志里一串 `HikariDataSource has been closed`，正常停机看起来像故障。
- **首轮加载放太晚**：塞在 `ApplicationRunner` 里，端口已经开始接流量，第一批请求撞上还没建好的池子。应该放 `afterSingletonsInstantiated`，并且读不到配置就启动失败。
- **页面直接调 setter**：内存改了、表没改，下次重启回到旧值；或者 DBA 改表被内存旧值覆盖。两套状态一定会出问题。
- **队列缩容把拒绝数打上去**：已经排队的任务不会因为容量改小就消失，`size()` 仍然大于新容量，新任务全部被拒。缩容必须等水位降下来、并且分批。
- **只改 `core` 不改 `max`**：`core` 调到 64 但 `max` 还是 32，`setMaximumPoolSize` 那步会抛 `IllegalArgumentException`；反过来 `max < core` 的配置写进表里，刷新器直接抛异常，如果不 catch 会让整个刷新停摆。
- **`adjust_size` 填 0 或负数**：走到 `approach` 里 `Math.max(1, step)` 才兜住，但如果校验没拦住，日志会显示「一步都没走」而目标永远到不了，看起来像线程池卡住了。
- **没有本地兜底**：DB 抖动时把所有池重置成默认值，配置服务的 1 秒故障放大成业务 1 分钟的抖动。
- **`fixedRate` + 慢查询**：调度任务自己堆积，日志里一堆 `refresh` 并发执行。
- **调小 `core` 以为立刻回收**：`allowCoreThreadTimeOut` 默认 false，核心线程永远不会退，`getPoolSize()` 一直显示旧值，于是「再调小一点」，越调越乱。
- **`max` 调到几千**：线程创建要走内核，`-Xss1M` 的话 2000 线程就是 2GB 栈内存，直接 `unable to create new native thread`；就算创建成功，下游 DB 连接池也就 50 个连接，多出来的线程全在等连接。
- **面试官会接着问**：「多实例之间配置不一致的那 5 秒，会不会有问题？」——要答「线程数是软约束，这 5 秒只是各实例处理能力不同，任务分配本来就不均；真正不能容忍不一致的是『钱相关的开关』，那种要走配置中心 + 强一致，不是线程池这个量级。」

## 三层追问

1. **是什么**：动态线程池的技术本质是什么？
   把「参数」从进程内存里的 `volatile int` 搬到外部存储，再通过一个轮询器把变化同步回来。JDK 早就留了 setter，缺的只是「配置的外部化和分发」，所以它本质是一个**配置分发问题**，不是并发问题。
2. **为什么这么设计**：为什么不做成「实时推送 + 强一致」？
   因为收益不匹配成本。线程数调错最多是慢一点或浪费一点，不会造成资金错账；为它引入长连接、选举、一致性协议，复杂度远超收益。**按参数的重要程度选一致性级别**，这是这套设计的核心判断。
3. **不用会怎么样**：如果只能靠发版调参，实际会发生什么？
   调参会变成一件「有风险的事」，于是没人愿意做。池子按峰值配、常年偏大，或者按均值配、遇到峰值就积压。最坏的情况是故障当时明明知道该改哪个数，却因为要发版而只能重启——重启还会丢掉队列里的任务，把小故障放大成大故障。
