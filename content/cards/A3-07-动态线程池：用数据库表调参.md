## 30 秒简述

动态线程池 = 把线程池参数从「启动时固定」变成「运行时可改」。**核心不是调参 API**（JDK 本来就有 `setCorePoolSize`），而是三件事：

1. **配置存哪**：一张配置表 + 一张审计表，`version` 单调递增；
2. **怎么让每个实例及时看到**：启动全量加载，运行期每 5 秒按 `version` 拉增量；
3. **改完哪些真生效**：`core` / `max` / `keepAlive` / 拒绝策略能改，**队列容量改不了**（`LinkedBlockingQueue.capacity` 是 `final`），必须换成自定义的可变容量队列。

最大的坑不是「怎么改」，而是「以为改了」：表里字段改了、代码还是 `new LinkedBlockingQueue(1000)`，配置就是个装饰。

## 是什么

### 一、JDK 给了哪些口子，边界在哪

| 参数 | 有 setter 吗 | 改大的效果 | 改小的效果 |
|---|---|---|---|
| `corePoolSize` | ✓ `setCorePoolSize` | **立刻补线程**（内部 `addWorker` 补齐差值） | 不立刻回收，空闲线程到 `keepAlive` 才退；核心线程要开 `allowCoreThreadTimeOut` 才退 |
| `maximumPoolSize` | ✓ `setMaximumPoolSize` | 立刻，但只在下次「队列满扩容」判断时体现 | 正在跑的线程不受影响，只影响后续判断 |
| `keepAliveTime` | ✓ `setKeepAliveTime` | 立刻 | 已经在 `poll(timeout)` 里等待的线程仍按旧值醒来 |
| `RejectedExecutionHandler` | ✓ `setRejectedExecutionHandler` | 立刻 | 立刻，但对队列里已排队的任务无效 |
| `threadFactory` | ✗ 无 setter | — | 线程名在创建时定死，改不了 |
| `workQueue` 容量 | ✗ 无 setter | — | `capacity` 是 `final`，见下面「可变容量队列」 |
| `allowCoreThreadTimeOut` | ✓ | 立刻 | 立刻 |

两个必须记住的实现细节：

**1）`core ≤ max` 这个不变式会抛异常，所以改的顺序有讲究。**

```java
// setMaximumPoolSize 里有校验：maximumPoolSize < corePoolSize 直接抛 IllegalArgumentException
// 所以调大时：先 max、后 core；调小时：先 core、后 max —— 保证任何中间态都合法
if (targetMax > targetCore) {
    p.setMaximumPoolSize(targetMax);
    p.setCorePoolSize(targetCore);
} else {
    p.setCorePoolSize(targetCore);
    p.setMaximumPoolSize(targetMax);
}
```

顺序写反了会抛异常，而且**异常只发生在调小 max 的那一次**，测试环境线程数少不一定复现。

**2）`setCorePoolSize` 调大的实现是「补线程」，不是「改个数」。** 源码里会算出 `delta = corePoolSize - workerCount`，然后循环 `addWorker(null, true)`；调小时只把字段改小，多余的线程要靠空闲超时自然退出——如果 `allowCoreThreadTimeOut=false`（默认），**这些线程永远不会退**，你以为调小了，实际只是新任务来得少了。

### 二、表怎么设计

两张表：一张配置、一张审计。配置表存当前值，审计表存「谁在什么时候把什么改成了什么」。

```sql
CREATE TABLE t_dynamic_thread_pool (
  id                 BIGINT       NOT NULL AUTO_INCREMENT,
  pool_key           VARCHAR(64)  NOT NULL COMMENT '线程池唯一标识，如 dai-fa-batch',
  pool_name          VARCHAR(128) NOT NULL COMMENT '中文名，给人看的',
  core_size          INT          NOT NULL,
  max_size           INT          NOT NULL,
  queue_capacity     INT          NOT NULL COMMENT '0 表示沿用代码里的默认值',
  keep_alive_sec     INT          NOT NULL DEFAULT 60,
  reject_policy      VARCHAR(32)  NOT NULL DEFAULT 'CALLER_RUNS',
  allow_core_timeout TINYINT      NOT NULL DEFAULT 0,
  enabled            TINYINT      NOT NULL DEFAULT 1 COMMENT '0=不下发新配置，不是销毁线程池',
  version            BIGINT       NOT NULL DEFAULT 1 COMMENT '每次修改 +1，刷新器按它做增量',
  update_by          VARCHAR(64)  NOT NULL,
  update_time        DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  remark             VARCHAR(255) DEFAULT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_pool_key (pool_key),
  KEY idx_version (version)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='线程池动态参数';

CREATE TABLE t_dynamic_thread_pool_log (
  id         BIGINT      NOT NULL AUTO_INCREMENT,
  pool_key   VARCHAR(64) NOT NULL,
  before_val JSON        NOT NULL,
  after_val  JSON        NOT NULL,
  version    BIGINT      NOT NULL,
  operator   VARCHAR(64) NOT NULL,
  created_at DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_pool (pool_key, id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='线程池参数变更审计';
```

设计上的五个取舍：

- **用 `version` 而不是 `update_time` 做增量水位**。`update_time` 有两个致命问题：同一秒内的多条变更只拉到一条；多实例时钟不一致、DB 主从延迟时水位会错乱。`version` 由 `version = version + 1` 原子递增，天然单调。
- **`enabled` 的语义是「停止下发」，不是「销毁线程池」**。停用后实例沿用最后一份配置继续跑，业务不受影响——这条语义写不清楚，运维就会拿它当「下线开关」用。
- **表里没有的 `pool_key` 不报错**，用代码里的默认值建池。配置表是「覆盖」，不是「唯一来源」，否则新增一个池要先找 DBA 插数据。
- **数值字段不加 `CHECK` 约束**（MySQL 5.7 会忽略），上下限校验放在应用侧，因为告警和审批也在应用侧。
- **审计表不存外键**。线程池可能被删，历史不能跟着没。

### 三、刷新链路

![动态线程池的刷新链路：配置表、定时刷新器、线程池实例与生效边界](img/threadpool-dynamic-link.svg)

```java
@Component
public class PoolConfigRefresher {

    private final JdbcTemplate jdbc;
    private final Map<String, ThreadPoolExecutor> registry;      // pool_key -> 实例，启动时注册
    private final Map<String, Long> localVersion = new ConcurrentHashMap<>();

    /** fixedDelay 而不是 fixedRate：上一次跑完再等 5 秒，避免 DB 慢时任务堆积 */
    @Scheduled(fixedDelay = 5_000)
    public void refresh() {
        List<PoolConfig> changed;
        try {
            changed = jdbc.query(
                "SELECT * FROM t_dynamic_thread_pool WHERE version > ? AND enabled = 1",
                ROW_MAPPER, maxLocalVersion());
        } catch (Exception e) {
            log.warn("pool config refresh failed, keep local cache", e);
            return;                                              // DB 抖动：沿用本地值，绝不重置线程池
        }
        for (PoolConfig c : changed) {
            try {
                apply(c);
                localVersion.merge(c.getPoolKey(), c.getVersion(), Math::max);
                log.info("pool config applied: {}", c);
            } catch (Exception e) {
                log.error("apply pool config failed: {}", c, e);  // 单条失败不影响其他池
            }
        }
    }

    private void apply(PoolConfig c) {
        if (!c.valid()) { throw new IllegalArgumentException("illegal config: " + c); }

        ThreadPoolExecutor p = registry.get(c.getPoolKey());
        if (p == null) { log.warn("unknown pool_key {}", c.getPoolKey()); return; }

        // 1) 先解决 core ≤ max 的中间态，再改数字
        if (c.getMaxSize() >= p.getCorePoolSize()) {
            p.setMaximumPoolSize(c.getMaxSize());
            p.setCorePoolSize(c.getCoreSize());
        } else {
            p.setCorePoolSize(c.getCoreSize());
            p.setMaximumPoolSize(c.getMaxSize());
        }

        // 2) 队列容量：只有实现了 CapacityAdjustable 的队列才改得动
        if (p.getQueue() instanceof CapacityAdjustable && c.getQueueCapacity() > 0) {
            ((CapacityAdjustable) p.getQueue()).setCapacity(c.getQueueCapacity());
        }

        p.setKeepAliveTime(c.getKeepAliveSec(), TimeUnit.SECONDS);
        p.setRejectedExecutionHandler(RejectPolicies.of(c.getRejectPolicy()));
        if (c.getAllowCoreTimeout() != p.allowsCoreThreadTimeOut()) {
            p.allowCoreThreadTimeOut(c.getAllowCoreTimeout() == 1);
        }
    }
}
```

刷新链路上有四个容易漏的点：

- **`fixedDelay` 不是 `fixedRate`**。`fixedRate` 按固定频率触发，DB 慢的时候任务会堆在调度队列里。
- **单条失败不影响其他池**：`apply` 包在 try-catch 里，一个配置写错（比如 core>max）不该让整个刷新停摆。
- **更新 `localVersion` 要取 max**：多行同时变更时，不能简单覆盖成最后一条的版本号。
- **DB 不可用时必须沿用本地缓存**。配置读不到就重置线程池，等于把「配置服务抖动」放大成「业务抖动」。

### 四、队列容量：唯一改不动的参数

`LinkedBlockingQueue` 的 `capacity` 是 `final`，构造完就锁死。要让它可调，两条路，**区别在「能不能往大调」**。

**路 1：继承 + 自己判断（只能调小）**

```java
/** 只能缩、不能扩：super(capacity) 里的 capacity 是硬上限，扩容无效 */
public class ShrinkableLinkedBlockingQueue<E> extends LinkedBlockingQueue<E> {
    private volatile int capacity;

    public ShrinkableLinkedBlockingQueue(int capacity) {
        super(capacity);                 // 父类的 capacity 是 final，钉死在这里
        this.capacity = capacity;
    }

    @Override
    public boolean offer(E e) {
        if (size() >= capacity) return false;   // 先用可变容量卡一道
        return super.offer(e);                  // 再走父类（父类按旧容量判断）
    }

    public void setCapacity(int c) {     // 自定义方法，不是重写，不能加 @Override
        if (c > remainingCapacity() + size()) {
            throw new IllegalArgumentException("超出父类硬上限，调不大");
        }
        this.capacity = c;
    }
}
```

这条路能用的前提是「只往小调」——大促前调小队列来提前拒绝，是常见需求；但反过来想在大促前**放宽**队列就不行了，`super.offer` 会在旧容量处直接返回 `false`。另外 `put()` 走的是父类的等待逻辑，也得同样重写，否则阻塞路径仍按老容量走。

**路 2：把 `capacity` 变成 `volatile`（可扩可缩，生产选这个）**

思路是把 `LinkedBlockingQueue` 的源码抄一份，只改一个地方：把 `private final int capacity` 改成 `private volatile int capacity`，再补一个 `setCapacity`。`offer` / `put` / `remainingCapacity` 全部原样保留，因为它们本来就在读这个字段。

开源实现里，Hippo4j 的 `VariableLinkedBlockingQueue`、Dynamic-TP 的 `TaskQueue` 都是这个做法。代价是要维护一份 JDK 类的拷贝，JDK 升级时得跟着对一遍。

两个实现都实现同一个接口，刷新器就不用关心具体类型：

```java
public interface CapacityAdjustable {
    void setCapacity(int capacity);
}
```

**为什么非改不可**：队列容量是线程池里最影响「积压还是拒绝」的参数。前面「七个参数」那篇说过，无界队列会让 `max` 失效；同样地，队列开小了会拒绝、开大了会积压。这个数在大促前后差好几倍，改不了就等于动态线程池只做了一半。

### 五、安全阀：动态调参是「线上改代码」，必须有刹车

| 闸门 | 规则 | 作用 |
|---|---|---|
| 关系校验 | `core ≤ max`，全部非负 | 挡住写错的配置 |
| 硬上限 | `core ≤ 256`、`max ≤ 512`、`queue ≤ 100000` | 挡住「手滑多打一个零」 |
| 幅度限制 | 单次变更超 ±50% 要求审批或二次确认 | 挡住「一把梭」 |
| 变更审计 | 写 `t_dynamic_thread_pool_log` | 出事能查谁改的 |
| 一键回滚 | 把旧值写回、`version + 1` | 30 秒内恢复 |
| 生效观察 | 变更后 1 分钟内看拒绝数、队列水位 | 发现「改了更糟」 |

## 为什么这么设计

**为什么落 DB，不落配置中心？** 内网环境里引入 Nacos / Apollo 要走采购和运维审批，而 DB 是现成的；DBA 改一行 SQL 就能救火，不需要懂配置中心的命名空间；DB 天然可审计、可回滚、可写 `WHERE` 条件批量改。代价是**没有推送**，只能轮询，延迟 5 秒起。

**为什么轮询，不搞推送？** 轮询的代码是 30 行，没有长连接、没有客户端 SDK、不怕网络抖动、断线重连这些都不存在。线程数这种「软参数」延迟几秒完全无感。代价是**每个实例每 5 秒查一次库**——50 个实例就是 10 QPS，对配置表这种小表可以忽略，但如果实例上千就要调大间隔或加本地缓存。

**为什么不用 Hippo4j / Dynamic-TP？** 它们功能更全（自带看板、告警、变更历史），但要多部署一个 server、多一套账号权限、多一份升级维护。自研几百行能嵌进现有的告警和审批体系，出问题自己看得懂。代价是**没有可视化看板**，得自己写个查询页或者直接用 SQL。

**为什么 `version` 而不是 `update_time`？** 见前面表设计。时钟和并发是这类「增量同步」最经典的两个坑，`version` 一个字段同时解掉。

**这套设计的固有代价**：多实例之间最多差一个轮询周期（5 秒），这段时间里两台机器线程数不一样。对线程池来说这是可接受的——线程数是「软约束」，差 5 秒不会造成数据问题，只会让监控曲线有个台阶。

## 不用会怎么样

- **调参 = 发版**：账期前发现线程数不够，走发布流程要 30 分钟，期间队列一直在涨。更糟的是**发版本身有风险**——重启会丢掉队列里没跑的任务，本来只是「慢」，重启变成「丢」。
- **参数写死在 `@Bean` 里**：每次调整都要改代码、过评审、全量发布。久而久之没人愿意调，池子要么长期偏小（扛不住），要么长期偏大（浪费资源、打爆下游）。
- **只敢调大不敢调小**：扩容要发版，缩容也要发版，于是按峰值配置常年挂着，DB 连接池被这些空闲线程占着。
- 真实场景：某支付公司清结算夜间对账，8 线程硬编码，账期日积压 40 万笔，值班同学想改发现只能重启，重启又怕丢任务，最后是临时挂了台机器分担分片——**动态线程池要解决的就是这种「明明知道该改哪个数，却改不了」的场面**。

## 替代方案

| 方案 | 适用 | 代价 / 风险 |
|---|---|---|
| **DB 表 + 定时轮询**（本篇） | 已有 DB、要审计、不能加中间件 | 秒级延迟、每实例周期性查库 |
| 配置中心 + 监听回调 | 团队已有 Nacos / Apollo | 多一套依赖；回调要自己做防抖（一次发布可能触发多次） |
| Hippo4j / Dynamic-TP | 想开箱即用、要可视化看板 | 部署 server、版本与 Spring Boot 绑定、内网适配 |
| Arthas `ognl` 临时改 | 排障时救急 | 不持久，重启即失效，容易忘记改回去 |
| 滚动发布改环境变量 | 一年调一两次 | 慢、有风险，本质还是发版 |
| 不做，靠容量规划留足余量 | 流量平稳、可预测 | 成本高，且应对不了突发 |

## 项目中如何使用

**某银行代发批量（账期扩容）**

- 池子 `pool_key = dai-fa-batch`，平时 `core 16 / max 32 / queue 2000`，`CallerRunsPolicy`。
- 账期日前一天，值班同学执行一条 SQL（走审批后由 DBA 执行）：

```sql
UPDATE t_dynamic_thread_pool
   SET core_size = 32, max_size = 64, queue_capacity = 4000,
       version = version + 1,
       update_by = 'oncall-zhang',
       remark = '账期日扩容，跑完回滚'
 WHERE pool_key = 'dai-fa-batch';
```

- 5 秒内三台实例全部生效，日志里能看到 `pool config applied: dai-fa-batch core 16->32`。
- 账期跑完执行回滚：把 `core_size / max_size / queue_capacity` 改回原值、`version + 1`，审计表里两条记录一前一后，谁在什么时候扩容、什么时候缩回来都查得到。

**某支付公司清结算对账**

- 白天 `core 4`，夜间 22:00 前调到 `core 16`，因为对账文件系统并发高了反而更慢，白天不需要那么多线程。
- 这个池没有用定时任务自动切，就是值班表里的一条待办：22:00 前改表，早上改回来。**能用一条待办解决的，不要写定时任务**——定时任务自己也会失效，还会在节假日误触发。

**某跨境电商支付中台的回调处理**

- 大促前 `core 32 → 64`、`queue 5000 → 20000`，同时在监控上盯 `getQueue().size()`。
- 这里必须同时改队列，否则线程加了一倍、队列还是 5000，多出来的线程只是让队列更快填满，然后更早开始拒绝。

## 常见陷阱

- **「假动态」**：表里加了 `queue_capacity` 字段，代码还是 `new LinkedBlockingQueue(1000)`，改了没反应。这是最常见的一种，面试里说出来反而加分——说明真做过。
- **只改 `core` 不改 `max`**：`core` 调到 64 但 `max` 还是 32，`setMaximumPoolSize` 那步会抛 `IllegalArgumentException`；反过来 `max < core` 的配置写进表里，刷新器直接抛异常，如果不 catch 会让整个刷新停摆。
- **用 `update_time` 做增量水位**：同秒多条变更只拉到一条，主从延迟时水位倒退，配置时好时坏。
- **没有本地兜底**：DB 抖动时把所有池重置成默认值，配置服务的 1 秒故障放大成业务 1 分钟的抖动。
- **`fixedRate` + 慢查询**：调度任务自己堆积，日志里一堆 `refresh` 并发执行。
- **调小 `core` 以为立刻回收**：`allowCoreThreadTimeOut` 默认 false，核心线程永远不会退，`getPoolSize()` 一直显示旧值，于是「再调小一点」，越调越乱。
- **`max` 调到几千**：线程创建要走内核，`-Xss1M` 的话 2000 线程就是 2GB 栈内存，直接 `unable to create new native thread`；就算创建成功，下游 DB 连接池也就 50 个连接，多出来的线程全在等连接。
- **`enabled = 0` 当成「下线」用**：以为停用会把线程池销毁，实际只是不下发新配置。真要下线得让业务方把池子摘掉。
- **面试官会接着问**：「多实例之间配置不一致的那 5 秒，会不会有问题？」——要答「线程数是软约束，这 5 秒只是各实例处理能力不同，任务分配本来就不均；真正不能容忍不一致的是『钱相关的开关』，那种要走配置中心 + 强一致，不是线程池这个量级。」

## 三层追问

1. **是什么**：动态线程池的技术本质是什么？
   把「参数」从进程内存里的 `volatile int` 搬到外部存储，再通过一个轮询器把变化同步回来。JDK 早就留了 setter，缺的只是「配置的外部化和分发」，所以它本质是一个**配置分发问题**，不是并发问题。
2. **为什么这么设计**：为什么不做成「实时推送 + 强一致」？
   因为收益不匹配成本。线程数调错最多是慢一点或浪费一点，不会造成资金错账；为它引入长连接、选举、一致性协议，复杂度远超收益。**按参数的重要程度选一致性级别**，这是这套设计的核心判断。
3. **不用会怎么样**：如果只能靠发版调参，实际会发生什么？
   调参会变成一件「有风险的事」，于是没人愿意做。池子按峰值配、常年偏大，或者按均值配、遇到峰值就积压。最坏的情况是故障当时明明知道该改哪个数，却因为要发版而只能重启——重启还会丢掉队列里的任务，把小故障放大成大故障。
