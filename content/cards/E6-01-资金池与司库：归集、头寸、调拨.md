## 30 秒简述

司库解决的是企业资金的三件事：**看得见**（多银行多账户统一视图）、**调得动**（归集与调拨）、**控得住**（额度、审批、留痕）。核心链路是「账户 → 归集 → 资金池 → 头寸 → 调拨/支付 → 回单 → 对账」六段闭环。资金池分实体池（真把子公司钱划到集团账户）和虚拟池（不动账，靠内部台账调剂），后者上线快、成本低但不满足所有合规场景。技术上最难的不是页面，是**调拨指令的异步状态机**（发出去的结果未知怎么办）和**头寸算得准不准**。

## 是什么

- **账户分层**：集团户（主办账户）→ 成员单位户 → 各银行实体账户。每个账户带用途（收款/付款/归集/费用/保证金）、余额分类（可用、冻结、在途）、所属组织与数据权限。
- **归集**：按策略把成员单位账户的钱上划到集团户。常见三种——实时归集（每笔到账即划走）、限额归集（留底 N 万，超出部分上划）、手动归集（财务发起）。反向下拨同理。
- **资金池两种形态**：
  - 实体池：真实发生银行转账，集团户余额就是池子余额，子公司账面通过内部往来记账。
  - 虚拟池：**不发生真实转账**，集团在系统内建一套内部台账，成员单位透支时内部计息，日终按净额轧差。优点是零手续费、实时调剂；缺点是不能真正透支银行账户，受监管与银行协议约束。
  - 委贷池：通过委托贷款实现资金调剂，合规要求最高，要签合同、计息、报备。
- **头寸**：`可用头寸 = 银行可用余额 + 在途收入 − 在途支出 − 冻结/保证金 − 已预约未执行`。按日、按时段（大额支付系统有清算窗口）滚动预测，供财务决定是否调拨或拆借。
- **调拨指令生命周期**：草拟 → 复核 → 审批（可多级）→ 发送银行 → 银行受理 → 成功/失败/**未知** → 回单回写 → 记账。和对外支付一样，必须区分「已受理」与「已到账」。
- **银企直连**：部分银行走前置机（装在企业内网，银行提供驱动），新一些的走 OpenAPI；报文异步，必须配查询接口与日终对账单。
- **多租户（SaaS）**：数据按租户隔离（分库或 tenant_id + 行级权限），银行密钥按租户独立托管，组织树决定可见范围。

## 为什么这么设计

企业资金天然分散在几十上百个银行账户里，靠 U 盾 + 网银 + Excel 汇总，头寸永远是昨天的。司库把「查询—决策—执行—核对」搬进一个系统，价值在于**决策时点的数据是实时的**。

虚拟池之所以存在，是因为真实归集有成本和合规摩擦（每笔跨行转账要手续费、要合同依据），而集团内部调剂本质上只是记账问题。代价是它不能解决「银行账户真的没钱」的情况——所以大集团往往是「实体池打底 + 虚拟池做日常调剂」的混合模式。

## 不用会怎么样

- 头寸看不到：一边账上趴着几千万活期，一边为支付缺口去做高息拆借，一年白扔几十万利差。
- 归集不及时：子公司账户沉淀大量资金，集团授信利用率低。
- 调拨无审批、无留痕：内控审计过不了，出现资金挪用无法追溯。
- 指令状态不做「未知态」：银行超时直接置失败，财务重新发起，结果银行两笔都成功，形成重复调拨、长款挂账。

## 替代方案

| 方案 | 适用 | 说明 / 风险 |
|---|---|---|
| 银企直连只做查询（资金视图） | 只想知道余额 | 上线最快；不能执行，仍要人工操作网银 |
| 实体资金池 | 集团管控强、成员单位配合 | 资金真实集中，利息归集；有转账成本与合规手续 |
| 虚拟资金池 | 成员单位多、日常小额调剂 | 零成本实时调剂；受监管限制，不能真透支 |
| 委贷池 | 上市公司、合规要求高 | 合规性最好；流程重，要合同与计息 |
| 司库一体化（含票据、供应链） | 大型集团 | 覆盖全；实施周期长，通常按模块分期 |

## 项目中如何使用

- **某银行财资系统**：负责账户管理、资金池、调拨与头寸模块。账户维度按「租户 → 集团 → 成员单位 → 银行账户」四级建模，余额拆可用/冻结/在途；归集策略做成可配置的规则（触发条件 + 留底金额 + 执行时段），由调度任务按租户分片执行。
- **C9→C10 重构里最实质的一块**：把调拨指令从「同步调银行接口、失败就报错」改成**异步状态机 + 查询补偿 + 日终对账**——发送后落 `PROCESSING`，超时落 `UNKNOWN`，由查证任务按退避节奏调银行查询接口，最终以日终对账单为准回写。这一改把「银行维护窗口导致的批量失败」从每天几十笔降到个位数。
- **头寸计算**：日终 + 每小时快照两套口径，快照用于实时看板，日终用于对账；在途收入按「已收款未入账」的单据推算，宁可低估不可高估——低估最多是少调拨一次，高估会导致调拨被银行退回。
- **多租户隔离**：租户级分库 + 银行密钥按租户加密托管，组织树做数据域，跨租户查询在 DAO 层强制带上 `tenant_id`，防止越权。

## 常见陷阱

- 把头寸当余额：漏掉在途、冻结、已预约，算出来的可用资金是虚的。曾经因为把保证金账户算进可用头寸，调拨指令被银行退回，当天有 3 笔对外付款延迟。
- 调拨指令不做幂等：财务手抖点两次，或者前端超时重试，银行侧收到两笔。
- 银行回单不回写：系统里显示「处理中」，实际早已到账，日终对账才发现状态漂移。
- 面试官会追问「虚拟池和实体池的区别」以及「你们为什么选这个」——要能说出合规与成本两方面的取舍，而不是只讲功能。

## 三层追问

1. **头寸怎么算准？**——分「已确定」（银行余额、已受理指令）与「预测」（在途收入、待执行付款）两部分；预测部分单独展示，不混进可用头寸；关键时点（大额支付截止前）做一次强同步查询。
2. **调拨超时了怎么办？**——和对外支付完全一致：置未知态 → 按退避查询银行 → 日终对账兜底；只有查到「银行无此指令」才允许重发，且必须带同一个业务流水号。
3. **多租户怎么保证隔离？**——连接层分库 + SQL 强制租户条件 + 密钥按租户独立托管 + 组织树数据域三层；租户之间共享的是代码和调度框架，不共享数据与凭证。
