## 30 秒版
优化慢 SQL 的标准动作：**先看执行计划（explain / explain analyze）→ 确认是没走索引、走了错索引还是回表太多 → 针对性改 SQL 或改索引**，不是先加索引。典型失效场景：函数/运算作用于索引列、隐式类型转换、前导模糊 `%x`、不满足最左前缀、`or` 连接非索引列、范围查询后的列无法用于排序、选择性过低让优化器放弃索引。

## 是什么（核心机制）
- explain 关键列：type（ALL/index/range/ref/eq_ref/const）、key、rows、filtered、Extra（Using index 覆盖 / Using filesort / Using temporary / Using index condition）。
- 优化器基于成本选索引，统计信息（基数）不准时会选错，可用 `analyze table` 或 force index 临时干预。
- 深分页 `limit 100000,20` 会扫描并丢弃 10 万行 → 改游标分页或延迟关联（先用覆盖索引拿主键再回表）。

## 为什么这么设计（权衡）
MySQL 只能在"索引列有序"的前提下做二分查找，任何对列的计算都会破坏有序性假设；优化器的成本模型是估算，所以它可能宁可不走索引（回表太多时全表扫反而快）——这不是 bug，是代价权衡。

## 不用它会怎样
单条慢 SQL 在 40 万笔/日量级会放大成连接池耗尽：慢查询占住连接 → 后续请求排队 → 接口超时 → 上游重试 → 雪崩。资金类系统还会引发对账任务延迟。

## 替代方案对比
| 手段 | 场景 | 注意 |
|---|---|---|
| 加联合索引/覆盖索引 | 高频固定查询 | 控制索引数量 |
| 改写 SQL（拆分 or、去函数） | 逻辑可改 | 优先于加索引 |
| 冗余字段/结果表 | 报表与对账聚合 | 引入一致性维护成本 |
| 读写分离 + 从库查询 | 读多写少 | 主从延迟对资金类不可接受，需强一致场景回主库 |

## 项目里怎么用（陈聪）
- 对账明细查询原来按 `date_format(create_time,'%Y-%m-%d')` 过滤导致索引失效，改成时间范围区间查询后走 range。
- 清算人员按"渠道 + 状态 + 日期"翻页深分页，改为按自增 ID 游标翻页。
- 交易流水表曾因 `varchar` 字段传数字导致隐式转换失效，统一在 DAO 层做类型校验。

## 三层追问
1. 为什么函数会导致失效？——B+ 树按列值排序，函数后每行都要计算，无法二分。
2. 索引区分度多低就不该建？——一般选择性 < 10%（如性别）不适合单独建索引，除非配合其他列做联合索引。
3. 加了索引反而变慢是什么情况？——写多读少、回表比例高、优化器选错索引、索引太多导致 buffer pool 命中率下降。

## 常见陷阱
- 一遇慢查询就说"加索引"，不问是读慢还是写慢。
- 不知道 `Using filesort` 与 `Using temporary` 的含义。
