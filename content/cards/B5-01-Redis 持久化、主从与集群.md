## 30 秒简述

结论：Redis 的可靠性由持久化、复制、集群三块拼起来，但**真正打垮线上 Redis 的通常不是这三样，而是大 key 和热 key**。持久化决定单机重启丢多少：**RDB 恢复快，可能丢分钟级；AOF everysec 最多丢 1 秒**，但要扛 rewrite。**复制是异步的，主库挂了天然可能丢最后一段**，所以幂等键这类数据不能只放 Redis，必须有 DB 兜底。集群解决容量和故障转移：哨兵做主从切换，Cluster 用 16384 个 slot 分片。大 key 的危害是 `DEL` 同步释放内存、阻塞主线程；热 key 则是把单个分片的 CPU 和网卡打满。一个 8MB 的对账结果 DEL 阻塞 200 毫秒就够拖垮上游。

## 是什么

**持久化**

- RDB：`bgsave` fork 子进程写快照，靠写时复制（COW）不阻塞主线程；优点是文件小、恢复快，缺点是两次快照之间的数据全丢，且 fork 瞬间内存可能翻倍。
- AOF：追加写命令，`appendfsync` 三档——`always`（每条 fsync，最安全最慢）、`everysec`（每秒，默认，最多丢 1 秒）、`no`（交给 OS）。
- AOF rewrite：`bgrewriteaof` 另起子进程按当前数据重写最小命令集；rewrite 期间新写入同时进 `aof_buf` 和重写缓冲，避免丢命令。
- 混合持久化（4.0+）：`aof-use-rdb-preamble yes`，AOF 文件前半段是 RDB 格式、后半段是增量命令，兼顾恢复速度与丢数据窗口。

**复制**

- 全量同步：从库发 `psync`，主库 `bgsave` 生成 RDB 传过去，期间的写命令进 `repl_backlog` 补发；之后走增量，靠 `offset` 续传。
- 复制是**异步**的：主库写成功即返回客户端，数据还没到从库；主库宕机，这段数据就丢了。可用 `min-replicas-to-write` 限制「至少 N 个从库确认才允许写」，代价是可用性下降。

**哨兵与集群**

- 哨兵：监控 + 主观下线（单哨兵判定）/ 客观下线（quorum 个哨兵认同）+ 选举 Leader 执行故障转移，客户端向哨兵要新主地址。切换期间有秒级不可用；老主恢复后若仍接写会产生脑裂，靠 `min-replicas` 与重启后降级为从库来收敛。
- Cluster：16384 个 slot，`CRC16(key) % 16384`，每个主负责一段；客户端访问错节点收到 `MOVED`（永久重定向）或 `ASK`（slot 迁移中临时重定向）；无中心节点，靠 gossip 传播状态。

**大 key / 热 key**

- 大 key：单个 value 过大（几十 MB）或集合元素过多（十万级）。危害：网络阻塞、`DEL` 同步释放内存阻塞主线程、Cluster 下分片倾斜、迁移卡住。
- 热 key：单个 key 的 QPS 远超其他。危害：单个分片 CPU/网卡打满，整个集群跟着抖。
- 治理手段：大 key → 拆分成多个小 key、用 `UNLINK` 异步删除、`HSCAN` 渐进清理；热 key → 本地缓存兜底、key 加随机后缀打散到多分片、读写分离走从库、`--hotkeys` 或采样 `MONITOR` 做热点探测。

## 为什么这么设计

单线程模型换来了无锁与可预测的延迟，代价是**任何阻塞操作都会拖垮全局**，所以持久化必须 fork 子进程、删除大 key 必须异步。

复制选择异步而不是同步，是拿「可能丢最后一段数据」换吞吐与可用性；要强一致就得上 WAIT 或换别的存储，成本和延迟都不是缓存层能接受的。Cluster 用固定 slot 而不是一致性哈希，是为了让映射关系确定、迁移有明确单位、客户端能缓存路由表。

## 不用会怎么样

- 只开 RDB 且间隔 5 分钟：宕机丢 5 分钟写入。如果幂等键存在 Redis 里，重启后同一笔请求被当成新请求，**直接重复支付**。
- 关掉持久化当纯缓存，却把分布式锁、幂等键、验证码也放进去：重启后锁全丢，并发控制失效。
- 单机不集群：内存到上限只能垂直扩，主库挂了业务全停，故障恢复靠人。
- 大 key 用 `DEL` 删：主线程阻塞几百毫秒到数秒，所有请求排队超时，监控上表现为「Redis 抖动 → 上游线程池打满 → 雪崩」。

## 替代方案

| 方案 | 适用 | 说明 / 风险 |
|---|---|---|
| 纯缓存（不开持久化） | 丢了能回源重建 | 最快最简单；绝不能放锁/幂等键 |
| RDB + AOF 混合 | 绝大多数生产环境 | 推荐默认；注意 rewrite 时的磁盘与 fork 开销 |
| 主从 + 哨兵 | 单机内存够、只要高可用 | 运维简单；切换有秒级中断，容量仍受单机限制 |
| Redis Cluster | 数据量大、需要水平扩展 | 客户端要支持集群；跨 slot 的 `mget`/事务/Lua 受限 |
| 本地缓存 + Redis 两级 | 极热数据、容忍短暂不一致 | 扛住热 key；多实例间一致性要额外处理 |

## 项目中如何使用

- **某银行幂等键**：`pay:idem:{商户号}:{请求号}`，`SET NX EX 24h`，同时落一张 DB 幂等表做兜底——**Redis 只做第一道闸，DB 唯一索引才是最终保证**，这样即使 Redis 丢数据也不会重复支付。
- **某跨境电商多租户缓存**：key 统一 `t{tenantId}:biz:key`，Cluster 下用 hash tag 保证同一租户的相关 key 落同一 slot，批量操作不会跨 slot 报错；租户级缓存整体过期靠 TTL + 主动清理双保险。
- **某支付公司渠道配置热更新**：配置变更走 pub/sub 广播，各实例收到后重建本地 `ConcurrentHashMap` 副本，Redis 只作为分发通道，不承担读流量。
- **两次真实故障**：① 某个大商户的费率 key 变成热 key，单分片 CPU 打到 100%，用了「本地 Caffeine 缓存 + key 加随机后缀打散到 8 个分片」压下去；② 对账结果按天塞进一个 String，涨到 8MB，定时任务 `DEL` 时主线程阻塞约 200ms，改成 Hash 按商户拆 + `UNLINK` 异步删。

## 常见陷阱

- 在生产上执行 `KEYS *` 或 `FLUSHDB`：前者阻塞主线程，后者直接清库，必须用 `SCAN`。
- 把主从当强一致：刚写完立刻读从库，读到旧值，用它做幂等判断就会放行重复请求。
- Cluster 下写跨 key 的 Lua 或事务：全部报 `CROSSSLOT`，要么加 hash tag，要么改成单 key 结构。
- 面试官会追问「AOF everysec 真的只丢 1 秒吗」：正常情况是，但主库 fsync 卡顿或磁盘满时会退化成 AOF 写失败——所以还要监控 `aof_last_write_status`。

## 三层追问

1. **RDB 的 fork 会阻塞吗？**——fork 本身要拷贝页表，内存越大耗时越长（几十 GB 实例可能几十毫秒），这期间主线程是停的；COW 之后如果写入密集，会触发大量页复制，内存可能接近翻倍。
2. **哨兵切换期间业务怎么办？**——客户端要能感知「连接被重置 → 重新向哨兵要主地址」，写请求短暂失败；重试要幂等，否则切换窗口就是重复提交窗口。
3. **热 key 为什么不能靠加从库解决？**——从库只能分担读，写热 key（如秒杀库存）依然打在主上；而且从库扩容对单分片 CPU 的缓解有限，本质要靠「打散 + 本地缓存 + 业务侧合并」。
