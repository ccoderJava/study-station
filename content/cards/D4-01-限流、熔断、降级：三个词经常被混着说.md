## 30 秒简述

三者是**不同位置的保护手段**：**限流**是入口闸门，控制「进来多少」，保护自己；**熔断**是出口开关，控制「调用下游多少」，保护自己不被下游拖死；**降级**是能力收缩，决定「资源不够时先放弃什么」，保护核心业务。一句话串起来：**先限流挡住非核心流量，再熔断切断坏掉的下游，最后降级把剩余资源让给核心链路**。顺序不能反——没有限流就熔断，等于让流量把线程池占满才发现下游挂了。

## 是什么

1. **限流算法**
   - 固定窗口：实现最简单，窗口边界有双倍突刺（59 秒 100 个、61 秒再 100 个）。
   - 滑动窗口：把窗口切成 N 个格子滚动计数，突刺变小，内存随精度增长。
   - 漏桶：恒定速率流出，绝对平滑，但不允许突发。
   - **令牌桶**：按速率放令牌，桶容量决定允许多大突发——**业务限流基本都用它**（Guava `RateLimiter`、Sentinel 的匀速/预热模式）。
2. **熔断三态**：`CLOSED`（正常放行，统计失败率）→ `OPEN`（直接拒绝，不再打下游）→ `HALF_OPEN`（放少量探针，成功则恢复，失败则继续熔断）。关键参数是**统计窗口**、**失败率阈值**、**最小请求数**（请求太少时算失败率没有统计意义）。
3. **隔离**：线程池隔离（每个下游独立线程池，慢调用不会占满全局）vs 信号量隔离（只限制并发数，开销小但不隔离线程）。Hystrix 时代偏线程池，Sentinel 偏信号量 + 并发数控制。
4. **降级**：返回兜底值（缓存快照、默认值、空列表）、关闭非核心功能（推荐位、积分、消息推送）、异步化（同步转排队）。
5. **限流的位置**：网关（全局 QPS、IP/用户维度）、应用（接口维度）、资源层（数据库连接、线程池、MQ 消费速率）。**只在一处限流是不够的**。

## 为什么这么设计

因为**容量是有限的，而流量是无界的**。系统必须在「拒绝一部分请求」和「全部请求一起变慢直至全挂」之间做选择——限流就是主动选择前者：**有损但可控，好过无损但崩塌**。

熔断的存在是因为**故障会传染**：下游 RT 从 50ms 涨到 2s，上游线程全卡在等响应，线程池打满，上游也开始超时，故障沿着调用链一路向上蔓延，直到整个集群不可用（雪崩）。熔断在检测到下游病态时**主动切断**，把故障限制在下游一个点。

降级的存在是因为**资源不够时必须排优先级**：支付成功页比推荐位重要，扣款比积分重要。没有降级预案，故障时所有功能一起死，恢复时也分不清先救谁。

## 不用会怎么样

- 无限流：一次营销活动把 10 倍流量打到核心接口，数据库连接池占满，正常交易也被拖死——**事故往往是「非核心流量杀死核心业务」**。
- 无熔断：一个下游（比如短信、风控、渠道查询）慢 3 秒，上游线程全被占住，接口 RT 全线上涨，监控上看到的是「自己变慢了」，排查却要花两小时才定位到下游。
- 无降级：故障时所有人同时点「重试」，流量再翻一倍，形成**重试风暴**，本来只是抖动，被重试打成雪崩。
- 只做单机限流：集群 20 台，每台限 100 QPS，实际入口可能是 2000 QPS，限流形同虚设。

## 替代方案

| 手段 | 保护对象 | 触发依据 | 典型实现 |
|---|---|---|---|
| 网关限流 | 整个系统入口 | QPS / 并发数 / 用户维度 | Nginx `limit_req`、Spring Cloud Gateway、Sentinel 网关流控 |
| 应用限流 | 单个接口 | QPS / 线程数 / 热点参数 | Sentinel、Guava RateLimiter、Redis + Lua 分布式计数 |
| 熔断 | 上游自身 | 失败率 / 慢调用比例 / 异常数 | Sentinel `DegradeRule`、Resilience4j |
| 隔离 | 上游自身 | 并发占用 | 线程池、信号量、连接池分池 |
| 降级 | 业务功能 | 人工开关 / 自动触发 | 配置中心开关 + 兜底逻辑 |
| 排队削峰 | 整个系统 | 队列长度 | MQ、令牌队列、预约制 |

选择顺序：**先算容量（QPS 上限是多少），再定限流阈值（容量的 70~80%），再配熔断（下游 RT 超过基线 3 倍或失败率 >50%），最后写降级预案（哪些功能可以先关）**。

## 项目中如何使用

- **PayBy 渠道限额**：银行渠道有单日限额和单笔限额，超了就是「送进去被拒」，白白消耗渠道配额还可能触发渠道风控。做法是**渠道维度 Redis 计数 + 本地令牌桶双控**：Redis 管日累计（跨机器一致），本地令牌桶管瞬时速率（避免 Redis 成为瓶颈）。差异容忍度设在 0.5%，靠日终与渠道对账修正。
- **shopline 支付中台大促**：大促前做容量评估，核心支付接口按「压测峰值的 1.2 倍」定限流阈值，非核心接口（订单查询美化、推荐、埋点）阈值压到三分之一，并配了降级开关。大促当天核心链路 QPS 涨了 8 倍，非核心接口被限流拒绝约 12% 的请求——**这是预期内的主动丢弃**，事后看是正确的取舍。
- **招银云创拆分后的依赖治理**：C9→C10 拆完，服务从 3 个变成 12 个，一次「渠道查询服务」慢导致转账主链路线程打满。之后给每个外部依赖配了独立线程池 + 熔断（失败率 50%、窗口 10s、最小请求 20），核心与非核心依赖分池。**改造后同样的下游故障，只影响查询功能，转账不受影响**。
- **降级开关的纪律**：所有降级开关必须在配置中心可见、可审计，且**默认值是「正常」而不是「降级」**——见过一次开关配错，上线后就处于降级状态三天没人发现。

## 常见陷阱

- **阈值拍脑袋**：没有容量基线就设 1000 QPS，等于没设。阈值必须来自压测。
- **熔断阈值设太低**：正常波动（比如 1% 超时）就触发熔断，反而制造故障。要设「最小请求数」，否则低流量时 1 个失败就是 100% 失败率。
- **熔断后没有恢复策略**：`HALF_OPEN` 放行的探针太少会来回抖动，太多会二次打垮下游。
- **限流返回 500**：被限流应该是 429 或业务错误码 + 友好提示，返回 500 会触发客户端重试，雪上加霜。
- **降级逻辑本身依赖下游**：降级里再去查同一个下游，等于没降级。
- **忘记限流 MQ 消费端**：生产端限了，消费端被瞬时堆积打满，重复消费和积压一起上来。

## 三层追问

1. **分布式限流怎么做？**——Redis + Lua 做滑动窗口（ZSET 或 INCR + 过期），或者用「本地令牌桶 + Redis 定期配额分配」减少 Redis 调用。纯 Redis 每次请求一次往返，十万 QPS 下 Redis 自己就是瓶颈。
2. **熔断和限流的阈值怎么联动？**——限流是入口，阈值基于自身容量；熔断是出口，阈值基于下游健康度。两者独立配置，但**熔断打开后要通知限流层收缩**（比如降级接口的限流阈值），否则入口还在放流量，拒绝得更难看。
3. **怎么判断该限流还是该扩容？**——看瓶颈在哪：如果 CPU/连接池利用率不到 70% 就扩容；如果已经打满且扩容有上限（数据库连接、渠道配额），就必须限流。**能扩容解决的问题不要用限流掩盖**。
