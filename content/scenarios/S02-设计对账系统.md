## 30 秒简述

对账系统五段式：**拉单（多渠道获取账单）→ 解析（异构格式归一）→ 撮合（双方数据比对）→ 差错处理（长短款、单边账挂账/调账）→ 输出（报表与通知）**。设计要点：账单获取要有路由与重试、解析要能应对渠道格式频繁变更（脚本化）、撮合要大表分批 + 内存哈希匹配、差错要可运营（挂账池 + 处理流程 + 审计）、整体要可重跑且幂等。

## 是什么

- 拉单：HTTP / SFTP / 邮件附件 / 人工上传，按渠道配置路由，失败自动切换与重试，拉取记录留痕（防重复下载）。
- 解析：模板 + 脚本（Groovy）双模式；统一输出"标准流水模型"（渠道单号、平台单号、金额、手续费、状态、时间）。
- 撮合：以"渠道单号 / 业务参考号"为键，分批加载 + 哈希比对；量大时按渠道 + 日期分片并行（ForkJoin）。
- 差错：长款（渠道有我方无）、短款（我方有渠道无）、金额不符、状态不符、单边账；进入挂账池，运营可调账/调单，全程留痕。
- 结算：净额结算文件 vs 银行实际到账（银存资金）三方核对。

## 为什么这么设计

对账追求的是"可解释、可重跑、可追溯"，不是极致性能：所以每一步都落库留痕，允许失败重跑（幂等），而不是追求一次跑完。牺牲的是存储与开发量，换来的是差错可定位、审计可交付。

## 不用会怎么样

没有对账，支付系统的错误只能等客诉发现；没有挂账池，差错散落在日志里无法闭环；不可重跑，一次失败就要人工造数，运营成本极高。

## 替代方案

| 方案 | 适用 | 说明 |
|---|---|---|
| 日终批量对账（T+1） | 主流 | 账单驱动，覆盖全量 |
| 准实时对账（分钟级） | 大额、高风险渠道 | 用渠道查询接口比对在途单 |
| 实时逐笔核销 | 单笔大额转账 | 每笔同步核对，成本高 |
| 只做差错监控不做全量 | 量极大、成本敏感 | 风险漏检 |

## 项目中如何使用

- 某支付公司：Spring Boot + Dubbo 基础框架；Groovy 解析各渠道对账单（交易/手续费/净额结算文件），支持在线编辑-测试-审核发布，解决渠道格式频繁变更；ElasticJob 分布式调度；ForkJoin 分批撮合；MQ 分渠道分业务类型推送对账结果；差错支持挂账、调账、调单。
- 渠道对账单路由：HTTP / SFTP / Email 多方式自动切换下载。
- 结算账户热点资金流用 Redis 分批缓冲入账，避免高峰期行锁排队。

## 常见陷阱

- 只讲"比对两边数据"，不讲差错处理和运营闭环（这是对账系统的价值所在）。
- 忽略"不可重跑/不幂等"的问题，实战中会被追问。

## 三层追问

1. 千万级流水怎么撮合？——按渠道 + 日期分片，分片内分批（如 5000 条）加载建哈希表，流式比对；内存不够就落临时表用 SQL 比对。
2. 渠道账单格式变了怎么办？——脚本化解析 + 版本管理 + 灰度发布 + 解析失败告警；不重新发版。
3. 对账失败/漏单怎么发现？——核对"渠道账单笔数 vs 我方落库笔数"，差异即告警；再加总量金额校验（金额守恒）。
