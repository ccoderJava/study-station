## 30 秒简述

出款调渠道超时，**唯一正确的第一反应是「结果未知」，不是失败也不是重试**。方案是三步：**置未知态**（状态机显式建模 UNKNOWN，与 FAIL 严格区分）；**主动查证**（按退避节奏调渠道查询接口，5s → 15s → 60s → 5min，最长 2 小时）；**对账兜底**（日终以银行流水为准修正）。重试有严格前提：**必须先查到「渠道无此单」，才允许用同一平台单号重发**；平台单号作为幂等键透传给渠道，保证重复提交不会重复出款。整条链路的底线是「宁可挂着，不可猜」。

## 是什么

1. **超时的三种可能**：请求没到渠道（可安全重试）、渠道已受理但响应丢了（重试=重复出款）、渠道处理中（重试=重复出款）。**从调用方视角这三者不可区分**，所以不能靠猜。
2. **状态设计**：`INIT → PROCESSING → SUCCESS / FAIL / UNKNOWN`。UNKNOWN 是一等公民，带 `nextCheckTime`、`checkCount`，由查证任务驱动；SUCCESS 不可逆。
3. **查证接口**：主流渠道都提供「按平台单号查询」或「按日期+流水查询」。查证返回四种结果：成功（落 SUCCESS，回填渠道流水号）、失败（落 FAIL，释放冻结资金）、不存在（继续退避查询，不立即判失败，因为有落库延迟）、处理中（继续查）。
4. **重试的前置条件**：`查证 = 不存在` **且** 距首次提交超过渠道的落库延迟窗口（例如 5 分钟）。重发时带同一个 `requestId`，渠道侧幂等；若渠道不支持幂等，则必须人工确认。
5. **渠道抽象**：`submit / query / parseCallback` 三个方法统一接口，超时、重试次数、查询间隔按渠道配置（大额支付走人行通道，查询窗口更长）。
6. **回调与查询的关系**：回调是快路径，查询是兜底；两者都可能乱序到达，所以状态更新一律 CAS（`where status = 期望的旧状态`），终态直接幂等返回。

## 为什么这么设计

**为什么不能同步等**：银行渠道响应时间不受控（大额通道高峰期几十秒），同步等待会占满线程，且超时后结果依然未知——只是把不确定性从业务层推到了线程池。

**为什么查询优先于重试**：重试是「制造新请求」，查询是「确认既有事实」。在资金系统里，确认事实的成本永远低于纠正错误的成本。

**代价**：链路变长、运营介入变多（长时间未知要转人工）、需要维护每个渠道的查询能力差异表。换来的是「不会因为一次网络抖动产生两笔钱」。

## 不用会怎么样

- 超时直接置失败 → 客户看到失败、银行实际成功 → 客户投诉 + 冲正，或客户重新支付造成双付。
- 超时直接重试 → 银行两笔都成功 → 长款挂账，对账发现时已经是 T+1，客户资金被多扣一天。
- 只依赖回调 → 回调丢失（渠道侧超时、网络抖动、配置错误）后单据永远停在 PROCESSING，资金被冻结无法释放。
- 没有 CAS → 查询结果与回调并发写，晚到的「处理中」覆盖了已到的「成功」，状态回退。

## 替代方案

| 方案 | 适用 | 说明 / 风险 |
|---|---|---|
| 未知态 + 主动查询 + 对账兜底 | 出款、代付、退款 | 标准做法；需要渠道支持查询 |
| 同步阻塞等结果 | 内部系统、低延迟渠道 | 简单；线程占用高，超时后依然未知 |
| 纯回调驱动 | 渠道回调可靠、可重推 | 实现最轻；回调丢失即卡单 |
| 只靠日终对账 | 小额、可容忍 T+1 | 成本最低；客户体验差，资金占用久 |
| 渠道侧幂等 + 无条件重试 | 渠道明确支持幂等键 | 需拿到渠道的幂等承诺，通常只对大行有 |

## 项目中如何使用

- **某支付公司多渠道出款**：渠道适配层统一实现 `submit/query`，每个渠道配置 `queryInterval`（5s,15s,60s,5min,15min）与 `maxCheckWindow`（2 小时）。超时统一落 UNKNOWN，进查证队列（ElasticJob 分片扫描 `status=UNKNOWN and next_check_time <= now`）。查证到「不存在」且超过 5 分钟落库窗口，才允许重发；重发次数上限 3 次，超过转人工工单。
- **某银行超级直连 / 大小额**：大额支付走人行通道，返回「已受理」不等于成功，最终态以日终清算文件为准，所以状态机里额外区分「渠道已受理」与「清算成功」，对账时以清算文件回写。
- **一次真实故障**：某渠道查询接口在维护窗口返回「系统维护」而不是「查无此单」，查证任务把它当成「不存在」触发重发，造成 3 笔重复出款。修复方式是给查证结果加分类：`SUCCESS/FAIL/NOT_EXIST/PROCESSING/ERROR`，只有 `NOT_EXIST` 才允许重发，`ERROR` 一律继续等待——**「查不到」和「查不了」是两件事**。

## 常见陷阱

- 把「查询返回空」当失败：渠道落库有延迟，空结果可能只是还没写进去。
- 用「渠道流水号」做主键：超时时根本没有流水号，必须用平台单号做幂等键。
- 重试没有上限或没有退避，渠道恢复瞬间被重试流量打满。
- 面试官会追问：「如果渠道查询接口也挂了怎么办」——答：退避 + 转人工 + 对账兜底，绝不放宽重试条件。

## 三层追问

1. 为什么不能靠「超时时间调大」来解决？——调大只是降低超时概率，不确定性仍在，而且长事务会拖垮线程池；本质要用「状态 + 查证」建模。
2. 查证任务怎么保证不重复处理同一单？——扫描时用 CAS 抢占（`update ... set checker=? where id=? and status='UNKNOWN'`），或分布式锁按单据维度加锁。
3. 对账能修哪些、不能修哪些？——能修「状态不一致」和「单边账」（以银行流水为准回写）；不能修「重复出款」——那需要冲正流程，属于差错处理而不是对账。
