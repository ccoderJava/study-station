## 30 秒简述

热点账户就是**同一行记录的锁竞争**：`update account set balance = balance + ?` 每次都要拿行锁，单账户实际能撑的 TPS 大概在千级，结算日集中入账就会排队、连接池被打满。解法分三层：**入口限流**（把无限并发变成可控排队，超出的快速失败让上游重试）、**缓冲合并**（明细流水 append-only 落库不竞争，余额变更先入内存/Redis 队列，按账户聚合后每 100ms 或攒够 N 笔做一次批量累加）、**日终兜底**（余额快照与流水求和比对，差额进差错池）。核心取舍是：牺牲单笔实时可见性，换吞吐与稳定。

## 是什么

问题拆解：

1. **瓶颈在哪**：`update ... where id=?` 持有行锁直到事务提交，事务里每多一次 IO，锁持有时间就多一截。单账户并发更新时，后到的请求在锁队列里等，`innodb_lock_wait_timeout` 一到就报错；同时连接池被这些等待占满，其他账户的请求也拿不到连接——**热点扩散成全局故障**。
2. **容量估算**：假设单次 update 持锁 3ms，理论单账户上限约 330 TPS。日终 20 万笔要在 5 分钟内入完，需要 666 TPS——**必须减少 update 次数，而不是加机器**。
3. **方案骨架**：
   - **入口**：网关/Sentinel 按账户维度限流，单账户 QPS 上限 = 实测容量 × 0.7，超出返回「受理中」让上游稍后查询，而不是让它死等。
   - **明细与余额分离**：流水表只 insert（顺序写、无锁竞争），余额表才是热点。
   - **缓冲合并**：应用内环形队列 + 定时刷（100ms）或按账户计数触发，把 N 笔累加成一个增量，一次 `update balance = balance + delta`。
   - **串行化**：同一账户的变更走同一个内存队列/同一个 MQ 分区，天然串行，不需要分布式锁。
   - **兜底**：余额更新与流水落库不在同一事务，靠「余额 = sum(流水)」的日终校验修正。
4. **失败处理**：队列在内存，进程挂了会丢增量——用「先写流水（含状态=待入账）→ 再更新余额 → 回写流水状态」的两阶段，进程重启后扫「待入账」流水重新聚合。

## 为什么这么设计

**为什么不让数据库自己扛**：数据库的行锁是悲观锁，热点行天然不适合高并发写，加机器只是加锁队列长度。

**为什么用「合并」而不是「拆账户」**：拆影子账户（一个逻辑账户拆成 N 个物理子账户）能线性扩容，但会带来余额分散、对账复杂、转账时要在子账户间调度的问题，资金系统里一般只对超大商户用，且必须配套「子账户余额汇总」的准实时视图。

**代价**：单笔入账后余额不是立即可见（有 100ms 级延迟），运营查询需要读「余额 + 在途增量」；合并逻辑一旦有 bug，影响面是一批而不是一笔，所以合并必须可回放、可对账。

## 不用会怎么样

- 结算日凌晨批量入账，账户行锁排队，`Lock wait timeout exceeded` 刷屏，任务失败率 30%。
- 连接池被等待中的请求占满，同一应用里的查询接口也开始超时，故障从「入账慢」升级为「整个结算服务不可用」。
- 重试机制介入后，同一笔被重复入账（没有幂等键），日终对账出现长款，需要人工冲正。
- 为了不超时把 `innodb_lock_wait_timeout` 调大，结果请求堆积更严重，最终 OOM。

## 替代方案

| 方案 | 适用 | 说明 / 风险 |
|---|---|---|
| 直接 update 单行（+ 限流） | 单账户 QPS < 300 | 最简单；超过就是排队，必须限流兜住 |
| 缓冲合并入账 | 结算、代发、平台分账 | 主流方案；牺牲实时性，要求可对账 |
| 影子账户拆分 | 超大商户、持续高并发 | 扩容线性；余额分散，对账与调拨复杂 |
| 消息队列串行消费 | 已有时序要求 | 天然串行防并发；消费积压时延迟升高，需要分区数规划 |
| 记账凭证化（只写流水，余额异步汇总） | 类账本系统 | 扩展性最好；余额查询要走汇总表，实现成本高 |

## 项目中如何使用

- **某支付公司结算账户**：商户结算账户在 T+1 上午集中入账，最初是同步逐笔 update，峰值时锁等待告警。改造为「Redis List 按账户分桶缓冲 + 定时批量累加」，同一商户的入账在单线程内串行消费，余额更新从「每笔一次」降到「每 100ms 一次」。同时把明细流水改成纯 insert，与余额更新解耦。
- **某银行代发**：代发批次动辄上万笔，同一个付款账户是天然热点。做法是批次内先按收款账户聚合（同一收款人多笔合并成一笔入账），再按付款账户串行入账；批量任务用线程池分片，但**分片键是收款账户而不是付款账户**，避免所有分片打同一个付款账户。
- **验证方式**：重构后用流量回放把历史结算日流量灌入新链路，比对「逐笔余额变动序列」与「合并后余额序列」的终值一致，再核对总笔数与总金额守恒。

## 常见陷阱

- 只答「用 Redis 缓冲」，讲不清「缓冲丢了怎么办」——必须有流水兜底与重启重放。
- 合并后丢失单笔可追溯性：合并的每一笔都要能定位到批次号，否则对账差异无法归因。
- 限流维度选错：按接口总 QPS 限流，热点账户照样打爆；要按账户维度限。
- 面试官会追问：「余额什么时候对用户可见」——要明确给出延迟量级（100ms / 秒级）以及运营侧的读取口径（余额 + 在途）。

## 三层追问

1. 缓冲队列用 Redis 还是本地内存？——本地更快但有丢失风险；Redis 可跨实例但多一次网络往返。资金场景推荐「本地批量 + 流水落库 + 定时快照」组合，Redis 只做削峰不做唯一真相。
2. 怎么保证同一账户的变更顺序？——按账户 hash 到固定队列/线程/MQ 分区，消费端单线程处理该账户，顺序由路由保证，不依赖锁。
3. 合并后如何应对「部分成功」？——批量 update 要么全成要么全败；增量按批次落一张 `balance_delta` 表，成功后标记，失败重放，用批次号做幂等。
