## 30 秒简述

重复支付的来源有三类：**客户端重试或换单号重推、网关与渠道超时重发、并发多点提交**。防护分四层递进：**入口层**（前端防重、请求指纹去重、OpenAPI 约定原单号重推）、**锁层**（按「租户 + 业务参考号」加分布式锁，把并发转成串行）、**判断层**（幂等表或状态机前置校验，已处理就直接返回原结果）、**存储层**（唯一索引兜底，这层不能省）。核心原则：**锁只是降低冲突概率，唯一约束才是最终正确性保证**——锁丢了、超时了、Redis 换了，唯一索引还在。

## 是什么

- 一锁：Redisson 锁 key = `pay:{tenant}:{bizRefNo}`，租期 + 看门狗续期。
- 二判断：查幂等表（或用单据状态机判断是否已在处理/已成功）；命中即返回原结果（幂等返回，不报错）。
- 三更新：更新单据状态（状态机只能单向推进）+ 落流水，同事务提交，`where status = 期望原状态` 保证 CAS 语义。
- 兜底：支付流水表唯一索引 `(tenant, biz_ref_no, biz_type)`，重复插入直接失败。

## 为什么这么设计

四层是有意冗余：锁解决并发（性能层），状态机解决并发下的顺序（逻辑层），唯一索引解决"锁失效/跨机房/主从切换"（正确性层）。任何一层单独使用都有漏洞，这在资金系统里不可接受。

## 不用会怎么样

只有前端防重 → 网络重试照样重复；只有分布式锁 → Redis 主从切换丢锁即重复扣款；只有状态机 → 高并发下并发读同一状态都通过校验（需要 `for update` 或 CAS 更新）。

## 替代方案

| 方案 | 强度 | 缺点 |
|---|---|---|
| 前端按钮置灰 | 最弱 | 只防误触 |
| 请求指纹（参数哈希去重表） | 中 | 需定义指纹要素 |
| 分布式锁 | 中 | 主从切换风险 |
| 状态机 + CAS 更新 | 强 | 要求状态设计正确 |
| 唯一索引 | 最强 | 只能在落库时刻生效，需处理异常返回 |

## 项目中如何使用

- 某银行：全系统重复支付与幂等加固，落地"一锁二判断三更新"统一范式，配合前端防重。
- 协议层：输出标准 OpenAPI 规范，明确异常重推必须复用原业务参考号，推动客户回检；从源头消除"换单号重推"。
- 经办超时防重：采集单据关键要素生成哈希，发往银行前比对同哈希超时单据，命中拦截转人工——解决"银行可能已受理但响应超时"的模糊态。

## 常见陷阱

- 只说"加锁"，被追问"锁失效怎么办"就答不上。
- 把幂等设计成"重复请求返回报错"——正确做法是返回原结果。

## 三层追问

1. 幂等 key 怎么选？为什么不能用请求流水号？——流水号每次重试都会变，key 必须用业务语义唯一标识（租户 + 业务参考号 + 业务类型）。
2. 银行返回超时，你怎么知道成没成功？——不能猜，必须主动查询（单笔查证）+ 对账兜底；查询无结果时置中间态，禁止直接重发。
3. 幂等返回时给客户返回什么？——返回首次结果（成功/失败一致），并标记 `idempotent=true`，避免客户误判。
