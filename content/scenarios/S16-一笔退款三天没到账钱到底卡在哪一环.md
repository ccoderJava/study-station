## 30 秒简述

退款不到账，本质是**一笔资金在状态机里卡住了，或者状态机认为它成功了但资金没动**。排查顺序固定三步：**先定位状态**（在哪个系统、哪个状态、下一步该谁动）、**再对齐三方**（自己系统的单、渠道的回执、账务的流水，三者必须能对上）、**最后定性质**（是流程没推动、是状态错乱、还是钱真的丢了）。回答这类问题，**绝对不能直接说「我查一下」**——要先讲清「一笔退款要经过几个环节、每个环节可能怎么断」，这才是面试官想听的。

## 是什么

一笔标准退款要经过五段：

1. **受理**：商户发起退款 → 校验（原单可退、金额不超、时间窗内）→ 生成退款单（`INIT`）。
2. **记账（冻结/挂账）**：从商户待结算余额扣减，转入「退款在途」科目。**这一步是资金视角的起点**。
3. **发往渠道**：调用银行/微信/支付宝退款接口 → 拿到受理回执（可能同步成功，也可能「处理中」）。
4. **渠道处理**：渠道内部审核、清算、回单。**这一段完全不受你控制，时间是黑盒**（1 分钟到 7 个工作日）。
5. **确认与对账**：渠道回执成功 → 我方状态置 `SUCCESS` → 账务冲销「退款在途」；日终用对账文件核三方（我方单、渠道单、账务流水）。

每一段都有典型的断点：

| 环节 | 断点 | 表现 |
|---|---|---|
| 受理 | 校验通过但没落库 | 无单可查 |
| 记账 | 扣了余额但没生成退款单 | 钱少了，单没有 |
| 发送 | 调用超时，不知道渠道收没收到 | 单一直「处理中」 |
| 渠道 | 渠道审核拒绝但没回调 | 单一直「处理中」，实际已失败 |
| 确认 | 回调丢了 | 渠道成功，我方仍「处理中」 |
| 对账 | 状态改成功但账务没冲销 | 单成功，钱还在途 |

## 为什么这么设计

因为**退款链路跨越了「我的系统」和「别人的系统」，中间没有分布式事务**。你无法和银行谈 2PC，只能靠「状态机 + 幂等 + 对账 + 补偿」这一套最终一致的做法。

所以设计上必须满足三条：
- **状态可查**：每一笔在每个环节都有明确状态和更新时间，且有「最后更新超过 N 小时仍未终态」的告警。
- **动作幂等**：重复发起退款、重复接收回调都不能多退一次（退款是最容易多退的场景，因为没有「余额不足」这种天然限制）。
- **对账兜底**：不管前面怎么断，日终对账必须能算出差额并生成差错单。

## 不用会怎么样

- 状态只有「成功/失败」两态：超时的时候没法表达「不知道」，只能猜一个，猜错就是资金差错。
- 没有超时告警：客户三天后打电话才发现，此时已经过了渠道的可查窗口。
- 回调不幂等：渠道重推 3 次，退了 3 笔钱出去。
- 不对账：状态和资金长期不一致，等到财务月结才暴露，损失已经放大。

## 替代方案

| 环节 | 常见做法 | 取舍 |
|---|---|---|
| 状态表达 | 三态（成功/失败/处理中）+ 子状态 | 必须，否则表达不了不确定 |
| 结果获取 | 同步返回 / 异步回调 / 主动查询 | 三者都做：同步返回受理，回调主推，查询兜底 |
| 渠道确认 | 只信回调 | 风险：回调丢了就永久卡住 |
| | 回调 + 定时查询（30 分钟一次，退避） | **推荐**，成本低，能自愈 |
| | 只靠日终对账 | 太晚，用户已经投诉 |
| 差错处理 | 自动重试 | 要区分「可重试」与「不可重试」错误 |
| | 人工差错池 | 必须有，作为最后兜底 |

## 项目中如何使用

- **PayBy 清结算的一次真实排查**：商户投诉一笔 12 万的退款 3 天没到。排查路径：先查我方退款单状态 `PROCESSING`，最后更新在 3 天前；再查渠道回执——渠道侧显示「已退款成功」；再查账务，发现「退款在途」科目余额里还挂着这 12 万。结论：**回调丢了，且日终对账没有覆盖这个渠道**（该渠道只给了汇总文件，没有明细）。处理：手工冲销 + 补发通知，同时推动渠道开通明细文件。
- **根因修复**：加了「处理中超过 2 小时主动查询」的补偿任务（因为 90% 的卡单靠主动查询就能自愈），并在对账里增加「状态自比对」（我方 `SUCCESS` 但账务未冲销的单子单独列出来）。
- **shopline 退款链路**：退款单状态机加了 `UNKNOWN` 子状态（超时导致的不确定），专门配一个查证任务。**关键设计：`UNKNOWN` 不等于失败**，不允许自动重发，必须先查证——这是用一笔 5 万的重复退款换来的教训。
- **对账口径**：退款对账要按「原交易号 + 退款单号」双维度匹配，只按退款单号会漏掉渠道侧的「部分退款合并」情形。

## 常见陷阱

- **把「处理中」当失败重发**：渠道实际已完成，重发就是多退一笔。这是退款最危险的坑。
- **只信回调不做主动查询**：回调丢失率在跨公网场景下并不低（千分之几），没有查询兜底就会长期卡单。
- **对账只对金额不对状态**：金额对上了（都在途），但状态错乱，用户看到的是「退款中」永远不动。
- **没有「在途资金」科目**：退款在途和已退混在一个科目，出问题时无法区分「钱在哪」。
- **查询任务频率太高**：每 10 秒查一次，把渠道查询接口打成限流。用退避策略（5 分钟 → 30 分钟 → 2 小时）。
- **人工处理没有审计**：手工改状态不入审计表，事后无法追责，也无法沉淀成规则。

## 三层追问

1. **回调丢了怎么发现？**——两条线：实时线是「超时未终态」告警（T+2h），兜底线是日终对账。**只靠对账太晚，只靠告警会漏掉对账能发现的资金差错**。
2. **状态和资金不一致时，以谁为准？**——**以渠道/银行的实际资金为准**，我方状态是「认知」，不是「事实」。处理顺序是：先查证渠道真实状态 → 修正我方状态 → 再补账务分录。绝不能反过来（改状态让账对上）。
3. **怎么防止多退？**——三重：发起时幂等键（原单号+退款请求号唯一索引）、`UNKNOWN` 状态禁止自动重发、渠道侧同一退款请求号重复提交返回第一次结果（大多数渠道支持）。**最后还有对账，多退一定会被算出来**。
