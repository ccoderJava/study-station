## 30 秒简述

重复入账是**「至少一次投递」+「消费端不幂等」**的组合事故。止损分三步，顺序不能反：**先停（暂停消费，防止继续错）→ 再查（按业务流水号统计重复笔数与影响范围）→ 再修（冲正多记的，不是删记录）**。修复分两层：**当天止血**靠对账 + 冲正，**根因修复**靠幂等键 + 唯一索引 + 状态机前置判断，三道缺一不可。回答时要突出一个观念：**MQ 的语义就是会重复，重复不是异常，是常态**。

## 是什么

重复的四个来源，逐个对应：

| 来源 | 机制 | 对策 |
|---|---|---|
| 生产端重试 | 发送超时后重发，第一条其实到了 | 业务唯一键 + 消费端幂等（同一个键多次投递只处理一次） |
| Broker 重投 | 消费 ack 丢失/超时，Broker 认为没消费 | 消费幂等（ack 前失败会重投，这是正常行为） |
| 消费端 rebalance | 分区迁移时未提交位点的消息被新消费者重放 | 幂等 + 位点提交与业务处理的一致性 |
| 人工/补偿重放 | 运维重跑、补偿任务重发 | 补偿也要走幂等入口，不能直接调业务方法 |

幂等的三道实现，从强到弱：

1. **唯一索引（最硬）**：`uk_biz(biz_type, biz_no)`，重复插入直接抛 `DuplicateKeyException`，捕获后当成功处理。DB 保证，不会漏。
2. **状态机前置判断**：`update ... where status = 'INIT'`，影响行数为 0 就是已处理。适合有明确状态流转的业务（支付、退款、代发）。
3. **Redis 去重（最快但有风险）**：`SET key NX EX 86400`，失败说明处理过。**只能作为前置挡板**，不能作为唯一保证——Redis 丢数据或过期就会重复。

我的实际做法是**三层叠加**：Redis 挡 99%（减少 DB 压力）、状态机判断业务合法性、唯一索引兜底（最后一道，保证不出错）。

## 为什么这么设计

因为**分布式系统里「Exactly Once」只在理论上有**（需要两阶段提交 + 幂等，本质上还是 at-least-once + 去重）。工程上的正解是：**投递保证 at-least-once，消费保证幂等**，两者配合达到「业务上恰好一次」。

为什么不能靠「减少重投」来解决？因为 ack 丢失无法避免（网络、进程崩溃、超时），你无法区分「对方没收到」和「对方收到了但 ack 丢了」。只能接受重复，然后去重。

为什么修复要用冲正而不是删记录？因为**账务的每一次变动都必须是可追溯的**。删记录会破坏流水连续性，审计过不去，也无法解释「为什么余额和流水对不上」。冲正（反向记账 + 关联原流水号）才是会计上正确的做法。

## 不用会怎么样

- 只靠 Redis 去重：Redis 主从切换丢了几百个 key，第二天重复入账，对账才发现。
- 唯一索引建在自增 ID 上：等于没建。
- 幂等键选错：用「消息 ID」做幂等键——但生产端每次重试会生成新消息 ID，去重失效。**幂等键必须是业务键**（业务流水号、订单号 + 动作类型）。
- 消费端捕获所有异常当成功：处理失败的也 ack 了，消息丢了，比重复更严重（重复至少能对出来，丢了要靠客户投诉）。
- 修复只改代码不查历史数据：改完代码，历史重复数据还在账上，下次对账继续差。

## 替代方案

| 幂等实现 | 强度 | 性能 | 适用 |
|---|---|---|---|
| 唯一索引 | 最强 | 中（一次插入失败） | **必须有，兜底** |
| 状态机条件更新 | 强 | 高 | 有状态流转的业务 |
| Redis SETNX | 中（可能丢） | 最高 | 前置挡板，削 DB 压力 |
| 分布式锁 | 中（锁超时误判） | 中 | 短事务、并发防重，不能替代幂等 |
| 事务消息 | 强（生产侧） | 中 | 只解决生产端不重复发，不解决重复消费 |
| 消费端本地去重表 | 强 | 中 | 无业务唯一键时（如日志类） |

## 项目中如何使用

- **某支付公司清结算的一次真实事故**：一次 MQ 集群升级导致大量 ack 超时，入账消息被重投。消费端当时只有「Redis 去重」，且 Redis 恰好在同期做过主从切换，丢了部分 key。结果约 340 笔结算入账被记了两次，金额合计 87 万。
  - **止损**：立刻暂停该 topic 消费 → 按 `settle_batch_no + account_no` 聚合，找出重复组 → 生成冲正单（反向分录，关联原流水）→ 恢复消费。
  - **修复**：入账表加 `uk(settle_batch_no, account_no, entry_type)` 唯一索引；消费逻辑改成「先唯一索引插入明细，再更新余额」，把「更新余额」变成「明细插入成功后的一次幂等更新」。
  - **复盘结论**：**Redis 去重不能当唯一保证**，这是当时设计上的认知错误。
- **某银行代发结果回写**：代发结果由渠道回调 + 定时查询双通道进来，天然重复。做法是「结果回写只做 `update ... where status = 'PROCESSING'`」，影响行数 0 就丢弃，简单可靠。
- **补偿任务也要幂等**：曾经补偿任务直接调 `accountService.credit()`，绕过了幂等入口，一次重跑导致重复入账。**规则：所有入账只能通过带幂等的唯一入口，补偿也一样**。

## 常见陷阱

- **用消息 ID 做幂等键**：生产端重试会生成新 ID，等于没去重。
- **「先查再插」**：查和插之间有并发窗口，两个消费者同时查到「不存在」然后都插入。必须靠唯一索引或原子操作。
- **唯一索引建了但业务键不唯一**：比如用「订单号」，但同一订单允许多次部分退款——索引直接报错，正常业务被拦。
- **幂等表没有清理策略**：去重表无限增长，一年后几亿行，插入变慢成为新瓶颈。按时间分区或定期归档。
- **捕获异常范围过大**：`catch (Exception e) { return; }` 把业务异常也吞了，消息丢失且无告警。
- **冲正做了但没关联原流水**：事后无法证明「这两笔是同一笔的借贷」，审计不通过。

## 三层追问

1. **幂等键怎么选？**——选「业务上唯一标识一次操作」的字段组合：支付用 `商户号 + 商户订单号`，退款用 `原单号 + 退款请求号`，代发用 `批次号 + 明细序号`。**不能包含时间戳、随机数、消息 ID**。
2. **唯一索引冲突了，业务该返回成功还是失败？**——**返回成功**（幂等语义：已经处理过 = 处理成功），但要区分「同一次请求的重复」和「不同请求撞了同一个键」——后者是 bug，要告警。
3. **重复已经发生了，除了冲正还该做什么？**——三件事：算清影响范围（笔数、金额、涉及的账户）、通知相关方（财务、商户）、把这次事故转成检测能力（加「同一业务键 24 小时内出现多次成功」的实时告警）。**修的是检测能力，不只是这次的数据**。
