## 30 秒简述

限量扣减的本质是**热点数据的高并发原子扣减**，分四层落地：**前置削减**（静态化、资格校验前置、单用户限次、令牌桶限流）、**原子扣减**（Redis Lua 把「查余量 + 判断 + 扣减」合成一步，或本地令牌预分配）、**异步落库**（扣减成功发 MQ，消费端批量入库，把峰值削平）、**对账兜底**（Redis 与 DB 定时核对，差异回补）。三条硬要求：扣减原子、请求幂等（用户 + 活动维度去重）、超发可检测（对账能算出超了多少，而不是靠用户投诉）。

## 是什么

1. **为什么不能直接打 DB**：`update stock = stock - 1 where stock > 0` 在几千 TPS 下会形成行锁排队，连接池瞬间打满，同一个库上的其他业务一起抖动。
2. **Redis Lua 扣减**：
   ```lua
   local left = tonumber(redis.call('get', KEYS[1]))
   if left == nil or left <= 0 then return -1 end
   if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then return -2 end
   redis.call('sadd', KEYS[2], ARGV[1])
   return redis.call('decr', KEYS[1])
   ```
   一次往返完成「查重 + 判断 + 扣减」，Redis 单线程保证原子性。
3. **本地分桶**：把 1000 个名额拆成 10 个 key（每桶 100），请求按用户哈希到某个桶，把单 key 热点分散到 10 个 key；桶空则顺延到下一个桶，允许少量浪费换吞吐。
4. **异步落库**：扣减成功后发消息，消费端按批次写明细表；峰值 2 万 TPS 的扣减，落库只有几百 TPS 的批量写。
5. **幂等**：用户维度用 SET 去重（`sismember`），DB 层用唯一索引（活动 ID + 用户 ID）兜底——Redis 丢数据也不会重复发奖。
6. **对账**：定时把「活动总数 − Redis 剩余」与「DB 成功明细数」比对，差异进补偿队列；超发时按「先到先得 + 后到补偿」处理并告警。

## 为什么这么设计

扣减是典型的「读少写多且强一致」场景：写必须串行化，但串行化又会成为瓶颈。Redis 单线程天然串行，单 key 十万级 QPS；DB 行锁只有几千。所以把「判定」放 Redis、把「记录」放 DB 异步落，是拿「短暂的最终一致」换吞吐。

代价必须说清楚：Redis 与 DB 之间有一个不一致窗口，Redis 挂了可能丢已扣未落库的记录，所以要有对账与回补；分桶会带来少量名额浪费（某个桶空了但别的桶还有）。

## 不用会怎么样

- 直接 DB 扣减：行锁排队，RT 从 10ms 涨到几秒，连接池打满，活动页 502，连带影响同库的支付业务。
- 先查再扣（`select` 后 `update`）：并发下必然超发，1000 个名额发出 1200 个，要么赔付要么道歉。
- 扣了 Redis 没落库，也没对账：Redis 重启后名额回到初始值，二次超发。
- 幂等只做在 DB 层：用户狂点产生 10 次 Redis 扣减，DB 唯一索引只留 1 条，另外 9 个名额白扣，剩余名额虚少。

## 替代方案

| 方案 | 适用 | 说明 / 风险 |
|---|---|---|
| DB 条件更新（`where stock >= n`） | 几百 TPS 以内 | 最简单、强一致；高并发下锁等待严重 |
| DB 悲观锁 / `select for update` | 强一致、低频 | 正确；吞吐最低，容易死锁 |
| Redis Lua 原子扣减 | 万级 TPS | 主流；需对账兜底 |
| 本地分桶 + 令牌预分配 | 十万级峰值 | 吞吐最高；会浪费名额，实现复杂 |
| MQ 串行消费扣减 | 可接受排队延迟 | 简单可靠；峰值时队列堆积、响应变慢 |

## 项目中如何使用

- **招银云创营销立减名额**：活动名额放 Redis（按活动维度一个 key），Lua 完成「用户去重 + 扣减」，成功后发 MQ 异步写领取明细；整点开抢时入口再加一层令牌桶限流（单机 500 QPS），把无效流量挡在业务逻辑之前。
- **与热点账户同源**：B6 的缓冲入账是同一思路的不同侧面——热点账户用「缓冲 + 批量落库」降低行锁竞争，名额扣减用「Redis 原子 + 异步落库」削峰，两者都在解决「热点行不能直接承接峰值」。
- **PayBy 渠道日限额**：单渠道每日限额 5000 万，用 Redis 计数 + Lua 原子判断，DB 只记流水；跨日切换用 key 带日期后缀，避免 0 点重置时读到旧值。
- **一次教训**：早期只做了 Redis 扣减没做对账，Redis 主从切换丢了约 200 条扣减记录，名额多放出 200 个。之后加了两道：AOF `everysec` + 每 5 分钟对账 + 超发自动冻结活动。

## 常见陷阱

- 用 `get` 再 `decr`：两步之间被插队，经典超发写法。
- Lua 里用浮点运算处理金额：`tonumber` 是 double，金额必须用整数（分）或字符串。
- 只在入口限流不做用户级幂等：同一用户并发 10 个请求照样能抢到 10 个。
- 面试官会追问「Redis 扣了但 DB 落库失败怎么办」——答：MQ 重试 + 消费幂等 + 定时对账回补，绝不回滚 Redis（回滚会造成新的竞态）。

## 三层追问

1. **分桶后某个桶空了怎么办？**——顺延到下一个桶（多一次 Redis 调用），或用「桶余量汇总表」做粗筛；顺延会带来跨 key 访问，所以要控制桶数量。
2. **为什么不干脆用 MQ 串行扣减？**——串行消费吞吐取决于单分区，且用户要等结果；秒杀类场景要求毫秒级反馈，只能前置到 Redis。
3. **超发了怎么补救？**——先冻结活动止损，再按扣减时间排序保留前 N 名，超出部分给补偿（券/积分），同时把差异写进事故复盘，修的是对账与幂等而不是「下次小心点」。
