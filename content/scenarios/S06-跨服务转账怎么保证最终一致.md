## 30 秒简述

跨服务转账不能用本地事务，也不该直接上 TCC 增加复杂度。**资金类的主流解是「本地消息表 + 幂等消费 + 状态机 + 对账」**：扣款服务在同一个本地事务里写「扣款流水」和「待发送消息」，事务提交后由投递器异步发 MQ，入账服务幂等消费、记账成功后回执，两边状态靠消息重试推进，最终靠日终对账校准。要点是三个「必须有」：**必须有本地事务保证业务与消息同生共死**（否则会丢消息或发空消息）、**必须有幂等键**（消息重复是常态）、**必须有对账兜底**（消息系统不保证 100%）。

## 是什么

1. **为什么不能用 2PC**：XA 需要数据库与协调者长时间持锁，性能差；跨团队、跨中间件（MQ、银行渠道）根本没法纳入同一个 XA 事务，实际落地几乎不用。
2. **本地消息表流程**：
   - ① 本地事务：`update 账户 set 余额=余额-100 where id=A and 余额>=100` + `insert 出账流水` + `insert 消息表(status=待发送)`，一个事务。
   - ② 投递器：定时扫待发送消息 → 发 MQ → 更新为已发送（发送与更新之间可能失败，靠「至少一次」+ 消费端幂等兜住）。
   - ③ 消费端：以消息里的 `bizNo` 做唯一键，先 insert 幂等表（唯一索引冲突即已处理），再入账，同一本地事务。
   - ④ 回执/补偿：入账成功发回执消息，出账侧更新流水为「已入账」；超时未回执触发查询或反向冲正。
3. **TCC 的适用边界**：强一致要求高、参与方少（2~3 个）、每个参与方都能提供 Try/Confirm/Cancel 三个接口时才用。资金系统里常见于「冻结-扣减-解冻」模型，这就是把资源预留显式化。
4. **Saga**：长流程编排（如跨行汇款：扣款→发渠道→等结果→记账），每步有补偿动作。适合流程长、无法持锁的场景，代价是补偿逻辑要写一份，且补偿本身可能失败。
5. **状态机是骨架**：转账单必须能表达「扣款成功、入账未知」这个中间态——这跟渠道超时是同一类问题。

## 为什么这么设计

**为什么本地消息表比 TCC 更常用**：它把分布式问题降维成「本地事务 + 至少一次投递 + 幂等消费」，实现成本低，且不要求下游改造接口。代价是**只保证最终一致**（秒级到分钟级延迟），并且需要一个一直跑的投递器和一张会膨胀的消息表。

**为什么一定要对账**：消息系统、消费者、数据库任何一环都可能丢或重复，理论上的「最终一致」在工程上要靠「定期核对 + 差错修复」兜底。所以资金系统的完整答案永远是「异步消息 + 对账」，缺一不可。

## 不用会怎么样

- 直接 `@Transactional` 包两个服务的 RPC 调用：事务只对本地库生效，远程调用成功但本地回滚 → 钱扣了没记账，或记了账没扣钱。
- 先调远程再写本地：远程成功、本地失败 → 单边账，只能靠人工找。
- 用 MQ 但不做本地事务绑定：事务回滚了消息已发出 → 下游凭空入账。
- 消费端不做幂等：MQ 至少一次投递 + 重试 = 重复入账，日终长款。

## 替代方案

| 方案 | 一致性 | 适用 | 说明 / 风险 |
|---|---|---|---|
| 本地消息表 + MQ | 最终一致（秒~分钟） | 资金转账、订单支付 | 主流；要有投递器与消息清理 |
| RocketMQ 事务消息 | 最终一致 | 已用 RocketMQ 的团队 | 半消息 + 回查，省掉消息表但要实现回查接口 |
| TCC | 准强一致 | 参与方少、可预留资源 | 三个接口成本高，空回滚/悬挂要处理 |
| Saga / 流程编排 | 最终一致 | 长流程、多参与方 | 补偿逻辑必须完整，补偿失败要人工兜底 |
| 最大努力通知 | 弱一致 | 对外通知、非资金 | 简单；不保证送达 |

## 项目中如何使用

- **某银行 C9→C10（账户与账务拆分）**：原来单体里「扣账户 + 记账」是一个本地事务，拆分后变成两个服务。方案是本地消息表：账户服务在扣款事务里写 `account_flow` + `mq_message`，投递器 500ms 扫一次，账务服务按 `bizNo` 幂等入账。转账单状态机为 `扣款成功/入账中/入账成功/入账失败待冲正`，超过 30 秒未回执由对账任务查账务服务的流水表。
- **重构期的验证**：用流量回放把生产流量打到新链路，比对「余额变动序列 + 分录明细」，同时故意在投递器注入延迟与重复，验证幂等与对账能否把差异收敛——这是拆分上线前最有价值的一轮测试。
- **某跨境电商支付中台**：支付成功后的「订单状态更新 + 商户通知 + 计费」用事务消息串联，商户通知是最大努力通知 + 定时补推，计费走本地消息表，两者失败互不影响。

## 常见陷阱

- 只讲「用 MQ 保证最终一致」，讲不出「消息和本地事务怎么绑定」——这是必问点。
- 幂等表只按消息 ID 去重，不做业务键去重：消息重发换了 ID 就重复入账。
- 补偿（Cancel）接口没有幂等和空回滚保护，TCC 场景下会把正常扣款回滚掉。
- 面试官会追问：「消息一直消费失败怎么办」——重试到上限进死信队列 + 告警 + 人工/对账修复，不能无限重试。

## 三层追问

1. 本地消息表会不会成为性能瓶颈？——投递器按状态 + 时间索引批量扫，单表按日期分区，历史消息归档；写入与业务同事务，只多一次 insert，成本可接受。
2. 为什么不能「先发消息再提交事务」？——消费者可能在事务提交前就收到消息，读到未提交数据或业务尚未生效，出现「消息先到、账没扣」。
3. TCC 的空回滚和悬挂怎么防？——Try 前先落事务控制表，Cancel 检查 Try 是否执行过（空回滚直接返回成功并记录），Confirm/Cancel 都要求幂等；用事务控制表的状态机统一判定。
