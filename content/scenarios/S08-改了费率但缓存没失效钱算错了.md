## 30 秒简述

缓存与数据库的一致性没有「绝对强一致」的低成本解，只有**把不一致窗口压到可接受范围**。主流是 **Cache Aside：读时未命中回源并回填，写时先更新数据库、再删缓存**（不是更新缓存）。删除失败要补偿（重试 + 消息），并给缓存设 TTL 兜底；对一致性敏感的配置（费率、限额）再加**延迟双删**或**binlog 订阅异步失效**。核心认知是：不一致的概率来自「并发读写交错」，不是代码写错；所以设计目标是「让最坏情况有界且可自愈」，而不是消灭它。

## 是什么

1. **为什么是「删缓存」而不是「更新缓存」**：
   - 更新缓存需要每次写都算一遍缓存值（写多读少时纯浪费），且并发写会乱序覆盖；
   - 删除是惰性的，下一次读自然回源，逻辑简单。
2. **Cache Aside 的不一致窗口**：
   - 线程 A 读未命中 → 查库得旧值 V1；
   - 线程 B 写库为 V2 → 删缓存；
   - 线程 A 把 V1 回填缓存 → **缓存里是旧值，且没有过期时间就会一直错**。
   - 概率低（要求读比写慢且恰好交错），但对资金类配置（费率）后果重。
3. **降低概率的手段**：
   - **延迟双删**：更新 DB 前删一次，提交后延迟 500ms~1s 再删一次，覆盖「回填发生在删除之后」的窗口。
   - **binlog 订阅**（Canal / 自研）：DB 变更后异步发消息删缓存，删除失败进重试队列，做到最终一致且与业务代码解耦。
   - **缓存永不过期 + 版本号**：缓存里带 `version`，读取时比对 DB 版本，落后则异步刷新。
   - **TTL 兜底**：任何方案都必须有 TTL，作为最后一道自愈手段。
4. **写失败与删除失败**：更新 DB 成功但删缓存失败（网络抖动、Redis 抖动），必须落一张「待失效」表或发消息重试，不能忽略异常。
5. **强一致场景**：直接不缓存，或用「分布式锁 + 读写串行化」——代价是吞吐骤降，只在极少数场景可接受。

## 为什么这么设计

**为什么接受最终一致**：让缓存与 DB 强一致，等于让缓存的每次读都去数据库验证一次，缓存就失去了意义。工程上的取舍是「用极小的不一致窗口换 10~100 倍的读性能」。

**代价**：不一致窗口内会读到旧值，业务要能容忍（例如费率变更后 1 分钟内仍按旧费率计费，差额可追溯），或者用「配置生效时间」做业务层规避——改费率时写「生效时间为次日 0 点」，让新旧费率天然有明确边界，这比追求缓存强一致更实用。

## 不用会怎么样

- 运营改费率后缓存没失效，10 分钟内所有交易按旧费率计费，少收手续费，且对账时无法区分「少收」与「漏收」。
- 缓存没有 TTL，一次回填旧值意味着永久错误，只能人工清缓存。
- 更新缓存而非删除：两个并发写按不同顺序落缓存，最终缓存是旧值，且看起来「写成功了」。
- 删除失败被 `try-catch` 吞掉，问题静默存在，直到客户投诉才发现。

## 替代方案

| 方案 | 一致性 | 适用 | 说明 / 风险 |
|---|---|---|---|
| Cache Aside（更新 DB + 删缓存） | 最终一致（毫秒~秒） | 绝大多数读多写少场景 | 主流；有极小概率回填旧值 |
| 延迟双删 | 最终一致（更小窗口） | 费率、库存等敏感配置 | 延迟时间靠经验，第二次删也可能失败 |
| binlog 订阅异步失效 | 最终一致（秒级） | 多实例、多语言消费 | 解耦彻底；依赖 binlog 与中间件可用性 |
| 分布式锁 + 读写串行 | 准强一致 | 极敏感、低并发 | 吞吐差，锁本身有故障风险 |
| 不做缓存，直接查库 | 强一致 | 低频配置、强一致要求 | 最简单；扛不住高 QPS |

## 项目中如何使用

- **招银云创费率与参数缓存**：费率按「商户 + 产品 + 卡类型」缓存，key 带版本号；运营修改后走「更新 DB → 发失效消息（RocketMQ）→ 各实例消费后删本地缓存 + Redis 缓存」，失败进重试队列并告警。同时费率表带 `effective_time`，改价默认次日生效——**用业务规则把不一致窗口变成零**，这是最省事的做法。
- **shopline 商户配置**：商户的支付方式开关、限额缓存在本地 Caffeine + Redis 两级，变更走 binlog 订阅失效，本地缓存 TTL 60s 兜底。两级缓存的好处是抗 Redis 抖动，代价是要处理「两级不同步」，靠短 TTL 收敛。
- **一次事故**：Redis 主从切换期间删除操作失败，异常被 `catch` 后只打了日志，缓存保留旧限额 40 分钟，导致部分商户超额支付被渠道拒绝。修复：删除失败写「待失效表」，定时任务补偿，并把「删除异常」纳入监控指标。

## 常见陷阱

- 答「先删缓存再更新 DB」——并发下脏数据概率更高，这是经典错误答案。
- 只讲 Cache Aside，不讲「删除失败怎么办」和「TTL 兜底」，方案不闭环。
- 把缓存一致性当成纯技术问题，忽略「业务上能不能用生效时间规避」这个更优解。
- 面试官会追问：「延迟双删延迟多久，为什么」——要答「大于一次读请求的耗时（查库 + 回填），通常 500ms~1s」，并承认这是经验值，不是精确保证。

## 三层追问

1. 为什么「先更新 DB 再删缓存」比「先删缓存再更新 DB」好？——先删会让后续读立刻回源读到旧值并回填，等写完成时缓存里已是旧值；后删则只有「读回填晚于删」这一种窄窗口。
2. 缓存击穿和一致性问题的区别？——击穿是「热点 key 失效瞬间大量请求打库」，解决用互斥锁/逻辑过期；一致性是「缓存内容与 DB 不同」，解决用失效策略。两者常被混答。
3. 多级缓存怎么保证一致？——统一由「变更事件」驱动失效，本地缓存靠短 TTL 与广播消息收敛；不要试图让两级缓存强同步。
