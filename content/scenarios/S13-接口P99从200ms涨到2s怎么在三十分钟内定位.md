## 30 秒简述

排查顺序固定为**先止血、再定位、后根治**。止血优先级是「限流 → 降级 → 回滚」，因为用户等不起，而定位可能要几十分钟。定位用四看：**看指标**（P99、错误率、GC、线程池、连接池、DB 慢查询数）、**看链路**（trace 里找最慢的那一段 span，而不是看总耗时）、**看日志**（慢 SQL、异常堆栈、超时）、**看变更**（当天有没有发布、配置改动、活动流量）。经验上 80% 的劣化来自五类：GC 停顿、连接池打满、索引失效或慢 SQL、下游超时引发重试风暴、锁竞争——先把范围压到某一类，再往下细查。

## 是什么

1. **为什么看 P99 不看平均**：平均值会被大量快请求稀释，2% 的慢请求在平均上看不出来，但用户真实感受到的就是那 2%。
2. **分层切分**：接入层（网关/Nginx）→ 应用层（线程池、GC、锁）→ 中间件（Redis/MQ/注册中心）→ 存储层（DB 慢查询、连接池）。每一层都有对应的黄金指标。
3. **trace 的作用**：一条慢请求拆成若干 span，先看「哪一段变长了」，再看那一段的细节（SQL 执行时间、Redis RT、下游 RT），避免盲目翻代码。
4. **常用工具**：`jstat -gcutil` 看 GC 频率与老年代占用、`jstack` 看线程阻塞（BLOCKED/WAITING 分布）、`jmap -histo` 看对象堆积、Arthas 的 `trace`/`watch`/`profiler` 在线定位、`explain` 看执行计划。
5. **变更关联**：故障开始时间点与发布/配置推送/定时任务/流量高峰对齐，往往能一步定位。

## 为什么这么设计

线上故障的第一约束是时间，不是彻底性。止血（限流/降级/回滚）成本低、见效快，能把影响面锁住；定位需要证据链，急不来。顺序反了就会出现「查了两小时，用户已经投诉了两小时」。

代价也很清楚：降级意味着部分功能不可用（例如对账查询降级为只返回汇总不返回明细），回滚可能丢掉新功能。这些取舍必须提前在预案里写清楚，而不是现场拍脑袋。

## 不用会怎么样

- 只加机器：如果是慢 SQL 或锁竞争，加机器只是把压力分摊到更多节点，DB 依然是瓶颈，问题会以更快速度复现。
- 只看平均值：监控一片绿，用户已经在投诉。
- 直接重启：把现场（线程栈、堆、连接状态）全丢了，下次还会复现。
- 把重试当修复：下游超时 → 上游重试 → 下游更慢 → 雪崩，故障半径扩大十倍。

## 替代方案

| 方案 | 适用 | 说明 / 风险 |
|---|---|---|
| 直接回滚 | 明确与发布相关 | 最快；如果根因是数据或流量，回滚无效 |
| 限流 / 降级 | 流量突增、下游劣化 | 见效快；影响部分功能，需产品确认 |
| 扩容 | CPU/连接数确实打满 | 简单；对慢 SQL、锁、GC 无效，还可能加剧 DB 压力 |
| 全链路追踪 + 指标定位 | 所有场景 | 最有效；依赖可观测基建是否到位 |
| 线上 profiling（Arthas） | 代码级热点 | 精准；有性能开销，生产需谨慎 |

## 项目中如何使用

- **某银行对账查询 P99 从 200ms 涨到 2s**：先看 Grafana——QPS 没变、应用 CPU 正常、**DB 连接池活跃数打满、慢查询数陡增**，范围瞬间收敛到存储层。Arthas `trace` 定位到某条明细查询，`explain` 显示走了全表扫描：某商户传了 `pageSize=5000` 且带了一个非索引字段的排序条件。
- **止血**：接口层限制 `pageSize ≤ 200`、对非核心字段降级不返回，5 分钟内 P99 回到 300ms。
- **根治**：深分页改游标（`where id > lastId limit n`）、按查询条件补联合索引、把排序字段纳入覆盖索引；同时对账明细按账期分区，避免全表扫描。
- **另一次是 GC**：老年代占用 90%、Full GC 每两分钟一次，`jmap -histo` 发现对账结果集被全量加载进内存（一次查几十万行），改成流式游标 + 分批处理，Full GC 消失。
- **沉淀成预案**：把「对账查询劣化」写成 SOP——先看哪四个指标、限流阈值多少、降级开关在哪、谁有权点，值班同学照着做，不依赖个人经验。

## 常见陷阱

- 上来就 `jstack`：线程栈只能看当前瞬间，没有指标与 trace 支撑时容易误判（比如把正常的 WAITING 当成死锁）。
- 把「加机器」当第一反应：CPU 不高的情况下扩容毫无意义。
- 忽略变更关联：其实是一次配置推送把连接池从 50 改成了 5，却在代码里翻了半天。
- 面试官会追问「如果是下游超时导致的重试风暴怎么处理」——答：先关重试或改成单次调用 + 快速失败，再对下游做熔断与隔离舱，最后才是修下游。

## 三层追问

1. **P99 高但 P50 正常，说明什么？**——长尾问题，通常是锁等待、GC、连接池排队、个别慢 SQL；如果是全局资源打满，P50 也会一起涨。
2. **怎么区分「应用慢」和「DB 慢」？**——看应用侧 span 里 SQL 占比与 DB 侧的慢查询日志、连接池等待时间；连接池等待高说明是 DB 吞吐不够，SQL 执行时间长说明是单条语句问题。
3. **止血之后为什么还要根治？**——止血只是把影响面压住，根因还在；下一次流量峰值会以同样方式复现，而且降级本身有业务代价，不能长期挂着。
