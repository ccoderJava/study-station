## 30 秒简述

排查顺序固定：**先定位（哪条 SQL、哪个 mapper、哪个时间点）→ 再解释（`EXPLAIN` 看 type/key/rows/Extra）→ 再改（索引或 SQL 形态）→ 最后防回归（审核 + 监控 + 门禁）**。九成慢 SQL 是三类原因：**没走索引**（隐式转换、函数包裹字段、违背最左前缀）、**要走但回表太多**（选择性差、覆盖索引缺失）、**数据量本身超纲**（深分页、全表扫描、大表未分区/归档）。治理优先级是「改 SQL > 加索引 > 拆表」，因为加索引有写入成本，拆表有迁移风险。

## 是什么

1. **定位**：
   - 慢日志（`long_query_time=1`，`log_queries_not_using_indexes`）、`performance_schema.events_statements_summary_by_digest` 按摘要聚合排序。
   - 应用侧：MyBatis 插件在 `StatementHandler.prepare` 计时，带上 `MappedStatement.id` 上报，能直接定位到 `XxxMapper.selectByCondition`，而不是只看到一条 SQL 文本。
   - 现场：`show processlist` 看长事务与锁等待，`information_schema.innodb_trx` 看持锁。
2. **解释**（`EXPLAIN` 关键字段）：
   - `type`：`const > eq_ref > ref > range > index > ALL`，到 `index/ALL` 基本就是问题。
   - `key` / `key_len`：是否用上预想的索引，`key_len` 能看出联合索引用了几列。
   - `rows`：预估扫描行数，与实际返回行数的比值决定索引是否高效。
   - `Extra`：`Using filesort`（排序无索引）、`Using temporary`（分组/去重无索引）、`Using index`（覆盖索引，好）。
3. **常见病因**：
   - 隐式转换：`where account_no = 1234567890`（字段 varchar，传数字）→ 索引失效。
   - 函数/运算包裹：`where date(create_time) = '2026-11-03'` → 改成范围查询。
   - 最左前缀断裂：联合索引 `(merchant_id, status, create_time)`，只查 `status` 用不上。
   - 回表过多：二级索引拿到 50 万主键再回表，比全表扫还慢，需要覆盖索引。
   - 深分页：`limit 1000000, 20` 要扫 100 万行，改延迟关联或游标（`where id > last_id`）。
   - 大表：流水表 2 亿行，任何范围查询都要靠分区裁剪或归档。
4. **治理手段**：联合索引按「等值在前、范围在后、排序列最后」排；能用覆盖索引就不回表；把大 SQL 拆成「先查主键再批量取详情」；历史数据冷热分离（热表 3 个月，冷表归档，查询按时间路由）。

## 为什么这么设计

MySQL 的优化器是**基于成本**的，索引选择依赖统计信息（`innodb_stats_persistent`），所以会出现「明明有索引却不走」——可能是统计信息过期、可能是回表成本估算高于全表扫、也可能是索引区分度太低。

治理的取舍是：**加索引提升读，牺牲写**（每个二级索引都要维护 B+ 树，写入放大）；**覆盖索引提升读，牺牲空间**；**分表提升单表性能，牺牲跨表查询与运维复杂度**。所以顺序永远是先改 SQL 形态，再考虑结构变更。

## 不用会怎么样

- 一个后台导出功能全表扫 2 亿行，把 buffer pool 冲干净，线上核心接口的命中率从 99% 掉到 70%，全线变慢——**慢 SQL 的杀伤力不止于它自己**。
- 深分页查询在高峰期把 CPU 打满，主从延迟从 100ms 涨到 30s，读到大量过期数据。
- 隐式转换的查询平时数据少看不出来，数据量涨到千万级后突然变慢，且不会报错，只能靠监控发现。
- 没有 SQL 审核，新需求上线带一条 `like '%xx%'`，一周后成为最大的慢查询来源。

## 替代方案

| 方案 | 适用 | 说明 / 风险 |
|---|---|---|
| 优化索引 + 改写 SQL | 绝大多数场景 | 成本最低见效最快；索引要评估写入影响 |
| 冷热分离 / 归档 | 流水、日志类大表 | 效果好；跨期查询要路由，历史查询变慢 |
| 分库分表 | 单表 > 5000 万且持续增长 | 解决容量问题；跨分片查询、分布式事务复杂 |
| 读写分离 + 从库查询 | 读多写少 | 缓解主库压力；主从延迟导致读到旧数据 |
| 换存储（ES / ClickHouse） | 多条件组合查询、报表 | 查询能力强；数据同步与一致性成本高 |

## 项目中如何使用

- **某银行账务流水查询**：流水表按 `account_date` 分区，热数据保留 3 个月，历史归档到冷表。核心查询条件固定为「账户 + 时间范围 + 状态」，建联合索引 `(account_no, status, create_time)`，让等值列在前、范围列在后；列表页只查需要的 8 个字段，做成覆盖索引避免回表。深分页改成「按 `id` 游标翻页」，导出走异步任务 + 分批拉取，不再让用户在页面上等。
- **某支付公司对账撮合**：撮合查询按「渠道 + 账单日期」定位，避免在 2 亿行上做范围扫描；批量比对时先只取 `(渠道单号, 金额, 状态)` 三列进内存建哈希，需要的详情再按主键批量回查，把「N 次单条查询」变成「一次 IN 查询」。
- **防回归**：MyBatis 插件采集超过 500ms 的语句并按 mapper 方法聚合告警；上线前 SQL 走审核平台（必须 explain，`type=ALL` 直接打回）；索引变更走 DBA 流程，禁止在业务低峰外的时间加索引。

## 常见陷阱

- 只看 `EXPLAIN` 的 `key` 有值就以为没问题，不看 `rows` 和 `Extra`——用上索引但扫了 80 万行一样慢。
- 无脑加索引：单表 15 个索引，写入性能下降 40%，且优化器选错索引的概率上升。
- 认为「加了 limit 就快」——深分页的 limit 前面那个大数字才是杀手。
- 面试官会追问：「explain 显示走了索引但还是慢，可能是什么」——回表太多、索引选择性差、排序无法用索引、锁等待、返回数据量过大（网络传输）。

## 三层追问

1. 为什么联合索引要「等值在前、范围在后」？——B+ 树按列顺序排序，范围列之后的列无法再用于精确定位；把范围列放最后，前面的等值列能最大化缩小扫描区间。
2. 覆盖索引为什么快？——二级索引叶子节点已包含所需列，不需要回表取整行，减少随机 IO；代价是索引变宽、写入成本上升。
3. 主从延迟下怎么做一致性读？——强一致读走主库；或记录位点（`GTID`）等待从库追平；或对「刚写完立刻查」的请求强制路由主库（同会话 sticky）。
