## 30 秒简述

切流方案四件套：**分流入口**（按商户维度切，不是按比例切随机请求，同一商户必须整链路走同一边）、**灰标透传**（HTTP header → ThreadLocal → MQ 消息属性 → 消费端，异步链路不丢标识）、**双跑比对**（新旧链路并行，新链路结果只比对不生效，比对响应、落库、状态机三处）、**护栏与回滚**（成功率、P99、未知态笔数、对账差异四个指标做阈值，触发即自动切回，且新链路产生的数据要能回灌旧链路）。节奏是 1% → 5% → 10% → 30% → 70% → 100%，每档至少观察一个完整日切和一个对账周期。

## 是什么

1. **分流维度**：按商户/渠道切而不是按请求比例切。同一商户的支付、退款、对账必须落在同一条链路，否则状态机与账务会分裂。
2. **灰标透传**：入口在 header 打 `x-gray: v2`，应用层放进 ThreadLocal，MQ 生产时写进消息属性，消费端读出来继续走新逻辑；任何一跳丢了标识，就会出现「写在新库、消费走旧逻辑」的脏数据。
3. **三种切流形态**：
   - 影子流量：复制一份请求给新链路，响应丢弃、写入影子表，用于提前发现差异。
   - 双写比对：真实请求写两条链路，以旧链路为准，新链路结果只做差异记录。
   - 真实切流：新链路生效，旧链路只做备份读取。
4. **比对口径**：响应报文（金额、状态、错误码）、落库结果（表、字段、条数）、状态机流转（新链路是否多/少一次状态跃迁），三类差异分表记录、逐条归因。
5. **护栏指标**：请求成功率、P99 耗时、未知态笔数、对账差异笔数、资金类异常（重复支付/负余额）零容忍。
6. **回滚**：配置中心开关秒级切回 + **数据反向同步**（新链路已产生的数据回灌旧链路或做兼容读），这是最容易被漏掉的一环。

## 为什么这么设计

重构真正的风险不是「新代码有 bug」，而是「不知道什么时候出的错、错了多少笔」。灰度把一次性的大爆炸拆成可观测的小步，把「出错」变成「出错但影响可控」。

按商户切而不是按比例切，是因为资金链路的正确性依赖状态连续性——同一商户一半请求走旧链路、一半走新链路，等于人为制造分布式不一致。

代价很实在：双跑期间机器与存储成本翻倍、比对差异要人盯、灰标透传要改全链路（包括定时任务与 MQ 消费者），回滚要准备数据回灌脚本。

## 不用会怎么样

- 一次性全量切：新链路一个空指针影响所有商户，故障时长 = 发现时间 + 回滚时间 + 数据修复时间。
- 只切读不切写：读新库、写旧库，两边数据分叉，对账时全是对不上的单。
- 灰标不透传 MQ：生产走新逻辑、消费走旧逻辑，同一笔单被处理两次或状态回退。
- 回滚没有数据回灌：切回旧链路后，新链路已经扣的钱旧系统看不见，形成单边账，只能人工补。

## 替代方案

| 方案 | 适用 | 说明 / 风险 |
|---|---|---|
| 停机切换 | 内网系统、可接受维护窗口 | 最简单；支付类系统基本不可接受 |
| 蓝绿部署 | 整机替换、回滚快 | 资源翻倍；数据层仍是共享的，解决不了 schema 变更 |
| 按商户灰度 | 支付/财资类系统 | 推荐；粒度可控，问题影响面就是那几个商户 |
| 按流量比例灰度 | 无状态服务、读多写少 | 简单；资金链路不适用（状态割裂） |
| 双写 + 影子比对 | 重构、迁移 | 最稳；成本最高，需要专门的数据比对工具 |

## 项目中如何使用

- **某银行 C9→C10 重构**：先在白名单 2 家商户上双跑两周，比对工具每天输出差异清单（响应字段级 diff + 落库行数 diff + 状态机轨迹 diff），差异归零后才开始按 1% → 10% → 30% 阶梯切流。
- **护栏**：成功率低于 99.5%、未知态单日超过 5 笔、对账差异超过 3 笔，任一触发自动回切；切流窗口限定在工作日 10:00–16:00，避开日终批处理。
- **一次真实回切**：切到 30% 时发现新链路调银行超时后直接落失败（旧链路是落未知态），当晚对账多出 3 笔单边账。因为回切开关和回灌脚本都提前演练过，5 分钟内切回，3 笔差异由日终对账修正，没有形成客诉。
- **流量回放是前置条件**：切流前把生产脱敏报文回放到新链路跑了两周（见 S03），先解决「明显跑不通」的问题，灰度只负责解决「跑得通但结果有细微差异」的问题。

## 常见陷阱

- 只做比例灰度不做商户灰度：资金链路状态割裂，问题排查时根本分不清是哪条链路写的。
- 回滚方案只写在文档里没演练：真出事时发现开关失效、脚本报错。
- 比对只比响应不比落库：接口返回一致，但金额精度、状态字段、时间戳已经不同。
- 面试官会追问「灰度期间新链路写的数据，旧链路怎么读」——答：兼容读（旧链路加新表读适配）+ 反向同步 + 双写兜底，三者至少要有一种，否则回滚即丢单。

## 三层追问

1. **为什么不能直接按 1% 请求比例切？**——请求是随机的，同一商户的「支付 → 回调 → 退款」可能落在不同链路，状态机与账务分裂；按商户切保证业务闭环在一个链路上。
2. **双跑期间以谁为准？**——以旧链路为准，新链路只记录不生效；一旦发现新链路更正确，也先修差异再切，不能中途换基准。
3. **灰度要观察多久？**——至少覆盖一个完整日切 + 一个对账周期（T+1），因为很多差异只在批处理和对账时才暴露，白天跑得再好也不算通过。
