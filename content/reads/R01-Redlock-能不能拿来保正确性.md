## 30 秒摘要

Kleppmann 2016 年批 Redlock 的那篇，结论是别拿它保正确性。他把锁的用途劈成两半：只为省事的场景（多扣一次钱、多发一封邮件）用单机 Redis 就够；要防数据损坏的场景，Redlock 缺 fencing token，还假设网络延迟、进程暂停、时钟漂移都远小于租约。替代方案是 ZooKeeper 加单调递增的 token，并且存储端要校验 token 只增不减。放到支付里看，锁只负责减少冲突，真正兜底的是幂等和唯一约束。

## 它讲了什么

文章上来先问一句：你拿这把锁干什么用？

- 按「锁失效了会怎样」分成两类。效率类失效的代价是多花几美分、用户收到两封同样的通知；正确性类失效的代价是数据损坏、账目对不上。这个切分决定了后面所有结论。
- 效率类不需要五个节点加多数派。单实例 Redis，SET NX 加锁、比 value 再删，异步复制到从库就行，代价是可能丢锁，但这类场景本来就能忍。
- 正确性类要面对两件事。锁是有租约的，客户端自己不知道自己已经过期；而任何一个分布式锁只要靠租约，就必须回答「过期之后原来的持有者还在写怎么办」。
- 第一个答案是 fencing token。锁服务每次发放锁时给一个严格递增的号，客户端带着号去写，存储端记住处理过的最大号，比它小的直接拒。文章的例子是 Client 1 拿到 33、卡住、Client 2 拿到 34 写入，Client 1 恢复后带 33 来写，被拒。
- 第二个答案他否定掉了：Redlock 拿时间当共识用。它假定网络延迟有界、进程暂停有界、时钟误差有界，三个都远小于 TTL。
- 举了两个破法。五个节点 A 到 E，Client 1 在 A、B、C 上加锁成功，C 的时钟往前跳，锁提前过期，Client 2 在 C、D、E 上加锁成功，两个客户端同时认为自己在持锁。另一个更常见：Client 1 向五台都发了请求，响应还在路上，客户端自己发生 stop-the-world GC，五台锁全过期，Client 2 加锁成功，Client 1 醒来从内核缓冲区读到「加锁成功」。
- 结论是 Redlock 两头不靠。效率场景它太重，正确性场景它不够，建议换成 ZooKeeper（Curator 的锁配方，zxid 或 znode 版本号当 token）或带合理事务保证的数据库，并且资源端强制校验 token。

## 关键论据

- 五副本、多数派才能算加锁成功，这是 Redlock 的基本盘。
- fencing token 的例子用了 33 和 34 两个具体数字，关键在单调，不在唯一。Redlock 发的是随机值，没法比较大小。
- stop-the-world GC 被记录到持续数分钟，远长于常见租约；HBase 出过这个故障。CMS 这类并发收集器偶尔也要停世界。
- 除 GC 之外，缺页中断、EBS 读盘变成同步网络请求、CPU 争抢、误发 SIGSTOP 都会让进程停住。
- GitHub 那次著名事故里，数据包被延迟了大约 90 秒，足够让租约在写入到达前过期。
- Redis 用 gettimeofday 判断键过期，这个时钟不是单调的，NTP 步进校正能让它前跳几分钟，也能回拨。
- 文中提到 Redlock 已经有十多个独立实现，作者认为这类算法不太可能过得了 Jepsen。
- 效率类失效的成本他给的是「多付 5 美分 AWS 费用」，用来说明这类场景根本不值得上五节点。

## 我的判断

先说我认的部分。锁失效代价决定方案重量，这个分法比讨论「哪个锁实现更好」有用得多。以前看团队选型，争的是 Redisson 还是 ZooKeeper，没人先问一句「锁挂了会怎样」，结果给一个只用来防重复导出的任务上了套复杂的锁。

再说我保留的地方。文章把 ZooKeeper 当成安全出口，但它给的只是 token 的生成能力，真正的防线在资源端：存储必须拒掉倒退的 token。这一条在业务代码里最难落地，等于要求每一次写库都带上 token 并做比较。多数团队做不到，于是「换了 ZooKeeper 就安全」变成心理安慰。

还有一层文章没展开：fencing 只保护单一资源。支付里一次操作往往要写订单、写流水、改余额，三个资源三套 token，中间还可能调外部渠道。锁的边界跟事务的边界对不上，token 只能保证某一次写不倒退，保证不了整笔业务。

支付场景里我把它归到正确性那一档：锁失效的后果是重复扣款、重复代发，属于要赔钱的级别。但这不意味着要去找一把绝对可靠的锁，而是承认锁不可靠，然后在下游补两道：幂等键加唯一索引，状态机限制非法跃迁。锁的价值从「防住」降到「少冲突、少回滚」，这个定位反而更经得起线上折腾。

顺带说一句，文章的语气值得学。他全程在拆假设，不讲「最佳实践」。面试里这么答，比背结论有说服力。

## 落到我这里

- 站内对应：`D3 分布式锁` 讲的是实现与坑，这篇补的是「用它的前提」；`E5 资金安全` 里的幂等与防重复，是锁失效之后的那道网。
- 项目经历能接上：某银行资金安全加固里做代发批量的重复提交防护，最后靠的是业务唯一键加状态机，锁只用来压住同一批次的并发入口。这段可以按「锁 + token + 幂等」三层讲。
- 面试怎么用：被问「Redis 分布式锁有什么问题」，先反问用途，再讲租约与 GC 暂停，再给 fencing token，最后落到「锁只是减少冲突，兜底靠幂等」。四步讲完，比列 Redlock 的五个步骤有信息量。
- 值得再挖的：ZooKeeper 的 zxid 怎么当 token 用、Curator 的锁配方怎么处理会话过期，这块我只有概念，没在生产上配过。
